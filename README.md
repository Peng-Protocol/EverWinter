# ❄️ EVERWINTER

**EverWinter** is a browser-based trading suite for Bybit USDT Perpetuals executing the **Winter-Chaser** strategy. See the [Strategy Guide](StrategyBook.md) for trading logic and rationale.

## Setup

Open any `.html` file directly in a browser. No build step, no server, no installation. Alpine.js and Bootstrap 5 are loaded from CDN — an internet connection is required on first load (cached after that).

To trade proactively, run `PseudoChaser` (longs only) or `PseudoWinter` (shorts only) with `Still-Water` and then `MultiIndicator` loaded; the same two files work on both bots. **Side check:** a plugin built for the other bot no longer refuses to load. Each plugin declares `targetBot` (`pseudowinter`, `pseudochaser` or `both`); if it names the other bot, it loads and runs anyway and its Plugin Manager card shows a yellow ⚠ warning (also logged once on load). A plugin that declares `both` (any case), or declares nothing, never shows the warning. ([more](#general-details))

**Load order**: EverWinter / SunChaser first (if live), then **Still-Water**, then **MultiIndicator**. MultiIndicator declares Still-Water as required and won't run without it. **Upgrading from the separate plugins**: remove Ashfall-Chaser, Permafrost-Winter, MultiIndicator-Chaser and MultiIndicator-Winter, then load the two merged files. Still-Water moves this side's saved `af*`/`pf*` settings to `sw*` and its stored data to the new keys once; MultiIndicator moves Winter's `miw*` settings and position tags to `mic*`.

## EverWinter / SunChaser (Live Trading Plugins)

EverWinter turns PseudoWinter into a live short-only Bybit bot; SunChaser does the same for PseudoChaser as long-only. Both sign requests with the stored `__ew_creds`/`__sc_creds` API key and place real orders — the topbar reads **Very Real Orders** once loaded, in place of the base simulation's **No Real Orders**.

### Order Handling (Open / Close tabs)

The plugin's accordion has three tabs: **API** (credentials), **Open** and **Close**. 

**Limit** here means a limit priced through the last price by the **Limit offset** (default 0.1%), so it normally fills like a taker; a negative offset makes it passive. **Market** sends a market order (IOC for entries, reduce-only IOC for closes). A **try** is one limit order, cancelled and repriced off a fresh last price if it doesn't fill. ([more](#general-details))

**Open and Close tabs** (the Close tab applies to every bot-initiated close: manual, runtime, cascade/sacrifice, bail sweeps and the post-bail re-check; exchange-native TP/SL closes are filled by the exchange and aren't affected)

| Setting | Open tab | Close tab |
|---|---|---|
| **Order type** (`ewOpenType`/`scOpenType`, `micCloseType`; default Limit) | Limit or Market entry. | Limit or Market (reduce-only) close. |
| **Limit offset** (`micOpenOffsetPct`/`micCloseOffsetPct`, default 0.1) | Distance through last price, in %. | Same. |
| **Limit tries** (`micOpenTries`/`micCloseTries`) | Default **1** (1–20): limit attempts before the fallback, or giving up. | Default **10** (1–100): reduce-only limit attempts before the fallback. |
| **Fall back to market** (`micOpenFallback`/`micCloseFallback`, default **on**) | After the limit tries go unfilled, send one market order. Off: give up and put the symbol on cooldown. | After the limit tries go unfilled, close with a reduce-only market order, repeated until flat. Off: keeps repricing the limit until the position is flat; a close never gives up. |
| **Fill timeout per try** (`micFillTimeoutMs`, default 10 s) | How long each limit try waits for a fill before it's cancelled. | n/a |
| **Cooldown after failed open** (`micFillCooldownMs`, default 15 min) | How long a symbol is skipped after an entry that placed an order but never filled. A rejected order doesn't trigger it. | n/a |
| **Reprice interval** (`micCloseRetryMs`, default 10 s) | n/a | Time between close tries. After the fallback, market closes repeat at most every 4 s. |

With the defaults, an entry that doesn't fill on its first limit goes to market, and a close that hasn't filled after ten limit tries (about 100 s) goes to market.

## Main Config

Changes take effect immediately and are persisted to localStorage automatically.

| Setting | What it does |
|---|---|
| **Scan Interval** (`scanMins`) | How often (minutes) the bot runs a full market scan. Controls both entry frequency and the scan bar in the UI. Can be changed while the bot is running (PseudoWinter/PseudoChaser): the interval is frozen when each cycle starts, so an edit applies from the next cycle and never fires or shifts the current one. |
| **Max Positions** (`maxPos`) | Maximum simultaneously open positions. No new entries open once this is reached. |
| **Leverage** (`leverage`) | Position leverage. Affects order size, TP/SL prices, and EDa thresholds. |
| **Min Notional** (`minNotional`) | Base margin per position in USDT. Actual order size = minNotional × leverage. |
| **Entry TP** (`entryTpRoi`, default 50%) | Take-profit ROI % target. When EDa is active this is the buffered target — the debt-free close happens at a lower percentage. In DCA Mode this is also the base the per-stage TP ladder scales down from (entry TP ÷ (stage+1), min 3%). |
| **Binary Mode** (`binaryModeEnabled`) | On: every position gets a take-profit and a stop-loss at entry and no DCA adds (`binaryTpPct`/`binarySlPct`, both default 50%). Off: multi-stage DCA. Add orders trigger below entry (PseudoChaser) or above it (PseudoWinter), each with a lower TP ROI target, and the stop-loss (`dcaSlPct`, default 16%) only arms once every first-wind DCA stage has filled. The DCA config controls need the `dca-long`/`dca-short` plugin (`plugins/modes/`); the binary and DCA logic itself is in the base bot either way. |
| **DCA Stages** (`dcaStages`, default 1) | Number of DCA add orders (1–6 in the plugin slider). Each stage has its own trigger slider (`dcaAddPct1`mic`dcaAddPct6`, defaults 3 / 6 / 12 / 18 / 24 / 30), set as % below entry for PseudoChaser or above entry for PseudoWinter, and only the sliders for selected stages appear. Triggers always increase by stage: lowering one stops at the previous stage's trigger, and raising one pushes the later stages up. Configs saved before per-stage triggers (a fixed 1.5%, then +3% per stage for non-3 stage counts) are migrated on load/import so they keep the same trigger prices. |
| **DCA Add Notional** (`addNotional`) | Margin (USDT) added per DCA stage — separate from **Min Notional**, which only sizes the initial entry. |
| **Drawdown Throttle** (`drawdownThrottleEnabled`) | Halts new entries for `drawdownHaltHours` (default 12h, free-entry field with no upper bound) when the rolling 6h realized PnL falls below a loss threshold. The Halt tab shows the live 6h rolling PnL. Its **Clear 6hr Record** button (with confirmation) zeroes that window manually, whether or not a halt is active. |
| **Drawdown Factor** (`drawdownThrottleFactor`) | Loss threshold as a multiple of entry margin. At 0.5× with $1 margin, $0.50 of rolling losses triggers the halt. |
| **Bail on Trigger** (`drawdownBailEnabled`, default on) | When on, triggering the Drawdown Throttle halt also immediately closes every open position at market (`bailAll()`) — the same sweep the Danger Zone's manual **Bail All Positions** button runs, and what the **BAIL** trade-card badge marks. |
| **Gains Lock** (`gainsLockEnabled`) | Halts new entries for 12 hours once rolling 6h profit hits a target. Banks a winning streak before it reverses. Same 6h rolling PnL readout and **Clear 6hr Record** button as Drawdown Throttle, shown in its own section of the Halt tab. |
| **Gains Factor** (`gainsLockFactor`) | Profit target as a multiple of entry margin. Same scale as Drawdown Factor. |
| **Manual Halt** | Button (Halt tab) that blocks all new position entry indefinitely until manually lifted. Independent of Drawdown Throttle and Gains Lock — overrides both and doesn't stack with either. |
| **EDa / Laggard Check** (`laggardCheckEnabled`) | Enables the Effective Debt Adjusted system. Realized losses are passed forward to surviving positions, which take higher TP targets to recover the debt. **Requires the EDa-Winter / EDa-Chaser plugin** (`plugins/modes/`). |
| **TP Buffer** (`laggardProfitOffset`) | Extra TP headroom reserved above the functional target (%). The debt-free close happens at `tpPct ÷ (1 + buffer/100)` — at 50% buffer with an 18% TP slider, trades close at 12% without debt. Requires the EDa plugin. |
| **Ticker Cooldown** (`bulkTickerCooldownHours`) | How long the bot reuses a cached bulk ticker fetch before hitting the API again (default 12h). The bulk list only says which symbols exist — criteria data never reads it — and the same window sets how long MI's re-entry block and the Ticker Graylist hold a closed symbol. |
| **Whiplash Audit** (`whiplashEnabled`) | When on, the position watcher fetches 1-minute klines near TP and near SL to confirm whether price spiked through either between watcher cycles. The SL audit (PseudoWinter 1.6.8 / PseudoChaser 1.6.9) uses the same proximity rule and 5-minute delay as the TP audit, with its own `_whiplashSlScheduled` flag, and closes at the SL price if a candle high (Winter) or low (Chaser) reached it. It aborts if the SL moved or cleared before the check ran. |
| **Whiplash Proximity** (`whiplashProximityPct`) | How close (%) to the TP or SL price triggers the kline audit. One setting drives both. |
| **Runtime Limit** (`runtimeHours`) | Maximum position age. Forces a close at the deadline if TP hasn't been hit. |
| **Symbol Banlist** (`banlistEnabled`) | When on, symbols on the ban list are excluded from all scans. Entries expire after 7 days. |
| **Position Price Feed** (`restPollEnabled`) | When on, replaces the WebSocket price stream for open positions with periodic REST calls; use it if the WS feed returns stale prices. Exactly one source runs at a time. Pseudo bots default to on and Psycho bots to off. ([more](#general-details)) |
| **Price Poll Interval** (`restPollBaseSec`) | Base polling interval in seconds for REST mode. The interval doubles automatically when price moves less than 0.1% between ticks and resets to base on any meaningful move. |
| **Dispatch Every** (`schedIntervalMs`) | Minimum gap (ms, default 150) between successive background fetches dispatched from the scheduling queue. Lower = faster background data turnover, at the cost of more simultaneous requests. |
| **Max Concurrent** (`schedMaxConcurrent`) | Hard cap (default 4) on background fetches in flight at once, regardless of how many subsystems have work queued. |
| **Slice Budget** (`schedSliceMs`) | How long (ms, default 8, 2–30) a scan stage runs before handing the browser back; a hidden tab uses 40 ms. Lower = smoother page, slightly slower scans. |
| **Follow Partner Bot** (`lfFollowPartner`) | When on, this bot stops fetching bulk tickers itself and uses the bulk list the partner hands over. The partner needs no toggle: it acts as leader while its heartbeat is fresh (newer than 2× **Scan Interval**), and this bot resumes scanning on its own if it goes stale. It also won't open a position on a ticker the leader already holds; Still-Water honours it too: a follower runs no sample batch of its own and adopts the leader's batch and scored store. ([more](#general-details)) |
| **Config Lock** (`cfgLocked`) | Locks all config controls to prevent accidental changes. On PseudoWinter/PseudoChaser it starts locked when the bot starts (and on page load) but can be unlocked at any time, including while the bot is running; this covers every config control, including Scan Interval, Leverage, Notional, Max Positions, Force Close Runtime and Binary TP/SL, and the plugin tabs follow the same lock. On EverWinter/SunChaser it still engages automatically while the bot is running, and it also locks the Open and Close tab controls (the tabs themselves stay navigable). |

## Stats Menu

The stats panel shows session-level metrics since the page was last loaded or state was cleared.

| Stat | Meaning |
|---|---|
| **Session PnL** | Cumulative realized PnL from all closed trades this session. |
| **Win / Loss** | Count of profitable vs. losing closed trades. |
| **Win Skew** | Share of total PnL magnitude (all closed trades, cumulative) that came from wins — sum of winning PnL ÷ (sum of winning PnL + sum of losing PnL). Weighted by trade size, not just a count of wins vs. losses. |
| **Avg PnL** | Mean realized PnL per closed trade. |
| **Open uPnL** | Unrealized PnL across all currently open positions. |
| **Positions** | Count of open positions. |
| **Last Scan** | Timestamp of the most recent scan cycle. |
| **Laggard** | The oldest open position — the EDa debt holder. Shows its current debt load when EDa is active. |
| **Persistence** | "Active" (live in-memory position count) vs. "Stored" (confirmed saved to localStorage). These should always match. |

**Persistence mismatch**: shown in red with a warning banner. It means a save failed or was overwritten, and usually clears on its own within a few seconds as the bot retries automatically. If it doesn't:
- Check the activity log for `[PST]`/`[PERSIST]` entries.
- Close any duplicate tabs of the same bot — a second tab can overwrite the first tab's saves with its own stale position count.

**Storage usage** (dropdown below Persistence, PseudoWinter/PseudoChaser only): breaks this bot's localStorage footprint down to one row per data type, including genuinely shared cross-bot keys but never the partner's private state. Oversized rows show in red with a **✕** to clear that bucket (with confirmation), and **Export** downloads the breakdown as a text file. The cross-bot corridor shows as one row of in-flight packets (normally empty), and plugin sources and plugin data (see Plugin data storage) show as IndexedDB rows that sit outside the localStorage quota and aren't part of the total.

**Power usage** (dropdown below Storage usage): a rolling average and peak of how many milliseconds the app spends reacting each second. A rising figure usually means a plugin panel left open somewhere is doing more work than it needs to — closing analytics panels you're not actively watching brings it back down.

**Ticker Graylist**: when MultiIndicator is enabled, the Stats menu shows a Ticker Graylist section listing symbols currently blocked from re-entry. It's empty when nothing is blocked. Each listed symbol clears itself automatically once the bulk ticker cooldown window elapses — no manual action needed.

### Actions Dropdown

- **Export** — Downloads current bot state (config, positions, closed trades, ban list, EDa state) as a `.json` file. Plugins with their own data (Still-Water scorer data) have their own Export in the Danger Zone of their accordions (see **Export & Import** under Still-Water Plugin) — the Stats menu Export covers the base bot state only.
- **Import** — Restores state from a previously exported `.json` file: config fields merge field by field and positions are replaced wholesale. A 5s debounce prevents accidental double-imports, and config keys that no longer belong to a loaded feature are dropped. ([more](#general-details))
- **Clear Closed Trades** — Wipes the closed trades list, resets session stats, and clears the 6hr drawdown/gains-lock rolling PnL windows. Open positions are unaffected.
- **Clear All** — Full reset. All positions, trades, stats, and config are wiped (config reverts to defaults).

### Activity Log

Timestamped entries for every significant bot event. Color coding:

- **White** — informational (scan results, entries, closes)
- **Yellow** — warnings (halts engaged, API retries)
- **Red** — errors (API failures, plugin conflicts)

Common prefixes: `[MHL]` manual halt · `[DWN]` drawdown throttle · `[GLK]` gains lock · `[PST]` (PseudoWinter) / `[PERSIST]` (PseudoChaser) save failures or recovered positions · `[ASH]` Still-Water events (both bots) · `[MI]` MultiIndicator events · `[SHR]` cross-bot corridor handovers and failed shares.

Bulk operations (Cascade, Sacrifice, Bail, scan entry bursts) are rolled up: `_logBatchBegin()` / `_logBatchEnd(label)` buffer per-event messages into one entry. Errors always log immediately. `log(m, type, live)` takes an optional third argument; `live = true` bypasses the buffer, so live close/entry retry lines (repricing, market fallback, per-try failures, fill timeout) show as they happen instead of after the whole roll-up finishes.

The log keeps the latest 300 entries in memory and in localStorage, dropping the oldest first. Each entry has a local `HH:MM:SS` string (`t`), which is what the UI shows, and an epoch-millisecond timestamp (`ts`). `ts` lets you match a log export to position and config exports, which are timestamped in UTC epoch; `t` alone can't be tied to a date or time zone.

## Trades Menu

The trades panel shows a card for each closed trade, newest first, with a close-reason badge: **TP**, **SL**, **FORCE** (runtime limit), **BAIL** (drawdown throttle bail), **Sub** (Substitution) or **Eject** (Ejection). Reasons added by other plugins show their own label. The simulation bots also show estimated fees on each card, and Net PnL, win/loss and the drawdown and gains windows are net of them. ([more](#general-details))

**Roll-up card**: when the closed trades list exceeds 50 entries, the oldest are compacted into a single roll-up card showing their net PnL, trade count, and the date range they cover. The roll-up is not a trade — it is a historical summary. In the PnL chart, the roll-up's net value acts as a baseline offset applied to every plotted point.

**PnL chart**: click the **PNL CHART** bar below the header to expand a cumulative PnL line chart, green when the net result is positive and red when negative. It only appears once at least 2 individual trades are closed. ([more](#general-details))

**CLEAR button**: removes all closed trades, resets session stats, and clears the 6hr drawdown/gains-lock rolling PnL windows. It asks for an inline confirmation ("Sure? Yes / No") before anything is deleted. ([more](#general-details))

## MultiIndicator Plugin (MI)

MultiIndicator is one file for both bots: it reads which bot it is loaded into and uses that side's conventions (Chaser longs, Winter shorts). All settings are `mic*`. The plugin filters entries with combinations of criteria called **slots**: a slot is an AND-gate, and a ticker only needs to match one slot to be eligible. No criterion is mandatory, and a slot (Auto or manual) can use any combination of `fund`, `va`, `iol`, `ios`, `lta` and `lpa`. Entry is scan-driven only: one pass per fresh sample batch. MI decides what it will enter and Still-Water suggests: with Still-Water loaded, only tickers in the latest batch's Indicator Forecast are entered, ranked by it. ([more](#multiindicator-details))

### Criteria

See StrategyBook's **Market Reading** section for what each criterion means and when to use it. This section covers tiering, recording, and fetch mechanics only.

**Slot builder badge key**: the manual slot builder uses the same emoji set as position/trade badges.

| Badge | Criterion |
|---|---|
| 🤑/💸 | Funding tier (direction-aware, see [Trivia](#trivia)). |
| 🔊 | V/A, volume versus the population sample-window average. |
| 🐂 | IO/L, the long share of the ticker's open interest versus the population sample-window average of that share. |
| 🐻 | IO/S, the same for the short share. |
| 🕐 | LTA, last completed hour's turnover versus the ticker's own average hour. |
| 💹 | LPA, last completed hour's price change versus every other ticker in the sample window. |

**IO/L and IO/S**: a ticker's long share of open interest is its open interest × the long share of accounts from Bybit's long/short ratio, and its short share is the remainder. The tier is `floor(100 × ln(share ÷ window average) ÷ step)`, so `iol+12` is 12 tiers more long open interest than the sampled population averages. Each needs the ticker's long share and a window average, so it has no tier until the sample window holds readings. ([more](#multiindicator-details))

**Recording**: every criterion is recorded as a signed tier on the position at entry.

### Config

| Setting | What it does |
|---|---|
| **Enabled** (`micEnabled`) | Master on/off. When off, the plugin opens no entries and runs no exits. |
| **Picks** (`micPicks`) | Max new entries per scan cycle (1–10). |
| **Share Cap** (`micShareCapEnabled`) | Limits plugin entries to a percentage of `maxPos`. Prevents MI from filling all position slots. |
| **Share Cap %** (`micShareCapPct`) | The cap percentage. At 50% with maxPos=6, MI can hold at most 3 positions. |
| **Tier Step Sizes** (`micFundStep`/`micVaStep`/`micIolStep`/`micIosStep`/`micLtaStep`/`micLpaStep`) | Read-only chips on the **Fetch** tab showing the tier step for each criterion. Defaults: `va` 1% deviation from the population average; `iol` and `ios` 1% (log) deviation of the long / short open-interest share from its window average; `lta` 10% deviation from the ticker's own hourly average; `lpa` 0.25 absolute points of 1h price change (shown as `pp`); `fund` 0.0025% of funding rate per tier, so 0.25% is tier 100. They can't be edited from the UI; change them via config import. Older installs saved the fund step as 0.25; it's migrated once, and saved `fund>N`/`fund<N` slot gates are rescaled ×100 so each keeps its threshold. |
| **Cascade** (`micCascadeEnabled`) | Closes every open position, whichever strategy opened it, when their collective unrealized profit reaches a threshold, banking a group move before it reverses. The position watcher checks this every 5s while the bot runs, not just once per scan, so a threshold crossed and reversed between scans is still caught. The closes are sent concurrently, not one after another. |
| **Cascade %** (`micCascadePct`) | Collective uPnL trigger as a % of base margin (minNotional ÷ leverage). While **Relative Target** is on the slider is hidden and unused: Cascade fires at the resolved entry TP. |
| **Sacrifice** (`micSacrificeEnabled`) | Closes every open position, whichever strategy opened it, when their collective unrealized loss reaches a threshold, capping group drawdown. It uses the same continuous position-watcher check as Cascade, and closes concurrently the same way. |
| **Sacrifice %** (`micSacrificePct`) | Collective uLoss trigger as a % of base margin (minNotional ÷ leverage). While **Relative Target** is on the slider is hidden and unused: Sacrifice fires at the resolved SL. |
| **Relative Target** (`micRelativeTargetEnabled`, default on) | Sub-toggle on the **Exit** tab, shown only while Cascade or Sacrifice is on. It sets each new position's entry TP and SL from what the market is actually paying: the LPA sample window's average move in the bot's favor × leverage is the entry TP, and the average move against it × leverage is the SL. **Cascade** is the entry TP and **Sacrifice** is the SL, so all four agree, and the **Targets Gauge** shows the live averages and resolved targets. ([more](#multiindicator-details)) |
| **Window** (`micRelBatches`, default **6**, 1–25) | Shown only while Relative Target is on. How many of the latest sample batches the average moves are taken from; older batches are ignored so stale readings don't dilute them. Within those batches each ticker counts once, by its latest reading. A short window reacts faster, so targets and deferment swing more from batch to batch; 25 is the most batches the sample history keeps. |
| **Min Entry TP** (`micMinEntryTp`, default **6**) | Shown only while Relative Target is on: the ROI % below which a position can't cover its entry and exit fees. If the resolved entry TP falls under it, the market isn't paying enough and new entries are deferred (at 6× leverage the window's average favorable 1h move must be at least 1%). Cascade and Sacrifice never fire below it, and the SL is floored at 1%. ([more](#multiindicator-details)) |
| **Targets Gauge** (no toggle) | Two-sided readout below the Entry/Exit/Fetch tab zones, visible whenever the plugin is enabled: SL and Sacrifice on the left, TP and Cascade on the right, with bars for TP and SL and text for the other two. Every value is green at or above Min Entry TP and red below it. The caption shows the window averages, and the gauge greys out with a note while Relative Target waits for 3+ readings on each side of zero. ([more](#multiindicator-details)) |
| **Substitution** (`micSubstitutionEnabled`) | When no entry slot is free (maxPos or Share Cap reached), closes the worst-scoring held position (any strategy's, not only MI's) and opens the best fresh candidate in its place, but only if the candidate's score beats the held position's *current* score by the **Substitution Margin**. Scores are Indicator Forecast scores in the bot's favor (see **Forecast Ranking**): a held MI position's current score (`_micLiveCompositeScore`) is the newest forecast on its ticker, else the score it opened on, so it's judged on where it stands now, not where it stood at entry. That latest score is recorded on the position. Each candidate is pre-flighted through the Force-Evaluate top-up before anything is closed. |
| **Substitution Margin** (`micSubstitutionMarginPct`) | How much better the new candidate must score than the worst held position, as a % of base margin (minNotional ÷ leverage), before a swap happens. Prevents swapping on marginal score differences. |
| **Substitution Min Age** (`micSubstitutionMinAgeMins`, default 60) | Minimum minutes a position must be held before it becomes eligible to be substituted out. |
| **Deferment** (no toggle) | An entry stop, only while Relative Target is on. It blocks every new entry while the resolved entry TP is under **Min Entry TP**, and needs only the LPA window. |
| **Re-entry Block Mode** (`micReentryBlockMode`) | Defaults to **Losers Only**, which lets a symbol that just closed in profit re-trigger immediately and blocks only a symbol that closed at a loss. **Winners + Losers** blocks a symbol from re-triggering for one bulk-ticker cooldown window (12h by default) after any close, win or loss. |
| **Auto Slots** (`micAutoSlots`) | Replaces the manual slot list with a minimum-gate qualifier: a ticker qualifies once it satisfies at least **Minimum Criteria per Slot** non-excluded criteria — not a fixed-size combination. Every criterion the ticker actually satisfies is captured and scored, not just enough to clear the floor. See `_micAutoQualify`. |
| **Minimum Criteria per Slot** (`micAutoSlotSize`) | The floor (1–6). At 1, a single true criterion qualifies the ticker — any others it happens to satisfy are still captured and scored. |
| **Exclude from Auto** (`micAutoSlotExclude`) | Criteria omitted from Auto's qualifying set entirely — never checked, never counted toward the minimum, never scored. Excluding more than `6 − Minimum Criteria per Slot` leaves Auto unable to ever reach its floor, and the plugin reports no active entry gate (`_micAutoActive`). |
| **Force-Evaluate General Criteria** (`micForceGeneralCriteria`, on by default) | Auto mode only. When on, just before a ticker opens, the plugin re-checks `fund`, `iol`/`ios` and `lta`/`lpa` with a forced per-symbol fetch, since the cycle's capped sample may not have reached it yet, and adds any that are newly true. It never drops a criterion already found, and costs a few extra requests per entry. ([more](#multiindicator-details)) |
| **Forecast Ranking** (no toggle, always on) | With Still-Water loaded, only tickers in the latest batch's Indicator Forecast are entered, ranked by its score in the bot's favor: Regime Caution's second score when that is on and the forecast has one, else the usual one. A negative score doesn't block an entry. A ticker the batch has no forecast for isn't a candidate. A following bot ranks on the leader's published forecasts for the batch (it waits up to 20 s for them). Without Still-Water, entries come from MI's criteria alone, unranked. ([more](#multiindicator-details)) |

### Slots UI

**Manual mode**: click a slot to select it, then toggle criteria on/off in the picker row below. ✕ deletes the slot; `+` adds a new empty one. All six criteria are tiered — clicking one opens its gate picker (direction plus tier) rather than toggling a bare tag. A slot with no criteria in it never matches.

**Auto mode**: replaces the manual builder with a minimum-slider and an exclusion chip row. A ticker qualifies on at least the chosen minimum of non-excluded criteria — every criterion actually true is scored, not just enough to clear the floor. The hint under the slider states the current floor as "qualifies on any N of M secondary criteria."

The six criteria are independent signed tiers, so any subset can be true for the same ticker at once and each contributes to the qualifying count on its own.

## Still-Water Plugin

Still-Water is one file for both bots. On PseudoChaser its panel is titled **Ashfall** (♨, orange) and on PseudoWinter **Permafrost** (❄, ice-blue); the code, settings (`sw*`) and storage layout are the same, and the side is read from the host at load. It provides the **Sample Scorer**, the **Indicator Forecast** that ranks each batch's tickers for MI's entries, and the **cross-bot bus** that shares cascade/sacrifice triggers with the partner. The panel has two tabs, **CROSS** and **SCORE**, with the Danger Zone (Export / Import / Clear Profile) below. ([more](#still-water-details))

### Config

| Setting | What it does |
|---|---|
| **Still-Water Mode** (`ashfallEnabled`, both sides) | Master toggle. |

### Extremity Scorer

Each criterion is a **dial family** (`fund`, `va`, `iol`, `ios`, `lta`, `lpa`) with a `+` and a `-` pole; each scan's readings build per-pole cutoffs that sort every reading as extreme or lukewarm. The side that has earned more becomes the favored side (ties default to extreme), and the chart and headline show it. Scorecards are per bot; see **Extremity Scorer Internals** in Trivia. ([more](#chart-and-scorer-display-details))

**Scorecard chart**: only the favored side's chart is shown (Extreme or Lukewarm) and it flips automatically when the favored side changes. Each criterion is a duo of bars, the `+` pole on the left and the `-` pole on the right, with profit above a zero line and loss below it. Only shown when MultiIndicator is loaded and enabled. ([more](#chart-and-scorer-display-details))

**CLEAR** wipes this bot's Sample Scoring store and Forecast Grader store (its Weight Profiles and Regime Caution's learning included) together (`__ew_sw_<side>_sampleobs_v1`/`…_fc_v1`) — cutoffs included, never the partner's. It also empties the graded-forecast history in IndexedDB (`__ew_sw_<side>_fcdb_v1`). The Indicator Forecast's candle cache (`__ew_sw_<side>_bg1h_v1`) is market data and survives it.

The chart is titled **Sample Scorer** and its bars are mean edge in pp, with liquidation outcomes blended in when Liquidation Surveillance is on. A status line above it shows the scored-sample count, plus the liquidation-sample count, tickers on watch and quiet graylist when Liquidation Surveillance is on, and the illiquid count when the Illiquidity Filter is on. With Liquidation Surveillance on, a further line shows the Event Size History's median, peak, bottom and event count. The LPA dial isn't drawn unless Liquidation Surveillance is on, since LPA is the price outcome. ([more](#chart-and-scorer-display-details))

**Headline & gauge**: the header number is relative: the favored side's favorable share of raw 1h move, so 50% is even. A gauge under it is scaled to the best share recorded, with **bottom** and **peak** marking the lowest and highest share (they update once the favored side has at least 10 raw samples). With Liquidation Surveillance on, the share is the 50/50 mix of the price and liquidation values. ([more](#chart-and-scorer-display-details))

The dollar mean and the share are always blended from the same figures, so they can never disagree in sign: each source (price, liquidation) is reduced to its mean favorable pp (P) and mean unfavorable pp (Q) per observation, the sources are mixed on P and Q, and the mean is P − Q while the share is (P − Q) / (P + Q). A share above 50% therefore always goes with a positive mean, and the colour follows both.

## Randomized Outcomes

Scan timing drifts independently per tab, and the sample is a fresh random draw of **Batch Size** candidates each cycle, so two identically configured instances won't share entry triggers, exit timing, or readings. This is intentional: instances in lockstep are easier to front-run and cluster losses at the same market event.

## Multiplex Plugins

To save resources in single-file browser execution, the system supports **Multiplex Plugins**. A standard plugin keeps its own telemetry isolated, while a multiplex plugin hooks into the combined component built when all plugins are loaded and reads the core data directly, without wrapping parent methods. This treats the master engine as a shared database, cutting resource use and avoiding race conditions between plugins. ([more](#general-details))

### The Speeder Module (Tentative Multiplex)

Located in `/plugins/multiplex/`, **Speeder** reuses functions in `MultiIndicator` and the data produced by `Still-Water`. That lets it read the rolling sample-cycle histories and the entry criteria builder directly.

* **What it does**: instead of judging order flow by fixed millisecond limits, Speeder splits the whole deduplicated pool of recent per-ticker trade intervals at the median on each scan.

* **How it does it**: to filter noise, landing in the fast or slow half isn't enough. A ticker's trade interval must also pass that half's own *mean*, which confirms a clear gap from baseline market speed.

* **When it acts**: like `MultiIndicator`, Speeder chooses its entry criteria (fast or slow) automatically, using a `base` setting tied to the liquidation regime. It can enter fast or slow tickers in hot or cold regimes.

* **When it doesn't**: if the plugins it depends on aren't in the combined component, Speeder logs a warning and stays inactive.

> **Note**: The Speeder strategy is tentative and lacks long-term historical validation; it remains isolated within the multiplex directory for demonstration purposes and architectural testing.

## Trivia

Developer-level detail with no operational consequence. Included for reference.

### General Details

The details left out of the shortened Main Config, Order Handling, Trades and Multiplex Plugins entries.

#### Limit orders and tries (Open / Close tabs)

Entries sell below / buy above the last price and closes buy above / sell below it.

#### Position Price Feed

Turning it on closes the WebSocket stream, and turning it off stops the REST calls. A saved Psycho config is switched off once on first load of PsychoChaser v1.9.1 / PsychoWinter v1.12.1; turn it back on if WS prices look wrong.

#### Follow Partner Bot

If the partner hasn't handed over a bulk ticker list (the corridor is empty between handovers, and a bot that has just reloaded has nothing until the partner's next publish), it reuses its own current list while that is within **Ticker Cooldown** plus 1.5 scan intervals of grace, so the partner's refresh at the cooldown boundary isn't beaten by a self-fetch, and otherwise fetches one bulk list itself rather than sitting idle with no tickers (for example right after a page reload). Everything else it fetches stays on the leader. The heartbeat is written once per completed scan cycle, and this bot steps back down as soon as the partner returns. The leader-held check runs at entry, before any instrument or price lookups.

#### Import (Actions dropdown)

The dropped keys cover both the bot and any installed plugin, and the cleanup also runs on every save, so retired settings don't linger.

#### Trade cards

**BAIL** closes every open position immediately on both bots. **Sub** marks a close that freed a slot for a higher-ranked candidate via MI Substitution, and **Eject** one made by MI Ejection, which needs two or more Deferment paths and so can't currently trigger. A reason with no registered label shows its raw name. On EverWinter/SunChaser, a bail sweep is followed by a direct exchange re-check.

The fees are `FEE_MAKER_PCT` 0.02% on entry and DCA fills and `FEE_TAKER_PCT` 0.055% on the close (the Bybit base-tier rates); live positions are skipped.

#### Plugin source storage

Plugin sources live in IndexedDB (`__ew_plugins_pseudowinter` / `__ew_plugins_pseudochaser`, object store `src`), are read once at boot and are held in memory. localStorage keeps a manifest entry per plugin, and the css and slot markup aren't stored at all because running the source rebuilds them.

An entry stays whole in the manifest until IndexedDB has returned its source identical on a later boot, so the manifest shrinks on the second load after a plugin file is loaded. A browser that doesn't persist IndexedDB for `file://` pages never loses a plugin; its entries just never shrink. If IndexedDB is unavailable, errors or doesn't answer within 4 s, the app starts anyway and plugin storage falls back to whole entries in localStorage. A manifest entry whose source is missing from IndexedDB is inactive, and the activity log says to re-load its plugin file. Removing a plugin deletes its source from IndexedDB.

Once IndexedDB has returned a source on any boot, loading or updating a plugin writes the source to IndexedDB first and stores only the slim manifest entry, so a full localStorage can't block it.

#### Plugin data storage

What Ashfall and Permafrost keep from Bybit and the scores built from it lives in the host's IndexedDB data store (`__ew_data_pseudowinter` / `__ew_data_pseudochaser`, object store `kv`, same key names as before), not in localStorage. The store is read into memory at boot, so plugins still read and write synchronously, and writes reach IndexedDB in batches. A key an older version left in localStorage moves on first read and is deleted once IndexedDB confirms the write. If IndexedDB is unavailable, fails or doesn't answer within 6 s, the store passes through to localStorage as before. Bucket pruning is unchanged. Needs PseudoWinter 1.25.0 / PseudoChaser 1.21.0; an older host keeps everything in localStorage.

Alpine loads only after the plugin sources have been read and applied (`window.__pluginReady`), which adds a few milliseconds to startup.

### MultiIndicator Details

The details left out of the shortened MultiIndicator entries.

#### Slots

Every criterion in a slot must be true for a ticker to qualify.

#### IO/L and IO/S

`ios-3` is 3 tiers less short than the sampled population averages. The long share is read by the sample batch, with one fresh read before entry when a candidate has none.

#### Relative Target

It replaced Target Halving, and a saved Target Halving on/off choice carries over once. On Chaser the favorable average is the up move (TP) and the adverse one the down move (SL); on Winter it is mirrored. Price move % × leverage is the ROI % the host's TP and SL use, so with a +2.5% average up move at 6× leverage Chaser's TP is 15%. While it's on, the Cascade/Sacrifice sliders are hidden and unused, and the gauge also shows the batch and ticker counts behind the averages. It also drives Deferment. It needs no Sample Scoring, only the LPA window: with fewer than 3 readings on either side of zero in the window, the configured values apply and Deferment is off.

#### Min Entry TP

Cascade is the same number as the resolved entry TP. Cascade and Sacrifice also never fire below 1%, and the SL has no deferral of its own.

#### Targets Gauge

TP and SL each get a bar from the centre axis, with a tick on the TP bar at Min Entry TP; Cascade and Sacrifice are text only, since they never fire below the floor. TP and SL are judged on the resolved value; Cascade and Sacrifice are judged on the resolved value *before* the floor lifts it, while their text shows the value that actually fires, so they read red while the floor is holding them up. A disabled Cascade or Sacrifice reads `off`.

The caption's window averages are up/down, leverage, batches and tickers, and it adds `TP under the N% floor: deferring` when the floor path is on. With Relative Target off the gauge shows the configured values (entry TP is the host's TP, SL the host's `binarySlPct`).

#### Force-Evaluate General Criteria

The function is `_micTopUpGeneralCriteria`. On a following bot this is the one exception to the no-own-fetch rule: it uses the leader's shared OC cache first and fetches the single symbol only if that has nothing.

#### Forecast Ranking

The score is Still-Water's Indicator Forecast for the ticker, in the bot's favor: `er` (Regime Caution's second score) when that layer is on and the forecast carries one, else `e`. Higher ranks first. Only tickers the latest batch started a forecast on are candidates, so a ticker outside it is neither ranked nor entered, and a negative score is not skipped. The leader publishes a batch's forecasts once, with their final scores, after the slow readings land, and a follower waits up to 20 s for that publish before it ranks. If none arrive the scan finds no candidates.

Without Still-Water, MI enters any ticker matching its criteria, with no forecast ranking.

### Still-Water Details

The details left out of the shortened Still-Water entries.

#### Still-Water overview

Still-Water's panel has two tabs: **CROSS** (the partner feed and last share) and **SCORE** (the scorer, forecasts and settings).

#### Sample Scoring

Criteria are read at sample time and paired with the last completed hour's price move, less the rolling LPA average, which makes it a same-moment correlation. LPA is never scored as a criterion on price observations, and its dial stays hidden from the **Sample Scorer** unless Liquidation Surveillance is on. Extreme Split and Min Samples set its cutoffs; the panel title carries a scored-sample count. It forces the hour-candle fetch on, since LPA is its outcome.

#### Score Horizon

It lives in the Score tab's settings dropdown. It's applied when the scorecard is built (scores move as batches age out) and when the store is saved. A short horizon leaves liquidation-fed poles thin (LPA especially). The Forecast Grader's graded store has its own size setting.

#### Sample Batch

The ticker request carries the 24h turnover, open interest and funding that `va`/`iol`/`ios`/`fund` compare against. The merged candle is what `lta`/`lpa` read, and the candles are kept for the batch so the Forecast Grader can read the last ~10 minutes. The long/short ratio is the long share that `iol`/`ios` split open interest by (one more request per ticker). Each fetch is an independent snapshot, and the only recent-trade fetch is the opt-in Illiquidity Filter's, one per ticker per refresh window. A follower also seeds its cycle history from that sample.

#### Liquidation Surveillance

**What's watched**: the sample batch itself, less the slots the Forecast Grader's revisits take (**Batch Size**, or the batch the grader names when Forecast Focus is on, in which case the watch opens on exactly that list; there's no separate watch size). Revisit tickers are taken out of the pool before this runs, so the watch never sees them and Liquidation Surveillance only fills the remainder. The feed is open only while the toggle is on and the bot isn't following.

**Each scan**: the tickers that stay are ordered by most liquidated turnover first. A ticker with none is graylisted immediately and replaced by a fresh random one. The batch is always filled to Batch Size: graylisted tickers are only drawn back in, oldest first, when there aren't enough others, and they leave the graylist when they are. This quiet graylist is for sampling only, so a quiet ticker stays an entry candidate (the Instability Graylist is the one that blocks entries).

**Scoring**: at the end of each watch the batch is re-fetched as usual, and the observation's criteria come from that fresh reading. An event is the ticker's net liquidated turnover (liquidated shorts minus liquidated longs, as a dollar size). Its pp is its side times the window's typical move (the median distance of the latest 1h price changes from their average) times its size against the median event in the Event Size History, capped at the history's peak (so at most peak ÷ median). Liquidated shorts are good for Chaser and liquidated longs for Winter. Every liquidation observation counts 1:1 with a price observation, with no turnover weight.

**Event Size History** (`swLiqHistHrs`, default 24 hours, 1–168, never shorter than the Score Horizon): one entry per liquidation event, its time and net liquidated dollars, kept in the Sample Scoring store (`lqh`, up to 5000 entries, aged out at the setting) and saved, exported, imported and cleared with it. The yardstick for a watch is the stored history plus that watch's own events, so it works from the first event: a lone event reads as exactly one typical move. A median-sized event reads one typical move, a smaller one less, a bigger one more, up to the biggest on record (peak ÷ median). Because liquidation sizes are heavy-tailed, that biggest event can read many times the typical move and carry its pole until it ages out. An event with exactly offsetting short and long liquidations reads 0 pp and stays out of the history. Events join the history even when their ticker could not be tagged.

**Reservation (Forecast Grader)**: a ticker that just had a liquidation event is reserved for a forecast of its own, so the event is still fresh when that forecast is graded. Each event in the chart history younger than the **Liquidation dropoff** reserves its ticker; a forecast started on it releases the reservation (a later event reserves it again) and is marked `bg._rv = 1`. A reserved ticker starts first among a batch's candidates, newest event first. One that already has a forecast in flight waits (a ticker is never queued twice) and, once free, is pulled into the next batch by the batch planner beside the revisits, at most half the revisit share, skipping illiquid and stablecoin tickers and any outside the pool. Reservations expire at the dropoff. It runs whenever the Forecast Grader and Liquidation Surveillance do and has no setting of its own. Reserved starts jump the random draw, so those forecasts are a liquidation-biased sample rather than a uniform one (the Export marks them).

**Blending**: a pole's score is the mean of its price edge and its liquidation edge once each has Min Samples (whichever has them stands alone; with neither, the pooled mean once the two together reach it). The favored-side comparison and the headline are mixed the same way, so the gauge reads the mix. Liquidation samples count toward a pole's sample total and extreme cutoff, and LPA is scored on liquidation outcomes while the toggle is on, so its dial reappears.

**Display**: the Liq view's ticker pills list only tickers that had liquidation events.

**Good to know**: liquidation events are irregular, so these samples accrue slowly and a score built on them is slow to move, especially on a rare pole. The watch survives a reload: its tally is saved as events arrive and the next scan after a restart scores it (events missed while the page was closed are absent and counted as the watch's blind time, and a watch older than 12 h is dropped). Only the leader watches; a follower adopts the leader's liquidation observations with the rest of the scored store, and its Liq view fills in from the lean the leader publishes for each watch, and its event-size line shows the summary the leader publishes. Turning it off ignores the stored liquidation observations (they're kept) and closes the feed.

#### Instability Graylist

Each ticker's liquidated-short and liquidated-long turnover are kept per watch and summed over the retained sample window; in the score 0% is one-sided and 100% is evenly mixed, and a ticker that flips between short-heavy and long-heavy watches compounds into instability too. The threshold is relative to the average, so a market where everything is mixed doesn't graylist everything. The ticker stays in the watch so its record keeps updating, leaves the list once its mixed watches age out of the window, and the list works on a follower too, since the split rides on the adopted history.

#### Illiquidity Filter

Each sample batch measures only the tickers it carries, with one recent-trade fetch each; a ticker's speed is the average gap between the times of the 3 trades, and **Measure again after** is in days. An illiquid ticker is dropped from that batch before its hour candle is fetched, and while its reading is live it's also left out of the scan pool. When the reading expires the ticker is allowed back, and the next batch it appears in measures it again, so slow tickers are rechecked on the same cycle and can recover. Coverage builds gradually: a ticker with no reading passes until a batch measures it. The leader measures and publishes the readings, and a follower makes no fetch.

The sample scorer status line and the setting's own hint show `N illiquid (>12s) · M measured · slowest Xs`.

#### Stablecoin Filter

The range is of the completed candle's open, high, low, close and the current price. Under the limit, the ticker is dropped from that batch (no result), counted in `excluded.gray`, and measured again the next batch it appears in after the verdict expires. The count graylisted shows under the setting. The leader judges and publishes the verdicts.

#### Forecast Grader

It runs with Sample Scoring (both always on). The scorecard pairs a ticker's readings with the 1h move that had already happened when it was sampled, so nothing else tests it forward. The graded forecasts change no headline either, and the forecasts' scores are what rank MultiIndicator's entry candidates (see **Indicator Forecast**).

**No extra fetches**: a forecast ticker simply appears in two ordinary sample batches, **Lead** batches apart. (With **Forecast Focus** on the grader names the batch itself, see below, but each forecast still comes back as an ordinary sample fetch.)

**Forecast (first appearance)**: from the fresh fund, V/A, IO/L, IO/S and LTA readings of that fetch, the scorecard as it stands scores the ticker: the mean score of the poles it lands in (each read from the Extreme or Lukewarm bucket its own tier falls in; poles without Min Samples are skipped, a ticker with none scored isn't forecast). That number is pp against the field in the bot's favor. It is frozen with the typical price of the ticker's last ~10 minutes from the same fetch (no price enters the projection). With **Range Fit** on, the number is first laid onto the range its own ticker (and the tickers that track it closest) has shown, and the raw score is kept beside it. With the **Indicator Forecast** on, the order the batch is laid onto the range in comes from the indicator rank instead (see below), and the scorecard's own number is kept as `projections.sc`. New forecasts come only from the fresh half of a batch, never from a revisit, and at most the revisit share of the batch size, so starts and revisits balance.

**Revisit (second appearance)**: before each batch is built, MI ask the grader for the forecasts falling due (oldest first) and give them up to **Revisits %** of the batch's slots (5–90). Liquidation Surveillance then fills only the remaining slots, from a pool without the revisit tickers. The revisit is an ordinary sample fetch, so it also feeds the scorecard as usual. A ticker that is illiquid now, or missing from the batch, is retried for two more batches and then voided. With Forecast Focus on, the revisit cap is the **Tickers per batch** count instead of **Revisits %** (see **Forecast Focus** below).

**Start log**: every batch's start is logged (the last 120 batches, `startLog` in the Summary export): tickers in the batch, how many were excluded (taken by a revisit, already pending, no price, nothing scorable), the candidates left, the room (`min(share slots, share slots × (lead + 3) − pending)`), how many started, how many of those were reserved and, with Forecast Focus on, how many were retries (`retries`). A batch that starts fewer forecasts than its room ran out of candidates, and the exclusions say where they went; a graded cohort can still shrink later through voids (`gone`, `late`, `thin`).

**Actual**: the price move runs from the frozen price to the revisit's **typical price** over its last ~10 minutes ((highest high + lowest low + last close) / 3 of the two newest 5-minute candles; the hour candle's typical price, then the last price, when the ticker traded nothing that recently), read in the bot's favor. The raw move is kept and the Export grades it too (`windowRaw`). The highest and lowest point since the forecast, from the 5-minute candles, are kept as well. A start batch with fewer than 3 gradable forecasts is voided.

**Timing**: due is a batch **number** (a persisted counter), not a timer, so a plugin reload doesn't misalign it. Each forecast keeps its real elapsed time, and one that sat past 1.5× the expected lead (a gap or downtime) is voided, not graded. The expected step is the median gap of the latest retained batches (the configured scan interval until there are enough).

**Grade**: direction right = 50 + 50 × size match, wrong = 50 × (1 − size match), 50 when either side is flat (size match = the smaller over the larger of |projected| and |actual|). A batch or the window is the mean of its forecasts' accuracies (total points over tickers × 100), and **influence** is each criterion family's share (Fund, V/A, IO/L, IO/S, LTA) of the projections' total absolute contribution (computed and exported, not shown in the hint or chart summary). The Export also holds, over the window of graded forecasts, **rank corr** (Spearman between projection and actual: +1 the scores called the order, 0 no information, negative backwards), **hit** (share with the projected sign right) against **base** (what always calling one side would have scored on the same actuals), **top-bottom fifth** (mean actual of the top fifth by projection minus the bottom fifth, in pp, from 20 graded) and **slope** (actual per unit of projection: 1 is calibrated, 0 is no information). Fewer than 5 graded reads as too few. Per forecast the Export also logs the path since the forecast, a wide snapshot of the readings at forecast time, the market context of each start batch (averages plus the spread, skew and extremes of the hour changes) and the alternative projections, and `projectionTest` grades each projection form (fitted, raw, sum of the poles, strongest pole, the scorecard's own score) on the same actuals.

**Sign convention**: every pp number the Grader shows or exports (projected, raw projected, actual, contribution, alternative projections) is in the bot's favor, so one sign always means one price direction: on Ashfall + is price up and − is price down, on Permafrost + is price down and − is price up. The `%` fields (raw move, move relative to the start batch, batch mean move, highest and lowest point) are plain price moves, + is price up on both.

**Settings**: **Lead** ranges 2–24 batches and **Graded forecasts kept** 60–6000 (default 3000). Unique tickers per batch fall by the revisit share (the scorecard still receives every ticker in the batch); with Forecast Focus on the grader names the batch instead (see below).

**Readout**: the hint under the toggle shows pending and graded counts, the window accuracy and the Range Fit state (tickers with past moves stored, forecasts fitted, and the fit's weight when the bot has backed it off). The Fcst chart view's summary lines the window and the selected batch, each with its net profit line.

**Net profit**: the Fcst view adds a **Batch net profit** and a **Window net profit** line, an estimate of what entering the forecasts' best picks would have returned. Per graded start batch the forecasts are ranked by projected pp in the bot's favor and the top N are taken, N being the host bot's Max Concurrent Positions (3 if it has none), and only forecasts projected in the bot's favor are entered. Each pick is one base-notional position (`minNotional`) at the host's leverage with the host's TP and SL, which are ROI on margin, so the price move is the ROI ÷ leverage: binary mode's TP and SL (`binaryTpPct`, `binarySlPct`), otherwise the entry TP and the DCA SL (`entryTpRoi`, `dcaSlPct`). The price path recorded at grading (the highest and lowest point since the forecast) decides the exit: the stop when the adverse move reaches the SL, or the liquidation price if that is nearer (100 ÷ leverage less a 0.5% maintenance margin; a liquidation loses the whole margin); the TP when the favorable move reaches it, for notional × the TP move; otherwise the pick is held to grading (about an hour at the default lead of 6 batches) and earns notional × its recorded raw move in the bot's favor ÷ 100. When one path touched both the TP and the SL the order is unknown, so the stop is assumed first. Forecasts graded before the path was recorded fall back to their end move alone. The simulation stays in the background and the readouts show dollars only: the batch line the selected (else latest) batch's sum; the window line the total over every graded batch in the store and how many batches were in profit. A batch with no forecast projected in the bot's favor reads that way and is left out of the window. Forecasts without a recorded raw move are skipped. It is still a simple estimate from stored data (one entry and one SL, so DCA adds are not simulated; no fees, funding or slippage) and changes no score or entry.

**Storage and sharing**: stored direction-neutral (price direction; the bot's favor is applied when read), so a following bot of the other direction adopts the leader's store as it is. **CLEAR** wipes it with the sample stores, its parts export on their own, and the Profile export carries its raw store, which Import restores. The graded forecasts live in IndexedDB (`__ew_sw_<side>_fcdb_v1`, object store `done`, one record per forecast keyed `startBatch|symbol`); localStorage keeps the pending queue, the counters and a short tail of graded rows: the newest 600 until IndexedDB has returned rows on a later boot (proof it persists in this browser), then the newest 120. Without IndexedDB, or if it hangs or fails, everything runs from localStorage as before. A following bot reads the leader's copy and leaves its own IndexedDB alone.

#### Forecast Focus

A sub-toggle under the Forecast Grader, **on by default**. Some tickers may need a different set of weights for the indicators and forecast tools, and a ticker's own history is too thin to learn that from (most tickers appear once or twice among the graded forecasts), so Forecast Focus keeps forecasting the tickers the scorer reads worst and lets what differs between their misses and their hits be compared in the Export. On its own it is observation only: it changes no score, forecast or entry. Weight Profiles (below) is the part that acts on what the retries show.

**The batch is the grader's.** With Focus on, the grader names every ticker of the sample batch and the host fetches only those, so Liquidation Surveillance, the hour candles, the readings and the scan's ranking all work from the same list. The batch is **Tickers per batch** (default 50, 5–50) in all, in this order: the due revisits first (up to that number), liquidation reservations (up to half of what is left), then either a retry cohort (once the pool fills the rest of the batch) or fresh tickers drawn at random from the pool, skipping tickers with a forecast in flight or in the retry pool and illiquid or stablecoin ones. New forecasts therefore take the slots the revisits leave, and every planned ticker that comes back usable starts a forecast; a batch can still come up a little short when a ticker turns out unusable (no price, nothing scorable), or when the pool itself runs out (see below). The liquidation watch opens on that same list, and **Revisits %** is not used while Focus is on. The per-forecast background readings (1-hour candles, open interest, funding trend) scale with the forecasts started.

**Retry pool**. A graded forecast under **51%** accuracy puts its ticker in the pool. It stays until one of its grades reaches **70%** (the Grader's pass line), whatever it scores in between: only the latest grade counts, and there is no cap on attempts. Pooled tickers are held out of fresh batches. When the eligible pool (no forecast in flight, not illiquid or stablecoin) is at least what the batch has left for new forecasts (after the revisits and the liquidation reservations), that many start as one cohort, longest waiting first, so a retry cohort is always a whole batch and a big pool rotates instead of re-forecasting the latest failures. Below that size the batch is all fresh tickers and the pool keeps waiting. A forecast that voids leaves its ticker pooled, an illiquid or stablecoin ticker waits, and one idle in the pool for 14 days (delisted, gone) is dropped.

**Short batches are filled.** The fresh draw skips every ticker with a forecast in flight or waiting in the retry pool, and with the Lead window full that can be most of the pool, which used to leave batches made of revisits and retries alone. When the planned batch is under **Tickers per batch**, it is filled with tickers that already have a forecast in flight or wait in the retry pool (illiquid and stablecoin ones are still skipped). These are fetched for every sampler, but no second forecast starts on them (they show as `pending` in the start log).

**Export.** Grades and Pending rows carry `attempt` (1 = a first forecast on the ticker, 2 or later = a retry). The Summary's `retryQueue` holds the queue (attempts, latest accuracy, first miss and last graded time, worst first, up to 400), how many tickers have passed and a log of the last 200 passes with their attempt counts; `startLog` gains `retries` per batch, and the settings carry the Focus values. Retry forecasts appear in Readings like any other (join on symbol + startBatch). With Weight Profiles on, the queue rows also carry the ticker's `profile`.

#### Weight Profiles

A sub-toggle under Forecast Focus (`swFcProf`, **on by default**, needs Focus on). One set of weights does not suit every ticker, and what separates the tickers it suits from the ones it does not cannot be told ahead of time. So a forecast that fails gets a **profile**, its ticker is retried on weights that differ from the general ones until a grade reaches 70%, and the weights that worked go to every later ticker that matches the profile. Unlike Forecast Focus on its own, this changes the live forecast: trial and proven weights shape the projection of the forecasts they start on.

**The profile.** A ticker's fingerprint is its readings ranked inside its start batch (-0.5 to 0.5, so it does not depend on the market): 24h turnover (`vol`), open interest (`oi`), funding (`fr`), spread (`spr`), last-hour range (`rng60`), position in the 24h range (`pos24`) and turnover against its own average (`lta`); at least four must be present. A profile is a centre in that space plus its weights and history. A ticker matches the nearest profile whose distance (the root-mean-square difference over the readings both have) is within **Profile match distance** (default 25%; two random tickers sit about 41% apart). A ticker that fails (under 51%) and matches nothing opens a new profile centred on it; at 60 profiles the nearest one takes it instead, so profiles merge rather than multiply. The match is made again at every forecast start, so a ticker whose readings have changed can move to another profile, and each graded member nudges its profile's centre toward itself (by 1 / (members + 1), at least 1/20).

**The weights.** Eight values. `fund`, `va`, `iol`, `ios` and `lta` multiply that scorecard family's contribution to the projection (1 = general; from -1 to 2, so a family can be silenced or reversed). `ind` is the Indicator Forecast's blend (0-1), `div` the weight of the candle-divination readings among the indicator readings (0-2), and `rng` the Range Fit blend (0-1). `ind` and `div` only count while the Indicator Forecast and Candle Divination are on, `rng` while Range Fit is on; a weight that does not apply stays at its general value. The general weights are 1 for the families and `div`, the Indicator Forecast's blend setting for `ind`, and the bot-managed blend for `rng`.

**Life of a profile.**

- **Learning.** A failed forecast gives its ticker a profile and queues it. When the ticker is next forecast it starts on the profile's current **trial**: random steps from the best trial so far (from the general weights while there is none), narrowing as trials accumulate (0.7 x 0.93 per trial, floor 0.2; the blends take 0.6 of that step), always at least 0.25 away from the general weights and not within 0.12 of a weight set that already failed. Every ticker queued on the profile uses the same trial until one of them is graded, then the next retry draws a new one.
- **Proven.** A trial graded at 70% or better becomes the profile's proven weights, with the grade that proved them.
- **In use.** Any forecast whose ticker matches a proven profile starts on its weights, queued or not. Grades on them count as passes (70%+) or failures (under 51%) in the profile's record.
- **Starting again.** A forecast on proven weights that grades under 51% sends the profile back to learning: those weights go into `failedProvenWeights` (and are avoided from then on), the trials start over from the general weights, and `restarts` counts it.

Tickers that match a profile still in learning and are not queued run on the general weights, so they are the control. As with the retry queue, a single grade decides, and a grade is a noisy measure; a profile's passes and failures on its proven weights in the Export show how they hold up afterwards.

**Where the weights act.** The family multipliers rescale the scorecard projection before anything else (the unscaled score stays in `projections.sc` and is graded as `projectionTest.scorecard`). `ind` replaces the Indicator Forecast's blend for that forecast, `div` scales the divination readings inside the indicator direction average, and `rng` replaces the Range Fit blend for that forecast. Accuracy is graded on the final projection as before.

**Export.** Grades and Pending rows carry `profile`, `weightSet` (general / trial / proven), `weights` (the set the forecast started on) and `traitRanks`. The Summary's `weightProfiles` holds the settings, the general weights, the counts, and per profile its status, members, recent tickers, centre, proven weights and accuracy, passes and failures on them, restarts, trials (this round and in all), best trial accuracy, current trial, failed proven weights and created / updated times. Profiles are saved with the Forecast Grader store (so they ride in the Profile export and import, a following bot adopts them, and CLEAR wipes them), and the Forecast Grader's hint line shows how many there are and how many are proven.

#### Range Fit

It targets **flattening**: scores average out toward zero, so projections come out far smaller than what the market actually pays and the accuracy's size match collapses. Each ticker is laid onto its own range.

**What's stored** (`__ew_sw_<side>_pm_v1`, see Trivia): one return per ticker per completed 1-hour candle, taken from the candles the Indicator Forecast already fetches, so it costs no request. A ticker first seen holds the 100 candles fetched for it (99 hourly returns) and grows an hour at a time while it keeps being sampled, up to **Past moves kept** (48–720 hours, default 168). It is market data, not forecast data: the scorecard CLEAR leaves it and **Clear past moves** empties it.

**Fitting**: moves are read market-relative, the hour's median change across the stored tickers taken off (the way grades read selection). A ticker needs 12 hours of them; one with fewer keeps its raw projection and is counted as short of history. Its range is its own moves pooled with those of the tickers that track it closest: the correlation of their market-relative hourly moves over at least 24 shared hours, the best **Correlated tickers pooled** (default 8) at or above **Minimum correlation** (default 0.4). Each peer's moves are scaled to the ticker's own spread (0.25–4×) and weighted by correlation squared, and **Own history share** (default 50%) of the range's weight stays with the ticker's own moves (all of it when no peer qualifies). Hourly moves are scaled to the forecast horizon (Lead × the scan step) by the square root of time. The batch is then ranked by score and each ticker takes the quantile of its own range at its rank: the best-scored sits at the top of what that ticker has shown it can do, the worst at the bottom, and tied scores share a rank. The raw projection's field is `rawProjectedPp`, and `projectionTest.raw` grades it on the same actuals, so the fit can be judged against it. The influence shares stay those of the raw score.

**Weight**: how much of the fit is used is the bot's own call, so there is no setting for it. Each forecast also keeps the full fit (`ef`). On the graded window the Indicator Forecast tests its readings on, the bot replays every forecast with both values recorded at fit weights of 100%, 75%, 50%, 25% and 0% and takes the weight with the best accuracy; a lower weight has to beat the one above it by more than 0.1 points, and under 6 graded batches the fit stands in full. It is re-tested with every graded batch and keeps being tested at 0%, because the test grades the full fit whatever weight was used. The hint under the toggle shows the weight once it is below 100%, and the Export's `rangeFit.weight` holds the weight, the accuracy at each and the reason.

#### Indicator Forecast

The forecast the grader runs on. The wide readings listed below are its data feed.

**What it does**: each new batch's forecasts are ranked by an equal-weight rank average (no fitted weights, so nothing to overfit) of the readings picked from the graded window (see below). Each picked reading is ranked within the batch, reversal readings counted upside down (centred, −0.5 to 0.5, ties sharing a rank), a ticker's score is the mean over the readings it has (at least 2, else it keeps the scorecard's number), and high = price up next. The score is blended into the forecast as `(1 − w) × scorecard + w × 2 × score × S` with `w` = **Indicator direction** and `S` the batch's mean absolute scorecard score (floor 0.05), then Range Fit lays the batch onto the expected range as before. Size comes from a **size index**: the geometric mean of the ticker's 60-minute range, Garman-Klass volatility (`gk60`) and 1-hour ATR (`atr14`), each against the batch median and clamped to 0.25–4×. The free readings exist when the forecast is filed and the 1-hour and open-interest ones a few seconds later, so the batch is scored once with the first and again when the rest has landed; it always starts again from the scorecard's own score.

**Which readings drive direction**: the set is re-picked whenever a batch has graded, from the graded forecasts of the last **Indicator test window** hours (default 4; at least 6 batches of 8 or more). Every logged reading is ranked within its batch against the move relative to the batch mean (so the market's drift is out of it) and gets its mean per-batch rank correlation over the window and over each half of it. A reading is used the way its own sign shows (a reversal reading counts upside down) and is **kept only if** (1) its sign is the same in both halves of the window, (2) its correlation is at least 0.02 in size, and (3) adding it does not pull the ensemble's rank correlation down (strongest first; a reading with the same values as one already considered is skipped, and so is one seen on under 15% of the window's forecasts). Nothing picked, or fewer than 6 graded batches, leaves the scorecard's own score standing. Size is not picked this way: it stays the volatility index. The Export's `directionTest` lists every reading's correlation (window, first half, second half), whether it is in and why not. Limits: about 4 hours with horizons overlapping 6 batches is only 4 or 5 independent windows, so some noise readings will be picked and drop out again as the window moves, and the picked ensemble's correlation on the window it was picked from is inflated.

**What it logs**: `bg._dc` (the direction score, price direction; the Export's `indDirScore` is it in the bot's favor), `bg._vi` (the size index; `sizeIndex`) and `ep.sc` (the scorecard's own score; `projections.sc`). `projectionTest.scorecard` grades that score on the same actuals as the forecast, and `rawProjectedPp` is now the score before the range fit with the indicator blend in it.

**Liquidation readings**: `lqa` (the lean of the age-weighted liquidated turnover, −1 to +1 with liquidated shorts +, price direction) and `lqt` (log10 of that weighted turnover) are built when a forecast is filed from every liquidation sample in the chart history older than the forecast (nothing from its own future), each weighted 1 when fresh down to 0 at the **Liquidation dropoff** (linear), and blank when the ticker had none. The chart history holds 25 cycles (about 4 hours), so a dropoff beyond that changes nothing. They are ordinary candidates in the selection above and enter direction only if they hold up; the lean saturates on one-sided events, so `lqt` carries the size.

**Readings logged with each new forecast** (stored on it as `bg`): *free, from data already fetched*: top-of-book imbalance (`tob`), price against the 24h VWAP (`vwd`), the 24h range (`rng24`) and the squeeze (`sq`: the 60-minute range over it), the funding interval (`fih`), time of day (`todS`/`todC`); from the 5-minute candles, close-location-weighted volume over 1h and 2h (`clv60`/`clv120`), Garman-Klass volatility (`gk60`), upper and lower wick shares (`wku`/`wkd`), drawdown from the 1h high (`dd1h`) and the skew of the 5-minute returns (`rsk`). *1-hour candles* (one kline request per ticker, then only the completed hours not held yet): Wilder RSI 6/12/24 (`rsi6`/`rsi12`/`rsi24`), StochRSI K on RSI 12 (`stk12`: a 14-value stochastic smoothed over 3), ATR(14) in % (`atr14`), Bollinger (20, 2) %B and bandwidth (`bbp`/`bbw`), distance from the EMA(20) (`ema20`), 24h and 72h return (`rt24`/`rt72`), distance from the 72h high and low (`d72h`/`d72l`) and a volatility regime (`vreg`: the last 24 hours' spread of hourly returns over everything held). *Open interest* (15-minute history, 17 rows): its change over 15 minutes, 1 and 4 hours (`oi15`/`oi1h`/`oi4h`). *Funding* (last 6 settlements, refetched only after the next one is due): last rate, mean and slope in basis points per settlement, and the interval (`fhl`/`fhm`/`fhs`/`fhi`). Taker flow and the full order book are deliberately not fetched: recent-trade pages cost 20–100× the rest and cover seconds on a major but hours on a dead alt, and a book snapshot decays within seconds against a 1-hour horizon. The candle flow readings and the top-of-book imbalance stand in for them.

**Fetching**: the slow readings are fetched right after a batch's forecasts are filed, three tickers at a time through the shared queue (the scan never waits on it); when they have landed the batch is scored again with all of them.

**What the Export shows** (`featureIC`, and the readings on each forecast): per reading, its mean per-batch rank correlation with the move (in the bot's favor) and with its size, t over batches, and its family (mom: RSI and StochRSI; vol; pos; ret; oi; fund; flow; ctx). With about 45 readings a few will clear t > 2 by chance, and the t overstates the evidence: batches start one scan apart but grade **Lead** batches later, so neighbouring batches share most of their move (the t is inflated by roughly the square root of Lead, about 2.4× at the default 6). Judge a reading by its sign across the thirds of the window and by whether it follows the batch's mean move, and replicate on a later export before trusting it.

**Liquidation diagnostics**: the liquidation watch opens when a forecast starts, so what it sees is the 10 minutes **after** the start, which makes it a diagnostic and never a model input (the model's own liquidation readings, `lqa` / `lqt`, are built from earlier cycles). Each such forecast gets `x_lqw` (1 watched; 0 no reading, set when the forecast is graded), `x_lqu`/`x_lqd` (liquidated short/long turnover), `x_lql` (lean in pp), `x_lqs` (seconds the watch really listened) and `x_lqg` (seconds it was blind, because the page was closed or the feed dropped). A window made from two folded watches reports nothing.

**Cost and storage**: about 3 extra requests per new forecast on first sight of a ticker (100 hourly candles ≈ 8 KB, open interest ≈ 1 KB, funding ≈ 0.6 KB), then mostly only the new hours; the free readings cost nothing. The candle windows also hold each hour's volume (about 0.4 KB per ticker) for Candle Divination. The candle windows persist across reloads in their own key (`__ew_sw_<side>_bg1h_v1`, see Trivia), and each completed hour also files one return per ticker into Range Fit's past-moves store (`__ew_sw_<side>_pm_v1`) at no request of its own; the open-interest and funding caches are memory-only. The readings are numbers on the forecast records, about half a kilobyte each, and live in IndexedDB with the graded forecasts (about 230 KB per 600 forecasts in the Export's compact Readings part). Without IndexedDB, if localStorage fills, the older half loses its readings and the save retries once. A readings run in flight is saved when the page is hidden or closed.

#### Candle Divination

A sub-toggle under Indicator Forecast that learns candle shapes from the 1-hour candles the forecast already keeps and reads each ticker's latest shape as a forecast reading. It makes no requests of its own.

**Shape**: six completed hours. Per hour, the body, upper wick and lower wick (the open is taken as the previous close), each divided by the ticker's own average hourly range over its last 24 hours (so a major and a small coin compare), clamped to ±4 and weighted from 0.6 (oldest hour) to 1 (newest): 18 numbers. The **volume** version adds six more: each hour's volume against the ticker's 24-hour median (log, clamped to ±3, same weights); it exists only when all 24 hours have volume. A slice needs 24 candles behind it for its scale, so a ticker holding 100 candles gives about 75 pairs (a slice and what followed it).

**Two libraries, learned prototypes**: price shape alone (reading `dvp`) and price + volume (reading `dvv`, behind its own switch). Each library is a set of **shapes** (prototypes): a centre, a match count, the mean move of the next hour (in units of the ticker's own average hourly range, + = price up), the share of next hours that rose, and the mean 6-hour path that followed with its count. A library starts empty and collects pairs; at 1,000 it is clustered (k-means with a k-means++ start, 12 rounds, at most one shape per 16 pairs, up to **Shapes in library**, default 64) and every pair gives its nearest shape its outcome. Afterwards every newly completed hour of a fetched ticker is one pair, learned once (the last hour learned is kept per ticker): it nudges its nearest shape's centre and averages (running means, rate 1 / min(count, 400)). At load the candle cache already in memory feeds a random sample of up to 4,000 pairs, so the price library is built at once with no fetch; the volume library fills as hours with volume accumulate. Changing **Shapes in library** applies on **Rebuild**, which re-clusters from the cached candles and drops the counts beyond them.

**Reading**: the ticker's newest slice (the last completed hour is its end) goes to its nearest shape (root-mean-square distance). No reading when that shape has fewer than **Minimum matches** (default 3) or lies farther than **No reading beyond** (default 2) × the library's typical distance (a slow average of the distances pairs matched at). Otherwise `dvp` / `dvv` = the shape's mean next-hour move, unshrunk. Diagnostics, never model inputs: `x_dvd` (the distance over the typical one, price library), `x_dvi` / `x_dvj` (which shape matched in the price / price + volume library). The forecast runs about 60 minutes from its start, and the reading is the next hour's close-to-close move after the last completed hour, so the two overlap rather than match exactly.

**In the forecast**: the readings are logged on each forecast like any other and are ordinary candidates in the direction test. Until the test has a verdict on one (too few graded batches or too few readings; the Export's `directionTest` shows `live until graded`) it counts at sign +1, since it is an expected price move; this also holds under 6 graded batches, when nothing else is picked. Once the test has a verdict, in or out (sign flip, too weak, pulls the ensemble down), the verdict rules. A ticker's direction score counts the columns present in the batch, so a ticker with no `dvv` is scored on the rest.

**Replacing the weakest**: a pair that matches no shape (beyond the abstain distance) takes over the shape with the fewest matches among those at least 300 pairs old, so a new pattern can earn a place instead of smearing into the nearest old one. At most one replacement per 100 pairs, so a market-wide shift cannot wipe the library; a new shape is protected for 300 pairs; a replacement keeps the shape's number, so an old reading's `x_dvi` / `x_dvj` can point at a shape that has since been swapped. The Export counts them (`replaced`).

**Storage and export**: the libraries are saved under `__ew_sw_<side>_div_v1` (see Trivia) and the candle cache gained a volume field (see Cost and storage above). The Summary export carries `candleDivination`: settings, and per library every shape's matches, mean next-hour and next-6-hour move, share up and paths. The libraries are not in the Profile export or Import; they rebuild from the candle cache. A follower bot adopts the leader's forecasts with their readings but does not run the learning, so its panel stays empty.

**Limits**: a 6-hour hourly-candle shape on its own is a weak signal, and much of what it can see overlaps readings already in the ensemble (close location, RSI, returns); the direction test over about 4 hours is short, so the readings can flicker in and out. With a minimum of 3 and no shrinkage, a shape with 3 matches ranks as loudly as one with 300. The learning was tested on synthetic candles with a planted rule (it found it), not on live data.

#### Crab Layer

A sub-toggle under Indicator Forecast (on by default) for tickers that move along a range instead of trending. It makes no requests of its own: it works from the 1-hour candles the forecast already keeps.

**Finding a crab**: for each of six windows (6, 12, 24, 48, 72 and 96 hours) the range is the highest high to the lowest low (from 12 hours up, the second-highest and second-lowest, so one spike wick doesn't stretch it). The window is scored as a crab by four tests, combined as a geometric mean: the range stops growing with time (the range over 1.6 × the hourly volatility × √hours; a random walk reads about 0.9, a bounded one far less), not much net progress (the net move over the range), the middle is crossed back and forth (a dead band of 10% of the range around it), and both edges are tested (visits to the outer 20%, counted once per stay, more of them on longer windows). A price more than the **Break margin** past the range is no crab, so a ticker that just broke out is left alone. A window counts as a crab when it scores over **Crab score to count** (default 50%).

**The snap**: the price's place in the range gives a snap reading: +1 at the bottom (expect up), -1 at the top, 0 in the middle (price direction). Only the window that matches the forecast horizon counts: the smallest window of at least 6 × the horizon (lead × scan step), so a 1-hour horizon reads the 6-hour range and a 4-hour one the 24-hour range. If that window isn't crabbing, the layer leaves the forecast alone.

**Breaker library**: crabs don't last. The library holds every past crab found in the candle cache, filed by its window and where in its range the price sat (bottom, middle, top), whether the last hour's volume was at least twice its median and whether the last 6 hours had squeezed to under 40% of the range, with what happened in the next 6 hours: held, broke up or broke down (a break is a close beyond an edge by the **Break margin**, default 15% of the range). Each setup's break chance starts at 15% with the weight of 30 crabs and moves with what is seen. The library is built at load from a random sample of up to 6,000 past candles from the cache already in memory, then learns every completed hour of a fetched ticker once. Saved under `__ew_sw_<side>_crab_v1` (see Trivia).

**In the forecast**: it runs after the indicator blend and before Range Fit. A crabbing ticker's score is pulled toward the crab's expected move, (1 - break chance) × the snap + break chance × the setup's break tilt, scaled like the batch's own scores (their mean size). The pre-crab and the full-crab score are both kept on the forecast (`ec0`, `ecf`) so the weight can be tested.

**Weight**: the bot's own call, so there is no setting. Every graded forecast the layer changed is replayed at 100, 75, 50, 25 and 0% of the crab and the best accuracy wins (a lower weight must beat the one above by more than 0.1 points). It is judged overall and per window (30+ forecasts each; a window with no verdict yet uses the overall one). Under 6 graded batches or 30 changed forecasts the layer stands in full. A Weight Profile that has its own crab weight (`crb`) replaces the managed one.

**Elsewhere**: the crab readings (`cb*`, `cp*`) are logged and exported but never fed to the indicator ensemble; the layer applies them itself. Candle Divination learns what each shape did next while crabbing and reads that when the ticker crabs, and the retry queue notes whether queued tickers were crabbing. The Summary's `crabLayer` holds the cohorts, including a position test; grades carry `crab`.

#### Regime Caution

A sub-toggle under Indicator Forecast (on by default). A forecast's score is pp against its batch and its grade subtracts the batch's own move, so how the market itself behaves shows in neither. Yet a score means different things in different markets: in a green one even negative scores can pay, in a red one even positive scores can lose. This layer reads the market's regime, learns how tickers in the same spot did, and keeps a second score beside the usual one. It makes no requests of its own and never uses BTC. The usual score and its grade are untouched; while the layer is on, the second score is the one that ranks MI's entries.

**The market**: on each window (**Windows**, hours, default 2, 6, 12, 24, 48 and 96, each up to 99 since the candle cache holds 100) every ticker whose last hour candle is at most 2 hours old is read: its move, its highest high and lowest low over the window (from the close before it), and the share of its hours that closed green. The market's typical high and low are the averages over those tickers. A ticker's **position** is its move divided by the typical extreme on its own side (-5% against a typical low of -10% reads -0.5; clamped to ±3). The market's score is the mean position over the tickers and then over the windows (about -1 deep red to +1 deep green), banded at ±0.15 and ±0.5 into deep red, red, flat, green and deep green. A window needs 20 tickers; until one has them, forecasts carry no reading. It reads every ticker with fresh candles, not only the batch, so a retry cohort doesn't skew it.

**Profiles**: per window, a ticker is filed by the market's state (flat; red with the ticker red or flat; red with the ticker green; green with the ticker green or flat; green with the ticker red) and its position (five levels), and separately by that state and its green share against the market's. The two states with the ticker against the market are the diverging ones. Overall a ticker is aligned (or none), diverging up (green against a red market) or diverging down, by whether it diverges on at least a third of the windows. Divergence is a profile of its own, and whether it is bullish or bearish is not assumed: it comes from what such tickers did.

**What it learns** (kept in the forecast store, every cell fading with a half-life of 72 hours): the market's move per market level (one observation per graded start batch; it starts from a prior, red leaning pessimistic and green optimistic, scaled by the typical size of the market's move and read in price direction so it flips for a bot that wants price down, worth 6 batches); each profile's **sensitivity** (how far its tickers moved with the market, 1 until it has history, worth 30 forecasts); and each bucket's **usual miss** (the actual move relative to the batch, less the score, shrunk by n / (n + 30)).

**The second score** (`er`, `projectedPpWithRegime` in the Export): the score + weight × shift, where shift = sensitivity × the market's expected move + the average usual miss of the buckets the ticker is in (each weighted by how much it has seen). It reads as the expected raw move. A shift in the bot's favor is halved and any shift is capped at 3 pp, since the aim is fewer bad entries rather than higher scores.

**Weight**: the bot's own call, like Crab's, so there is no setting. Graded forecasts the shift changed are replayed at 100, 75, 50, 25 and 0% of it, judged on the raw move (the shift carries the market's own move, which the relative grade hides), overall and per profile (30+ forecasts each), and the best accuracy wins (a lower weight must beat the one above by more than 0.1 points). Under 6 graded batches or 30 shifted forecasts the shift stands in full. A forecast's shift is learned before it is graded, so the replay is out of sample.

**Panel and export**: the hint under the toggle shows the market now. The panel shows the market per window, how many in-flight forecasts were marked down or up, the tickers moving against the market, what has been learned and the weight; **Clear what it learned** resets the learning. The Summary's `regimeCaution` holds the settings, the market now, the market's move by regime, sensitivity by profile, every bucket's usual miss, the weight, and a test: graded forecasts split by the shift (marked down, left alone, marked up), by profile and by regime, with the usual score and the regime score each tested against the raw move. Grades and Pending rows carry `regime`.

**Limits**: the market part has few independent observations (one per batch, whatever the batch size), so it learns slowly and leans on its prior at first. After a reload there is no reading until 20 tickers have fresh candles, which takes a few batches. Windows are bounded by the 100 hourly candles kept. The learning was tested on synthetic candles with planted rules, not on live data.

### Chart and Scorer Display Details

The details left out of the shortened Sample Chart and Scorer entries.

#### Sample Chart

Each button is labelled with the view it goes to, the order wraps at either end, and the view resets to Vol on reload. The chart only shows when at least one sample exists. Each cycle group is stamped with its sample time, and clicking elsewhere returns to the latest.

#### L/S view

It is drawn from a zero line on a symmetric axis sized to 1.3× the 95th percentile of |value|. Only tickers whose batch carried the ratio appear.

#### Fcst view

Bars are sorted best first on an axis of 0–100 (up at or above the 70% line, down below), and each column is stamped with the time it was graded. After the dashed line, each batch still to come shows a faint tick (`+1` = the next batch). The latest column is selected by default, and hover shows its count and grade. The summary also shows graded and pending counts, lead, revisit share and voids, in a **Window** line (accuracy) and a **Batch** line, each followed by its net profit line. The Tickers table lists that batch's tickers, best accuracy first: accuracy % (colored by the same cutoffs), projected pp, actual pp (green when the sign was called right) and the raw move, scrolling both ways. The Fcst view has no ticker chips.

#### Liq view

The window average uses each ticker's latest liquidation-event reading, and watched-but-quiet tickers aren't counted in either average, so they can't pull it toward 0. The pill styles are **favorable** (pure, the bot's side) fill and outline, **mixed favorable** fill only, **mixed unfavorable** outline only, **unfavorable** neither. Mixed means the minority side holds more than **Mixed %** of the turnover (default 30%; a dead-even split counts as mixed unfavorable), and favorable is liquidated shorts on Chaser and liquidated longs on Winter. The summary line adds how many tickers are unstable. Watches from before the split was recorded only know which side led, so their pills show as pure. Only tickers watched in a cycle appear, and only cycles watched while Liquidation Surveillance was on carry it; the newest cycle fills in once its watch is scored on the next scan. It rides in the same cycle history as the other views, so it holds as many cycles as that history does.

#### Dial families and the scorecard

`lpa` is the outcome and has no dial. Observations are tallied per side and per pole, and each scorecard reflects only its own bot's samples.

#### Scorecard chart

It is a single non-wrapping row of criterion duos that scales to its container, with the criterion emoji underneath each. The header shows the side's name and total; hover a bar for its PnL and W/L.

#### Sample Scorer

Hover shows the average edge, ↑/↓ counts and n. When Liquidation Surveillance is on, LPA is scored on liquidation outcomes and drawn. The Illiquidity Filter's line shows how many tickers are illiquid, how many have been measured and the slowest.

#### Headline & gauge

The share is the move in the bot's favor as a share of all raw move on that side. Hovering the gauge shows the sample count, the mean in dollars on one base position and the relative edge, while the per-criterion bars stay relative (mean edge vs the sampled population). **Bottom** and **peak** also need at least Min Samples, and they're cleared with the samples. The headline reads `—` until enough samples carry a raw move. With Liquidation Surveillance on, the dollar mean is mixed too (hover shows how many liquidation samples went in), and **bottom** and **peak** record the mixed share.

### Criteria Sampling Internals

- **Ticker Ranking**: each scan draws **Batch Size** tickers (default 50) at random and fetches their data fresh; that batch is the sample that feeds scoring. Entry candidates are every ticker the sample has reached, however old its reading, ordered by the Indicator Forecast's score where the batch has one (the scorecard's score otherwise), and each is refetched right before it opens, so any ticker the sample has reached can be picked. Refetches stop at one batch size per scan, since fetching all six criteria across 600+ tickers every 10-minute scan would be too heavy on computation and bandwidth; a larger batch size is an option if you have the resources. The batch isn't always purely random: with Liquidation Surveillance on, tickers that just had liquidations stay and quiet ones are replaced (see **Liquidation Surveillance** below), and with the Forecast Grader on, up to its **Revisits %** of the slots go to forecasts falling due (see **Forecast Grader** below; with Forecast Focus on the grader sizes the batch itself, see **Forecast Focus** below), with the Illiquidity Filter on, tickers measured as illiquid are left out (see **Illiquidity Filter** below).

- **Tier gate**: every criterion computes an integer tier as `floor(value / step)` and compares it against N. `fund` truncates toward zero instead, so a tiny negative rate lands on `fund-0` (mirroring `fund+0`) rather than flooring to `fund-1`. Current step sizes show as read-only chips under **Tier Step Sizes** on the Fetch tab. The same tier is recorded on the position and used as the scorecard key, so `fund>40` and `fund+70` are different tiers and are scored separately.

- **Bare-form exception — `fund`**: in Auto mode, a criterion named without a `>`/`<` comparison normally still requires a nonzero tier. `fund`'s bare form is the exception: it matches any finite funding rate, exactly 0% included, because real Bybit funding rates mostly sit well under a single **Fund Step**. A near-zero rate is a real lukewarm reading (`fund+0`/`fund-0`), so it attaches and feeds the lukewarm chart. The tiered forms are unaffected.

- **Funding emoji**: position and trade badges show 🤑 or 💸 for a `fund` tier, and the emoji says whether that funding sign favors the bot's own direction, so Winter and Chaser show opposite emoji for the same raw sign. The Extremity Scorer's own pills use one fixed set on both bots (💸 positive, 🤑 negative).
- **`va`**: `va+12` = 12 tiers hotter than the sampled population. `_swVolIoWindowAvg` delegates to `_swWindowStats`, a deduplicated latest-reading-per-symbol read (`vol`, `oi`, `oil`, `ois`, `ls`, `lta` or `lpa`) memoized per history state; the Sample Chart's Total avg draws from the same read.
- **`iol` / `ios`**: a ticker's long share of open interest is `oi × long share` and its short share `oi × (1 − long share)`. The long share is Bybit's long/short account ratio (`_swLsRatio`: `GET /v5/market/account-ratio`, 5-minute period, latest row, `buyRatio ÷ (buyRatio + sellRatio)`), fetched per sampled ticker with the batch and stored on its sample record as `bl` (null when the call fails; the record then carries no `bl`). The tier is `floor(100 × ln(share ÷ window average) ÷ step)` against the window average of that share (`oil`/`ois` in `_swWindowStats`, which only counts latest readings that carry both `oi` and `bl`), so there is no tier without both, or without a window average. The **L/S** chart view and the batch context read the same `bl` (skew = `(2 × bl − 1) × 100`).
- **`fund`**: tier is `trunc(rate% / Fund Step)` with an explicit sign, so tiny negatives tag `fund-0` and exact zero tags `fund+0`. Sample records carry the funding rate as `fr` (%) so the Fund chart and Sample Scoring can use it.
- **`lta`**: `_swLtaDev`; `lta+12` = 12 × **LTA Step** (default 10%) above the ticker's own average hour (`turnover24h / 24`). No population baseline.
- **`lpa`**: `_pfLpaWindowAvg(sym)`/`_afLpaWindowAvg(sym)`, in tiers of **LPA Step** (default 0.25pp). Absolute points, since a relative deviation is unstable near a zero mean. No tier until at least one other ticker has an `hc` reading in the window.
- **Candle fetch**: `_swHourCandle` calls `GET /v5/market/kline` at `interval=5&limit=26` (130 minutes of 5-minute candles) and merges the candles inside the last completed hour (`_swHourStart`) into its hour reading, so `ht`, `hc` and `htp` keep their meaning (a minute with no trade can leave the merged hour a little short); the forming candle is never part of it. The candles also sit in memory for the batch (`CAND5`), where the Forecast Grader reads the typical price of the last ~10 minutes (`_swTyp10`: the two newest candles started within 15 minutes of now, (highest high + lowest low + last close) / 3) and the path since a forecast. The hour reading goes in a memory-only per-symbol cache (`HOUR_CACHE`, pruned past 500) and is attached, as `ht`, `hc` and `htp`, to the ticker's OC cycle entry, so a **Follow Partner Bot** instance gets it from the leader (`_swHourReading`). The fetch rides the same batch (`wantHr` on `_ocFetchBatch`) whenever `lta` or `lpa` is in use. The Indicator Forecast's 1-hour kline fetch (`interval=60`) is separate and feeds only it.
- **Fresh batch fetch**: `_swFetchFreshTicker` calls `GET /v5/market/tickers?category=linear&symbol=` per batch symbol, keeps the raw payload for the scan (`_swFreshTicker`) and stores a compact `{ vol, oi, fr, px, ch }` reading. A failed fetch drops the ticker; there is no fallback to the bulk list. A **Follow Partner Bot** instance rebuilds tickers from the leader's readings (`_swSynthTicker`). Entry candidates are refetched the same way by `_swFetchCandidate` (ticker, plus OC and the hour candle when used), which touches neither the OC results nor the cycle history.
- **Entry-pool freshness**: MI act once per new batch (`_swOcResultsAt`), not once per bulk fetch, and `_micOpen` skip the pre-open price refetch for a ticker from the current batch (`_swTickerIsCurrent`). Candidates come from each ticker's latest stored reading (`_swLatestReadings`, rebuilt by `_swSynthStored` with `_cycle` set to that reading's own cycle time, so only the latest batch counts as current). Before a non-batch candidate opens or displaces a position, `_micVerify` refetches it, reruns the slot match, and stops at **Batch Size** refetches per scan. The refetched ticker only has to still qualify; it doesn't need to keep its ranked tier or score.
- `_micHourTier` returns `null` for missing data: the criterion check reads it as false and the annotator as "no sample", never a fake `+0`.
- Emoji for retired criteria stay resolvable in `critEmoji`/`swCritEmoji` so old records and exports render; they are display-only.

### Deferment & Ejection Internals

- **Deferment signal**: the Relative Target floor test alone (see below).
- **Deferment effect**: the scan returns before every open path, with guards inside `_micTrySubstitute` and `_micOpen`. Historical scoring still runs. One `⛔ Deferment` log line per streak.
- **Ejection**: runs every scan ahead of slot logic (so it acts with no active slots) when the deferment state's `eject` is set, which needs two or more paths in `why`. With only the floor path left, it can't fire. `_micEject` closes every non-pending position of any strategy concurrently (`Promise.all`), each close in its own try/catch, with one `⏏️ Ejection` log line naming the paths and close reason `ejection`. Each trade is scored against its opening criteria.

### Relative Target Internals

- **Targets**: `_micRelMoves` reads `_swOcCycleHistory`, takes the latest `micRelBatches` cycles by time and each ticker's latest `hc` (1h price change %) within them, and averages the positive and the negative readings separately; it returns null unless each side has at least Min Samples (floor 3) readings. `_micTargets` turns that into the targets: the favorable side's average × `leverage` is `entryTp` and `cascadePct`, the other side's average × `leverage` (floor 1%) is `slPct` and `sacrificePct`. Chaser's favorable side is the positive average, Winter's the negative. It returns the configured values untouched (`active:false`) when Relative Target is off, neither Cascade nor Sacrifice is on, or `_micRelMoves` has no data. `_micEffCascadePct` and `_micEffSacrificePct` return the resolved % floored at Min Entry TP and 1%; `_micTargetsText` feed the Exit-tab readout.
- **Per-position overrides**: `_micOpen` pass `_tpPct` and `_slPct` on the candidate. PseudoWinter/PseudoChaser use `_tpPct` for the entry TP, and `_slPct` for the binary-mode SL at open. It is also stored as `pos._slPctOverride`, which the DCA-mode SL arm, the SL drift check and the position card honor. Both candidate fields are excluded from the copy of candidate fields onto the position.
- **Targets gauge**: `_micTargetsView` turns `micTargets()` into `{left, right, note}` for the gauge (left SL and Sacrifice, right TP and Cascade). Each row carries its text, a bar width (none for Cascade/Sacrifice) and a class: `ok` when the resolved value is at or above `minTp`, `bad` below it, `off` when disabled or while Relative Target is still waiting. Cascade/Sacrifice classes read the raw `cascadePct`/`sacrificePct` (the configured value when `active` is false), while their text reads `micEffCascadePct`/`micEffSacrificePct`. The body binds it with `x-effect`. `micTargetsText` is no longer bound to anything.
- **Entry ranking**: `_micScanPool` asks `_swFcRankMap`() for the batch's forecast scores (the leader waits up to 20 s for the slow readings, a follower adopts the leader's store with `_swFcAdopt` and waits up to 20 s for one newer than the last it ranked on). When Still-Water is loaded the pool is cut to the tickers in that map (counted as `noForecast` in the scan skip summary), and each is scored with `_micRankScore`: the forecast's score in the bot's favor (`_swFcFavor`: `er` when Regime Caution is on and the forecast has one, else `e`, times `_swSampleDir`). Candidates sort by score, then by funding magnitude. Without Still-Water the pool is every criteria match, unranked. `compositeScore` is that score; Substitution compares it with `_micLiveCompositeScore` (`_swFcScoreOf`: the newest forecast on the held ticker, else the score at open) and writes the result to `pos._micCompositeScore`. The leader's shared write of the forecast store is held (`_swBgBusy`) from a batch's ingest until `_swBgRun` has landed the slow readings, so a follower only ever adopts final scores.
- **Deferment**: `_micDefermentState` wraps `_micDefermentStateBase`, which holds only the Relative Target floor test: it defers while the resolved entry TP is under Min Entry TP.
- **Headline source**: `_swSampleBuild` accumulates the raw edge per bucket into `swSampleBucketMeans` (`aE`/`aL`, counts `nAE`/`nAL`) and the signed favorable share `(P−Q)/(P+Q)` of those raw moves (`sE`/`sL`). `_swSampleWeather` returns the dollar `value`, the share (`s`, and `share` as 0–1) and the peak/bottom of each (`hi`/`lo`, `sHi`/`sLo`). `_swSampleTrackWx` keeps those peaks in the sample store as `wx`, and the leader shares them with followers. `aE`/`aL`/`sE`/`sL` come from one blend: each source is reduced to per-observation pp mass `{P, Q}` (price `p/n`, `q/n`; liquidation `p/w`, `q/w` once its bucket holds Min Samples), the sources are mixed on `P` and `Q` (50/50 for liquidation, only when the base exists), and `a = P − Q`, `s = (P − Q) / (P + Q)`, so their signs can't differ. With Liquidation Surveillance on, the liquidation side is part of that mix; `nlE`/`nlL` report its count, `nE`/`nL` and `nAE`/`nAL` include it, and the weather's `nl` carries it for the tooltip. The bucket `extreme`/`lukewarm` means that pick the favored side are mixed the same way. The peak/bottom `sHi`/`sLo` are tracked for the gauge only.

### Extremity Scorer Internals

- **Cutoffs**: come from the scored sample observations, built in `_swSampleBuild`. A pole with at least **Min Samples** readings cuts off at its **Extreme Split** percentile; a reading at or above it is extreme, anything below it and everything on an unproven pole is lukewarm. Bare sign-only tags (`+fund`/`-fund`) carry no magnitude and always classify extreme.
- **Two tallies**: the dial tally counts extreme occurrences only and is the flat `micCollapsedSlotRanks`/`micCollapsedCritStats` lookup that MI's manual-slot ordering reads. The Lukewarm Scoring tally counts every occurrence, bucketed by class then by pole (`fund+`/`fund-`, not merged by family, since a family's poles are opposite signals).
- **Favored side**: `_swLukewarmFavoredSide`, re-decided each time the scorer rebuilds (once per scan cycle).
- **Sample Scoring**: `_swExtremityBuild` runs `_swSampleBuild`, which publishes the outputs (cutoffs, `micCollapsedSlotRanks`, the two-bucket scoreboard) from `__ew_*_sampleobs_v1`, plus the per-bucket mean edge (`swSampleBucketMeans`) for the favored side. `_swSampleIngest` runs with each new sample cycle and stores one observation per ticker: its criteria tags at sample time, `y` (the last completed hour's price change minus the rolling LPA average from `_swLpaWindowAvg`) and `r` (the raw change). The build keeps only each ticker's latest observation per clock hour and skips `lpa` tags on price observations. The leader hands over `sampleScore` through the corridor and a follower adopts the delivered copy each scan (`_swSampleAdopt`).
- **Forecast Grader**: `_swFcPlan`(pool, cap)` is called by `_micScanFetch` before the batch is built (leader only, null when following). It takes the pending forecasts with `d <= seq + 1`, oldest first, skips illiquid tickers (`_swIlqIs`), caps them at `floor(cap × share)` and stores `{seq, cap, rev, rsv}` (`rev` = the revisits; `rsv` = the waiting liquidation reservations the planner added to the returned list, which the ingest does not treat as revisits) in `_swFcPlanned`; the builder removes those symbols from the pool, passes `cap − revisits` to `_swLiqPick`, and fetches `[...revisits, ...pool]` deduplicated and cut to `cap`. `_swFcIngest` runs after each batch's `_swSampleIngest` (and for a seeded follower batch, where it returns at once since a follower adopts the store with `_swFcAdopt`). It is idempotent on the batch timestamp, increments `seq`, and (1) grades every forecast with `d <= seq` whose ticker is in the batch with a price: elapsed over 1.5 × lead × `_swFcStepMs` counts as `late`, a missing ticker is retried until `seq − d >= 2` and then counts as `gone`, and a start batch with under 3 gradable forecasts counts as `thin`; the move is `m = (typical / price − 1) × 100`, where typical is `_swTyp10` of the ticker's 5-minute candles from this batch's fetch (`CAND5`; else the revisit result's `htp`, else its `px`) and price is the frozen typical price, `mu`/`md` are the highest and lowest point of those candles since the forecast, and the actual is `y = m − k`, `k` being the cohort's mean `m`; `y`, `m` and `k` are stored raw. Each graded forecast is filed with `e0` and `ef` (the full Range Fit value) beside `e`, which the Range Fit weight test reads. Then (2) it starts forecasts from batch results that are not revisits and not already pending: `_swSampleTags` (without LPA) gives the tags, `_swFcParts` the mean `pnl` (and each family's share `w`, stored raw like `e`) of the scoreboard entry (`swLukewarmScoreboard.extreme`/`.lukewarm`, picked by `swDialCutoffs`, needing Min Samples) of each tag's pole, multiplied by `_swSampleDir` to store it raw. Reserved candidates (`_swFcReserve`) go first, newest event first, and the rest are shuffled; all are capped at `min(share slots, share slots × (lead + 3) − pending)`, so the revisit half and the fresh half balance. The picked forecasts go through `_swFcRangeFit` before they are stored. The scoreboard used is the one built before this batch's observations, so a forecast never sees its own outcome. `_swFcStats` reads both values in the bot's favor (`dir × e`, `dir × y`) and returns n, Spearman rho (average ranks for ties), hit and base, the top/bottom fifth means and spread (n ≥ 20) the OLS slope, the mean accuracy (`_swFcAcc` per forecast) and the influence shares (`_swFcInfl`). `_swFcChartSvg`, `_swFcBreakdownHtml`, `_swFcSummaryText`, `_swFcWindowText` and `_swFcBatchText` draw the Fcst view; `_swFcExport` builds the Export file and Import restores `forecast.store` through `_swFcSanitize`. Nothing in `_swSampleBuild` reads the grader. **Range Fit**: `_swPmPush(sym, hs, ret)` files one hourly return (stored ×1e4 as an integer) into the module-level `PM` (`{s: {symbol: {t, r}}, v, dirty, rel, relV}`); `_swBgH1` calls it for each completed hour it feeds when that hour directly follows the ticker's last (a gap is kept as blanks, one longer than `micFcPmHours` resets the ticker), `_swPmLoad` reads `__ew_sw_pm_v1` and `_swPmSeed` fills from the candle cache (index-timed, like the candle libraries), `_swPmTrim` applies a new `micFcPmHours`, and `_swPmSave` writes it (called from `_swBgPersist`/`_swBgFlush` when dirty). `_swPmRel()` builds, once per store version, each ticker's market-relative hourly moves in % (the hour's median across the stored tickers taken off, which needs 8 tickers that hour) as a `Float64Array` over the stored hour span with the ticker's spread `sd`; tickers under `PM_MIN` = 12 hours are left out. `_swPmPeersOf` correlates a ticker's series with every other over their shared hours (at least `PM_PEER_MIN` = 24) and keeps the `micFcPmPeers` best at or above `micFcPmCorr`. `_swPmExpect` pools the ticker's own moves and its peers' (each × the ticker's `sd` over the peer's, clamped 0.25–4, all × √(lead × scan step ÷ 1 hour)) into a weighted distribution: the own moves hold `micFcPmOwn` of the weight (all of it with no peer), the peers share the rest by correlation squared, each peer's share spread over its moves; `_swPmQ(x, pr)` reads its quantile by interpolating between the weighted midpoints. `_swFcRangeFit(list, state)` sorts the batch by `e`, gives tied values their middle rank, reads each ticker's quantile at plotting position `(rank + 0.5) / n`, sets `e0` to the raw `e`, `ef` to that quantile and `e` to `w × ef + (1 − w) × e0`; a ticker with no usable range gets `e0` and `ef` of `null` and keeps its `e`. `micFcRangeInfo` keeps the last fit (counts, average peers, up to 80 rows) for the hint and the Export. `_swFcRangeBlendCalc()` sets `w`: over the forecasts in the indicator window that carry `ef` and `e0` it averages `_swFcAcc(g × ef + (1 − g) × e0, y)` for g = 1, .75, .5, .25, 0 and takes the lowest g that beats the one above it by more than 0.1 (w = 1 under `FC_IND_MINB` graded batches), cached per store length, newest grade and window. The batch context (`_swFcCtx(entry)`) is still filed in `fc.ctx` for the Export. `_swFcPass` (70) is the chart's up/down split, `_swFcMid` (50) its second cutoff and `_swFcClr` the green / yellow / pink colour of an accuracy.
- **Weight Profiles**: `_swFcLive` begins with `_swFcProfAssign`(list)`, which runs once per new forecast (marked by `pk`: `g` general, `t` trial, `p` proven): it ranks the batch's `sn` readings (`FC_PROF_TRAITS`) with `_swFcPct`, matches the nearest profile (`_swFcProfNear`, or `_swFcProfNew` for a queued ticker that matches none) and sets `pf` (profile id), `pc` (trial id), `pt` (trait ranks) and `pwt` (the weights it starts on; a trial comes from `_swFcProfCand`). `_swFcProfBase` rebuilds the scorecard projection from the per-family contributions (`w`) with the multipliers, and `_swFcProfW(f, key, default)` supplies `ind` (blend in `_swFcLive`), `div` (`_swFcIndDir`) and `rng` (`_swFcRangeFit`). The ingest calls `_swFcProfGrade` beside `_swFcRtyNote` for every graded forecast: it files the profile, nudges its centre, records the trial or the pass / failure on proven weights, proves or restarts. Profiles live in the store as `prof` / `profN` (`_swFcSanitize` keeps them and the new `pf`, `pk`, `pc`, `pt`, `pwt` fields on pending and graded rows). `_swFcPlan` appends `extraList` (more of the queue, then in-flight tickers) after the fresh draw when the batch is under Focus's size.
- **Forecast Focus**: `_swFcFocusOn()` (Grader on and `cfg.swFcFocus !== false`), `_swFcFocusN()` (5–50, default 50), `_swFcRtyShare()` (0–100 %, default 60) and `_swFcRtyLow()` (51; the pass line is `_swFcPass()`, 70). The store gains `rty` (ticker → `{n, a, t, f}`: forecasts graded since the first miss, latest accuracy, last graded time, first miss time), `rtyG` (passes) and `rtyL` (the last 200 passes, `{s, n, f, u, a}`); forecasts carry `rt` (the attempt number, null for a first forecast) and a start log row carries `y` (retries started). `_swFcRtyNote(fc, sym, acc, ts)` runs for each forecast as it is graded (accuracy from `_swFcAcc(e, y)`): at or above the pass line it removes the ticker and logs the pass, a queued ticker below it updates `n` and `a`, and an unqueued one under 51 is queued. In Focus `_swFcPlan` caps the revisits at `FocusN`, drops queue entries idle over 14 days and returns `{revisit: due + liquidation reservations + retries, batch, cap}`: `newRoom = FocusN − revisits`, reservations at most `newRoom >> 1`, retries sorted by `a` then `t` at most `floor(newRoom × share)` (skipping tickers with a forecast in flight, outside the pool, illiquid or stable), then fresh tickers walked off the shuffled pool until `FocusN` is reached; `batch` is all of them and `cap = batch.length`. `_micScanFetch` fetch `fcPlan.batch` as it is, passing it through `_swLiqPick(batch, batch.length)` only to open the liquidation watch on it, and keep the entry-verify budget at the configured batch size. `_swFcIngest` then starts up to `FocusN − revisits` forecasts (the pending ceiling stays `FocusN × (lead + 3)`), taking liquidation reservations first, then retries (worst `a` first, up to `floor(slots × share)`), then fresh tickers at random, and stamps `rt = n + 1` on those that were queued.
- **Indicator Forecast**: `_swBgFree`(r, t, cs, now, sn)` builds the readings that need nothing fetched (from the bulk ticker `t`, the 5-minute candles `cs` and the snapshot), and `_swFcIngest` files them on each picked forecast as `bg`; `_swBgRun`(pick)` (not awaited) then fills the slow ones with three workers: `_swBgH1` (kline `interval=60`; `BG1H[sym]` holds the last 100 completed closes, highs and lows, the Wilder state for RSI 6/12/24 (`_swBgFeed`: the first p changes seed a simple average, then `(avg × (p − 1) + x) / p`) and the last 20 RSI 12 values; first sight asks for 100 candles, later fetches for the completed hours missing plus one, and a gap over 90 hours re-warms; `_swBgH1Feat` computes the readings), `_swBgOi` (`/v5/market/open-interest`, `intervalTime=15min`; `BGOI` holds the last 17 rows merged by timestamp and counts as current when its newest row is the last completed quarter hour) and `_swBgFh` (`/v5/market/funding/history`, `limit=6`; `BGFH` is refetched when the next settlement, the last one plus the observed interval plus 2 minutes, is due, and at most every 10 minutes while the venue has not posted it). When the slow readings have landed, `_swFcLive(pick, ctx)` scores the batch again (it also runs at ingest with the free ones): it restarts every forecast from `ep.sc` (the scorecard's own score, stored at ingest), then, with `_swFcIndOn()` (= `_swBgOn()`, always on), `_swFcIndDir` writes `bg._dc` (`_swFcPct` ranks each reading `_swFcIndSelect` has picked within the batch, centred, ties sharing a rank, and flips it by its orientation; the mean over the readings a ticker has, at least 2 when that many are picked; none picked = no `_dc`) and `_swFcIndVol` writes `bg._vi` (`VOL_FEATS`: geometric mean of own / batch-median, clamped 0.25–4, a median needs 3 readings), blends `_dc` into `e` as `(1 − w) × e + w × 2 × dc × S` (`w` = `_swFcIndBlend()`, `S` the batch's mean |scorecard score|, floor 0.05) and lets `_swFcRangeFit` lay the batch onto the range, taking each ticker's size from `bg._vi` when present (else its 60-minute range over the batch median). `_swFcFeatureIC` reads both the snapshot and `bg`. `BG_SKIP` keeps predictions (`_sw`), the post-start liquidation diagnostics (`x_sw`) and `c60` out of `featureIC`. `_swBgLiq(cyc, syms, lean, split, cl)` is called by `_swLiqIngest` and copies the closed watch's result onto the pending forecasts of the cycle it started on, with `cl.at − cl.watch.t0 − cl.gap` as the listening time (`LIQ.gap`/`LIQ.downAt` count blind time: started when the feed closes, added when it opens, and on a restore `now − the saved time`; additive to the surveillance, scoring is unchanged), and saves the store at once; `_swBgSeal` writes `x_lqw = 0` when a forecast is graded without a reading. `_swBgPack`/`_swBgUnpack`/`_swBgPersist`/`_swBgLoad`/`_swBgFlush` persist `BG1H` (`BG_PERSIST_MAX` 600; returns ×1e5, wicks ×1e4, the Wilder state exact); `_swBgFlush` also runs on `pagehide` and when the page becomes hidden, and writes the unsaved readings of a run in flight.
- **Direction selection, liquidation readings and reservation**: `_swFcIndSelect`()` is cached on the graded count, the last graded time and the window. Its candidates are every numeric `sn`/`bg` key outside `BG_SKIP` seen on at least 15% of the window's forecasts (identical-value readings skipped); `_swFcPct` ranks each within each batch, the per-batch rank correlation with `y` (`_swFcCorr` of `_swFcRank`s) gives the window and half-window means, the screens run (same sign in both halves, size at least `FC_IND_FLOOR` = 0.02, then greedy by strength keeping a reading only if the ensemble's mean per-batch correlation does not fall), and it returns `{feats: [{k, s, o}], batches, rows, ic, table}` (`s` = `sn` or `bg`, `o` = the orientation ±1); under `FC_IND_MINB` = 6 batches it returns no features. `_swLiqDecayed`(sym, now)` walks `_swOcCycleHistory` (25 cycles), takes the cycles older than `now` and younger than the dropoff whose result for the ticker has an event (`_swLiqHas`), and weights its `lu`/`ld` by `1 − age / dropoff`; `_swBgFree` writes the result as `lqa`/`lqt`. `_swFcReserve`(fc, now)` fills `fc.rsv` (ticker → the event's cycle time) from the same history, prunes at the dropoff and keeps `fc.rsvC` (what started forecasts consumed, stored as the batch time minus 1 ms so an event on that very cycle reserves again); `_swFcPlan` appends up to half the revisit share of waiting tickers (not pending, in the pool, not illiquid or stablecoin) to its returned list, and `_swFcIngest` starts reserved candidates first and appends each batch's row to `fc.sl` (kept 120). The settings are `micFcIndWin` (1–48 hours) and `micFcLiqDrop` (0.25–24 hours).
- **Candle Divination**: module state `DIV` (`libs` {p, w}, `buf` for young libraries, `last` per ticker, `loaded`, `dirty`) and the constants `DIV_SL` 6, `DIV_BOOT` 1000, `DIV_SAMPLE` 4000, `DIV_CAP` 400, `DIV_MIN_I` 24, `DIV_GRACE` 300, `DIV_SPACE` 100. `BG1H[sym]` also holds `v` (hourly volume, null where not held), kept aligned with `c`/`h`/`l`; `_swBgPack` writes it as the 11th element and `_swBgUnpack` pads older entries with nulls. `_swDivVec`(st, i)` builds a slice's shape for the slice ending at candle `i`; `_swDivPairs(st, from, keep)` yields every (shape, what followed) pair whose following hour is newer than `from`. `_swDivLearn(sym, st)` runs from `_swBgH1` after new hours are fed (in a try, so a failure never costs the forecast its readings) and `_swDivFeed` either nudges the nearest shape (`_swDivTake`, running means) or, for a pair beyond the abstain distance, replaces the fewest-matches shape old enough (`lib.g` counts pairs fed, `lib.lr` the last replacement, `q.b` a shape's birth); a young library only collects, and `_swDivMaybeBuild` (after each readings run) clusters it with `_swDivKmeans`/`_swDivBuild`. `_swDivEnsure` loads `__ew_sw_div_v1` once and calls `_swDivBoot`, which samples the cached candles for any library still missing. `_swDivRead(st)` runs at the end of `_swBgH1Feat` and returns `dvp`/`dvv` and the diagnostics. In `_swFcIndSelect`, `_swDivLive(out)` adds `dvp`/`dvv` at sign +1 when no test verdict (a row with a correlation) exists, on both the under-`FC_IND_MINB` path and after the greedy pick; readings with the toggle off are skipped, and the cache key includes the toggle. `_swFcIndDir` requires at least 2 readings only as far as the batch has columns with any values. `_swDivPanel`/`_swDivSpark` draw the panel, `_swDivExport` builds `candleDivination`, `_swDivReset(rebuild)` backs the two buttons.
- **Liquidation event size**: `_swLiqIngest`(entry)` collects each watched ticker's event (`z` = |liquidated shorts − liquidated longs|), builds the yardstick from `_swLiqHistLive` (the stored `lqh` inside the sample store, aged by `_swLiqHistMs`: the setting, floored at the Score Horizon) plus the batch's own sizes through `_swLiqSizeStats` (`{n, med, peak, bottom}`), then writes `pp = sign(net) × _swLiqScale() × min(z, peak) ÷ med` as `r` (0 when `z` or `med` is 0) and appends the batch to `lqh` (capped at 5000). `_swLiqHistStats()` is the summary the status line shows; the leader publishes it as `lqs` in the shared `sampleScore` and a follower adopts it. The profile import accepts `lqh`.
- **Forecast net profit**: `_swFcNet`(recs)` filters the batch's forecasts to those with a recorded `m`, converts `e` and `m` to the bot's favor with `_swSampleDir()`, keeps those with `e > 0` and takes the top `cfg.maxPos` (3 if unset) by `e`. Each pick is simulated: `tp = (binary ? binaryTpPct : entryTpRoi) ÷ leverage`, `sl = (binary ? binarySlPct : dcaSlPct) ÷ leverage` (price %, defaults 18 / 18 / 16), `liq = 100 ÷ leverage − 0.5` and `stop = min(sl, liq)`; the favorable and adverse excursions come from `mu` / `md` (the end move alone when they are missing), and a pick exits at the stop when the adverse excursion reaches it (`−minNotional × sl ÷ 100`, or `−minNotional ÷ leverage` when the liquidation is the nearer), else at the TP when the favorable one reaches `tp` (`minNotional × tp ÷ 100`), else is held (`minNotional × m ÷ 100`); a path touching both counts as the stop. It returns `{n, usd, tp, sl, liq, held, lev, tpRoi, slRoi}`; the readouts use `usd` alone. `_swFcNetBatchText`/`_swFcNetWindowText` feed two extra text lines in the Fcst view (null in other views); the window groups every graded forecast in the store by start batch. The influence text is not emitted (`infl` is still computed and exported).
- **Forecast history and export parts**: `_swFcIdbBoot` (called once from init after `_swFcLoad`, never awaited, 4 s timeout, `_swFcIdbBroken` set on any failure) opens `FC_IDB`, reads every record and merges the ones the in-memory store lacks (records graded after the store's last batch are left over from a reset and are skipped; everything is skipped when following), sorts by grading time and cuts to the keep. `_swFcSave` hands the store to `_swFcIdbPush` (one transaction that puts the rows IndexedDB doesn't hold and deletes the ones the keep trimmed; `busy`/`dirty` serialise it) and writes localStorage with `FC_LS_TAIL` (120) graded rows only once IndexedDB has returned rows on a boot (`proven`), else `min(keep, 600)`; `_swFcClear` also clears the object store. `_swFcExport(part)` builds the Export parts (`summary` by default, `graded`, `readings` and `pending` with the readings as `columns` + `rows`, `ranges`, and `store`, which only the Profile export uses because Import reads `forecast.store`); `_swDownload(name, data, compact)` writes the `forecast:` parts without indentation.
- **Graylist**: there are two lists. The quiet graylist `lgray` (symbol → time it was found quiet) sits in the sample store and is written and read only by `_swLiqPick`; a quiet ticker is simply not picked for the batch until the pool runs short, and it stays a normal entry candidate. The Instability graylist blocks entries and isn't stored: `_swInstabStats` (memoized per history state and a `_swLiqVer` counter, since `lu`/`ld` are written onto cycles already in history) sums `lu`/`ld` per symbol over the retained cycles, needs `swInstabMinWatches` (2, no UI) watches with liquidations, scores `1 − |U − D|/(U + D)`, and flags symbols at or above `avg × (1 + Instability %/100)`. `_swGrayHas` (checked in `_micScanFetch`, counted as `excluded.gray`) returns true for that set, for any ticker `_swIlqIs` flags (Illiquidity Filter). The Instability check works while following, and neither of those two lists does anything when Liquidation Surveillance is off; the Illiquidity check depends only on its own toggle. `_swLiqPillClass` classifies a watch for the pills from `lu`/`ld`, falling back to the sign of `lq` on older cycles.
- **Thin poles**: a pole under **Min Samples** scores 0 and counts as lukewarm; at Min Samples its score becomes the plain mean of those readings with no shrinkage, so a rare pole (e.g. `fund-`) jumps from neutral to full weight on a handful of readings.
- **Score Horizon**: `_swObsHorizonMs` (the setting, minimum 0.5 h), `_swObsLive` (observations inside it) and `_swObsTrim` (age trim, then a byte cap from `_swObsCap`) are the only retention rules for the sample store. `_swSampleBuild` and the status line read `_swObsLive`, so scores follow the horizon between saves. The copy published for a following bot is the same age trim capped at 60 KB, so a follower can hold less than the leader.
- **Export / Import**: `_swExportPart` builds each export from the in-memory stores (cross events through `_swCrossRead`, so the full shared log, not the partner feed); `micExportData` adds `exportType`, `exportedAt` and `version`. `_swImportApply` recognizes record types by their keys, not by `exportType`, which is why single-type files, Profile and Everything all import, and it replaces only the stores present in the file. Sample observations go through `_swSampleSave`, so anything older than the horizon is dropped on import; cross events are merged on `ts|kind|source|symbol` because that log is shared with the partner bot.
- **Liquidation Surveillance**: the feed is `allLiquidation.<symbol>` on the public linear WebSocket, held at module level in `LIQ`: the socket, its subscriptions, the per-symbol tally `{up, dn, n}` (up = liquidated-short turnover, down = liquidated-long turnover, `S:'Buy'` meaning a long was liquidated), the watched set and the closed watch awaiting scoring.
  - **Feed**: subscriptions are diffed and sent 10 per request, with a 20 s ping and 5 s reconnect (`_swLiqWsSync`, `_swLiqWsApply`), and only while `_swLiqOn()` holds (toggle on, not following).
  - **Picking**: `_micScanFetch` calls `_swLiqPick(pool, cap)` with the shuffled pool. It closes the watch that just ran (snapshots and resets the tally; a watched ticker with events that is still in the pool is kept, most turnover first, and every watched ticker without events goes into `lgray`). It then fills the batch with the kept tickers, fresh non-graylisted ones and, only if still short, the oldest-graylisted (removed from `lgray` as they return), and subscribes the new set. It returns null when off or following, and the random batch stands.
  - **Ingest**: after that scan's batch lands, `_swSampleIngest` calls `_swLiqIngest`. It writes one `k:'l'` observation per ticker with events: criteria from the fresh reading (`_swSampleTags` with LPA included), `y = (up − dn)/(up + dn)`, `r = y × S` and `w = up + dn`, where `S` (`_swLiqScale`) is the median of |latest 1h change − window average| over each ticker's latest reading (floor 0.05pp). A ticker with events that wasn't re-fetched (more liquidated tickers than the batch holds) gets none.
  - **Cycle stamps and sharing**: it also stamps `lq` (the event's pp, size-scaled, 0 for watched-but-quiet) and, for tickers with events, `lu`/`ld` (liquidated-short / liquidated-long turnover in $) on the cycle the watch began on. The Liq chart view reads `lq`, and the pills and Instability Graylist read `lu`/`ld`. The leader also hands the lean over through the corridor as `liqLean` (`{cts, lq, ls}`, `ls` being the `lu`/`ld` split per symbol), keyed by the ts the cycle was published under (stamped on the cycle as `pub` from `_sharedPubTs('ocResults')` once the `ocResults` handover is queued). A follower's `_swLiqAdopt`, run at the end of `_ocSeedFromShared`, files it on the matching cycle of its own history, trying again next scan if that cycle isn't there yet.
  - **Build**: `_swSampleBuild` ignores `k:'l'` observations while the toggle is off. Otherwise each is parsed like a price observation (`edge = dir × r`, with `dir` −1 on Winter and +1 on Chaser), weighted `min(3, w / median w)`, added to the same pole pool and cutoffs and bucketed by them. The pole scores, favored-side means and headline figures are the 50/50 mixes described in **Headline source**.
  - **Caveat**: the LPA window average, V/A, IO/L and IO/S baselines read each ticker's latest reading, so a batch weighted toward tickers that keep liquidating tilts those baselines toward active names.
  - **Persistence**: the watch persists to `__sw_<side>_liq_pending` (4 s throttle while events arrive, plus each pick, ingest and page hide), with its blind time (`gap`) and, for a closed watch, its start, end and gap. The first pick after a reload restores it (dropping anything older than 12 h), reconnects the feed, and the next ingest scores it like any other. Price and liquidation observations are trimmed to the byte cap separately (`_swObsTrim`).
- **Illiquidity Filter**: readings live in the module-level `ILQ.rec` (`{ SYM: { t, g } }`), loaded by `_swIlqLoad` in `init()` and saved by `_swIlqSave` to `__ew_sw_<side>_ilq_v1`.
  - **Measure**: `_swIlqMeasure`(sym)` makes one `GET /v5/market/recent-trade?category=linear&symbol=…&limit=3` through `_qFetch`, sorts the trade times and returns `(newest − oldest) / 2` in ms. It returns null (nothing recorded, retried next batch) on a failed fetch or fewer than 3 trades. A reading is fresh while younger than `swIlqRefreshDays` (`_swIlqFresh`); `_swIlqIs` is true when the toggle is on, the reading is fresh and its gap exceeds `swIlqSlowSecs` × 1000.
  - **In the batch**: in `_ocFetchBatch`, a ticker already flagged is skipped before any fetch. Otherwise, right after its ticker fetch and before the hour candle, a ticker with no fresh reading is measured; if that makes it illiquid it's removed from the batch (`FRESH_TICKERS` entry deleted, no candle fetched, no result). The batch log line adds `N t measured (M illiquid, left out)`. The save runs once per batch and drops readings unseen for 3× the refresh window.
  - **In the pool**: `_swGrayHas` includes `_swIlqIs`, so MI leave flagged tickers out of the scan pool before the batch is drawn, and they don't take a batch slot. Counted as `excluded.gray`.
  - **Following**: a follower makes no fetch. `_swIlqAdopt`, run in `_ocSeedFromShared`, merges the leader's shared `ilq` (`{ SYM: [t, g] }`; the newer reading per ticker wins) into its own store and never publishes it back.
- **Stablecoin Filter**: verdicts live in the module-level `STB.rec` (`{ SYM: ms }`), loaded by `_swStbLoad` and saved by `_swStbSave` to `__ew_sw_<side>_stb_v1`. It adds no request: `_swHourCandle` calls `_swStbJudge` with every freshly fetched hour candle, which takes the range of the candle's open, high, low and close and the current price (the forming candle's close) as `(max − min) ÷ open` and stamps the ticker when it is under `swStbMinPct`. `_swStbIs` is true while a stamp is younger than `swStbHours`. In `_ocFetchBatch` a ticker just judged a stablecoin is dropped from the batch after its candle fetch (no result), and `_swGrayHas` includes `_swStbIs`, so MI leave it out of the scan pool (counted as `excluded.gray`) until the verdict expires. A follower never judges: `_swStbAdopt` merges the leader's shared `stb`.

### Cross-Tab Data Pool

Both bots share data two ways: a small registry in `localStorage.__ew_shared_v1` (with `BroadcastChannel('ew_shared')` change notices) for caches, heartbeats and open-symbol lists, and the **corridor** for the large datasets. Registry writes are last-write-wins per data type. Either bot operates normally solo — nothing is handed over and all ladder checks fall through to normal fetches.

Each bot publishes its own open-symbol list to this registry on every position open/close, and once more per heartbeat as a safety net for close paths that bypass `pseudoClosePosition` (e.g. the gap-fill audit). A following bot (`lfFollowPartner` on, partner heartbeat fresh) checks the leader's list before opening and skips any ticker the leader already holds; the leader never checks its own publish. Since the check only runs while `_lfIsFollowing()` is true, it switches itself off the instant the leader's heartbeat goes stale, with no separate expiry logic on the position data.

Not every `BroadcastChannel('ew_shared')` message carries a `localStorage.__ew_shared_v1` write behind it, though most do (`_sharedWrite`/`_sharedMerge` post a change notification after writing). `registerSharedMessageHook` is the general subscription point either kind of push is dispatched through on the receiving end.

### The Corridor

The corridor is a handover lane, not storage. It carries `bulkTickers`, `ocResults`, `sampleScore`, `fcGrade`, `liqLean`, `ilq` and `stb`. The publisher cuts a dataset's JSON into packets of up to 40,000 characters and keeps only a short window of them in localStorage: at most 4 packets at once across all datasets, so a 650 KB bulk ticker list never holds more than about 160 KB of the lane. The partner copies each packet into memory and confirms it in `__ew_xa_<type>_<bot>` (a cumulative count). The publisher deletes every confirmed packet, releases the next ones, and deletes the manifest after the last, so the lane is empty between handovers.

The receiver reassembles in memory, checks the length and checksum, and exposes the result through `_sharedRead`, which returns only what the partner handed over; a bot never reads its own publication, and `_sharedPubTs(type)` gives the timestamp the partner will file it under. The consumers then overwrite their own stored data from it. The delivered copy is memory-only, so a bot that reloads has nothing until the partner's next publish.

- **Pacing**: packets are confirmed in order. Pumping is triggered by the browser's `storage` events, a 1 s timer and each heartbeat.
- **Resend**: a receiver that reloads mid-handover, or whose reassembly fails its checksum, asks for a restart and the publisher resends from packet 0 (at most 3 restarts).
- **Abandon**: no confirmation for 120 s, or no room in localStorage for a packet, abandons that handover and logs `[SHR] ⚠` once per 30 minutes per dataset. A newer publish of the same dataset supersedes an unfinished one.
- **Partner offline**: nothing is sent while the partner's heartbeat is stale, and the ledger records it as skipped.
- **Cleanup**: at init each bot removes its own leftover lane keys, the dedicated keys from an earlier build (`__ew_sh_*`) and any legacy copy of a corridor dataset still in the registry.

### Scan Scheduler Internals

- **Stages**: `runScan` calls `_scanPipeline(ctx)`, which runs the host's `tickers` stage, then each plugin stage in load order (`sw-post`, then `mic-prep`, `mic-fetch`, `mic-pool`, `mic-entry`). Stages share `ctx`; a plugin appends `{ id, group, run }` to `_scanStageDefs` in `transform`, and a stage returning `false` skips the rest of its group. On a host without `_scanStageDefs` the plugin falls back to wrapping `runScan`.
- **Checkpoints**: loops call `if (this._scanDue()) await this._scanCp()`, which yields once `schedSliceMs` has elapsed (40 ms while the tab is hidden). The yield is a `MessageChannel` task rather than `setTimeout`, because a hidden tab clamps timers to 1 s or more.
- **Idle lane**: `_schIdle(key, fn)` queues one coalesced job per key (extremity rebuild, sample-store saves), flushed when the pipeline ends; `_schIdleCancel(key)` drops it.
- **Config edits while running**: the lock no longer forces itself on while the bot runs. Config is still read live, so a toggle flipped mid-scan can apply to the rest of that scan; only the scan interval is frozen per cycle (`_scanTotalMs`, set at the start of `runScheduledCycle` and read by both the scheduler tick and the catch-up check), so editing Scan Interval never triggers an immediate scan.
- **Timing**: each scan logs one `[SCH]` line with total ms, yields, long-task count and per-stage ms. `ui.scanning` stays on through the plugin stages, so a batch that outlasts the scan interval makes the next scan skip. The extremity rebuild itself is still one synchronous call.
- Every background or bulk fetch (bulk tickers, market watch, and any loaded plugin's kline and sample batches) runs through a single per-bot scheduling queue (**Scan Scheduling** in Main Config) instead of firing all at once. This keeps the browser responsive with one bot open and workable with two. Execution-critical single-symbol calls (opening, closing and watching a position) bypass the queue so order execution is never delayed behind background scanning. The scan itself is a pipeline of named stages that hands control back to the browser after each time slice (**Slice Budget**), so position watching, clicks and timers run mid-scan instead of waiting for it to finish.
- **Running both bots**: When both are open simultaneously they automatically share bulk ticker fetches, kline caches, and sample batches to halve API load. Either bot works normally on its own when the other tab isn't open.

### Live-Mode Internals

- **The tab buttons always work**: every control from **Order type** down is locked while Config Lock is on (it locks automatically while the bot runs). Settings are saved in the bot's config, so they persist and travel with Export / Import. Keys use the `ew` prefix on EverWinter and `sc` on SunChaser.
- **Balance**: fetched automatically the moment a valid key/secret pair is saved in the credentials panel, not only at page load.
- **Symbol banning**: a symbol is banned for a week when Bybit reports it can't be traded, or when it's blocked until a trading agreement is signed (for example some leveraged or inverse instruments). Both cases need a manual fix on Bybit's side, so the ban is treated as long-term instead of retrying every cycle.
- **Post-bail re-check**: after a bail sweep (manual Danger Zone bail or an automatic Drawdown Throttle bail), the plugin queries the exchange directly for any position still open in its own direction (Sell for EverWinter, Buy for SunChaser) and force-flattens it with a reduce-only close that follows the **Close** tab settings (see below). This catches positions that failed to fully fill.
- **Exchange sync cadence** : the full-book `GET /v5/position/list` sync runs once before and once after each scan loop, and nowhere else. It no longer fires after an SL/TP close, so exchange-native TP/SL fills and DCA fills are picked up at the next scan boundary, at most one Scan Interval later. Entries and closes still confirm their own fills with single-symbol `position/list` calls while they are in flight.
- **Concurrent group closes** : a live close doesn't return until the position is flat, because `_scLimitClose`/`_ewLimitClose` reprice and retry against the exchange (poll 2 s, reprice every **Reprice interval**), so a sequential loop stacked those waits per position. Every multi-position close path now runs its closes under `Promise.all`: `bailAll` (host), Cascade, Sacrifice and Ejection (`_micCheckCascade`, `micCheckSacrifice`, `micEject`). Each close is isolated in its own try/catch, so one failed close no longer aborts the rest of the group. Signed requests from the in-flight closes still queue through `_scDelay`/`_ewDelay` (250 ms apart), so they interleave instead of bursting. Per-position state stays safe through the `_scClosing`/`_ewClosing` guard and the host's `_closingIds` set, which make a second close of the same position a no-op.
- **Close-record lookup** (Still-Water): the `pseudoClosePosition` wrapper finds the trade it just closed by position id (`closedTrades.find(x => x.id === pos.id)`, skipped if the record already existed before the call) rather than reading `closedTrades[0]`. With concurrent closes another position's record can be inserted while this one is still awaiting, so index 0 and list-length growth no longer identify the right trade. The record feeds the MI direction-awareness feedback.
- **Cycle re-entry guard** : each close schedules a `runScheduledCycle` about 500 ms after it finishes. The host guards the scan itself with `_cycleRunning`, but not the plugin's pre- and post-scan `position/list` syncs, so N concurrent closes would have run N syncs. The plugin's `runScheduledCycle` wrapper now returns immediately while a cycle or an earlier wrapper call (`_cycleWrapBusy`) is in progress.
- **Pre-entry check**: before each entry the plugin asks the exchange for that one symbol and skips the entry if any position is already open on it, so a new order is never stacked on a position the bot isn't tracking.
- **DCA repair**: re-places missing DCA conditional orders, and runs only in the post-scan sync. It is skipped in binary mode, for positions with no DCA orders, and for positions opened in the last 2 minutes, because order status can lag a fresh placement and would trigger a duplicate.
- **Live retry log lines** : the `[EW]`/`[SC]` close and entry retry messages are logged with `live = true` (see Activity Log). Cascade, Sacrifice and Bail wrap their concurrent closes in a log batch, which used to hold every non-error line until the last close succeeded, so a close stuck in its reprice loop looked frozen.
- **Mark price ownership** : the pseudo watcher is the only writer of a live position's `markPrice` (last price). `_ewSyncPositions`/`_scSyncPositions` previously overwrote it on every sync with the exchange row's `markPrice`, falling back to `avgPrice`, so displayed prices jumped toward entry at each pre- and post-scan sync and snapped back on the next watcher tick. The sync now sets `markPrice` only when the position has none yet.
- **Live position prices**: the base bot's watcher skips live positions, so the plugin prices them itself. It reads the host's WebSocket ticker when the host has one for the symbol; otherwise it makes one REST ticker call per symbol on a throttle: the **Price Poll Interval** base (default 5 s), doubling while price moves less than 0.1% and capped at 60 s. This replaces a REST call per position on every 5 s tick.

### Plugin Transform Pipeline

``
pw()  →  plugin[0].transform(def)  →  plugin[1].transform(def)  →  ...  →  Alpine
``

Each plugin's `transform(def)` receives and returns the component definition, so load order matters for method wrapping. Strategy plugins must declare `after: ['everwinter']` / `after: ['sunchaser']` so the live-trading plugin's wraps are innermost, which means live-trading plugins (EverWinter, SunChaser) must load before strategy plugins (Still-Water, then MultiIndicator). The Plugin Manager shows the current load order and warns about conflicts.

### Bybit API Endpoints Used

**Public**: `GET /v5/market/tickers` (bulk for the symbol universe, per symbol for criteria data), `GET /v5/market/recent-trade`, `GET /v5/market/kline` (hourly bars on the bots, 5-minute bars on Still-Water, plus 1-hour bars for their Indicator Forecast), `GET /v5/market/account-ratio` (long/short account ratio, Still-Water only), `GET /v5/market/open-interest` and `GET /v5/market/funding/history` (Still-Water Indicator Forecast only), `GET /v5/market/instruments-info`. **WebSocket**: `wss://stream.bybit.com/v5/public/linear` (position price stream). **Signed (live mode)**: `GET /v5/account/wallet-balance`, `GET /v5/position/list`, `GET /v5/position/closed-pnl`, `GET /v5/order/realtime`, `POST /v5/order/create`, `POST /v5/position/trading-stop`, `POST /v5/order/cancel`, plus `GET /v5/execution/list` on the Psycho bots (DCA/AMa ladder fill checks). Signing: HMAC-SHA-256 via `crypto.subtle.sign`; 250ms minimum gap between signed requests (plugins).

**Call cadence**: the full-book `position/list` runs only before and after each scan loop. Single-symbol `position/list` calls happen around an entry (once before it, then polling for the fill) and while a close is repricing. On the Psycho bots, `execution/list` is called for a pending DCA/AMa stage only once price has reached that stage's trigger, plus one sweep of every pending stage after each scan loop to catch a wick through a trigger.
