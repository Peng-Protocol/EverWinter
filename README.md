# ❄️ EVERWINTER

**EverWinter** is a browser-based trading suite for Bybit USDT Perpetuals executing the **Winter-Chaser** strategy. See the [Strategy Guide](StrategyBook.md) for trading logic and rationale.

## Setup

Open any `.html` file directly in a browser. No build step, no server, no installation. Alpine.js and Bootstrap 5 are loaded from CDN — an internet connection is required on first load (cached after that).

To trade proactively, run `PseudoChaser` (longs only) with `MultiIndicator` and `Ashfall` loaded, or `PseudoWinter` (shorts only) with `MultiIndicator` and `Permafrost` loaded. To trade reactively, run `PsychoChaser` (longs only) or `PsychoWinter` (shorts only) on their own.

The Strategy Book explains how the Reactive and Proactive approaches differ, and the Psycho Handbook covers the Reactive bots' configs in depth.

## Menus

The UI has four views: **Market** (positions, scan controls, watchlist) plus three configuration/telemetry panels — **Config**, **Stats**, and **Trades**.

**Mobile** (≤768px): a bottom tab bar (⚙ Config · 📊 Market · 📈 Stats · 📌 Trades) switches between the four views full-screen, one at a time. Unchanged from earlier builds.

**Desktop**: Market, Config, Stats and Trades all sit side by side in normal document flow at the same level — no overlay, no dimming, no shadow. Config/Stats/Trades open via matching icon buttons (⚙ 📈 📌) in the topbar — no dedicated Market button, since it's never hidden. Config opens by default on launch; click its icon again (or any open panel's icon) to dismiss it.

Market is always twice as wide as one side panel. With both side panels open the split is Market 2/4, left panel 1/4, right panel 1/4; with one panel open it's roughly 2:1; with none, Market fills the row. Panels take slots in the order they're opened, not by which menu they are:
- First panel opened → left slot. Second → right slot.
- Once both slots are full, opening a third (currently-closed) panel replaces the **left** slot's occupant.
- Opening a fourth replaces the **right** slot's occupant — and it keeps alternating left/right on every subsequent replacement from there.

Two panels can be open at once; a third click always bumps whichever slot is due next rather than stacking a third panel.

## Plugins

To load a plugin, open the **Plugin Manager** panel at the bottom of the config menu, click **Load Plugin**, and select the `.html` file. **A page reload is required after loading or removing any plugin** — the plugin pipeline runs once at page boot, so changes don't take effect until the next load. Plugin sources are stored in IndexedDB rather than localStorage, so they no longer use up the localStorage quota; the plugin config row in Storage usage shrinks to a small manifest on the second load after a plugin file is loaded. ## EverWinter / SunChaser (Live Trading Plugins)

EverWinter turns PseudoWinter into a live short-only Bybit bot; SunChaser does the same for PseudoChaser as long-only. Both sign requests with the stored `__ew_creds`/`__sc_creds` API key and place real orders — the topbar reads **Very Real Orders** once loaded, in place of the base simulation's **No Real Orders**.

### Order Handling (Open / Close tabs)

The plugin's accordion has three tabs: **API** (credentials), **Open** and **Close**. 

**Limit** here means a limit priced through the last price by the **Limit offset** (default 0.1%), so it normally fills like a taker; a negative offset makes it passive. **Market** sends a market order (IOC for entries, reduce-only IOC for closes). A **try** is one limit order, cancelled and repriced off a fresh last price if it doesn't fill. ([more](#general-details))

**Open and Close tabs** (the Close tab applies to every bot-initiated close: manual, runtime, cascade/sacrifice, bail sweeps and the post-bail re-check; exchange-native TP/SL closes are filled by the exchange and aren't affected)

| Setting | Open tab | Close tab |
|---|---|---|
| **Order type** (`ewOpenType`/`scOpenType`, `…CloseType`; default Limit) | Limit or Market entry. | Limit or Market (reduce-only) close. |
| **Limit offset** (`…OpenOffsetPct`/`…CloseOffsetPct`, default 0.1) | Distance through last price, in %. | Same. |
| **Limit tries** (`…OpenTries`/`…CloseTries`) | Default **1** (1–20): limit attempts before the fallback, or giving up. | Default **10** (1–100): reduce-only limit attempts before the fallback. |
| **Fall back to market** (`…OpenFallback`/`…CloseFallback`, default **on**) | After the limit tries go unfilled, send one market order. Off: give up and put the symbol on cooldown. | After the limit tries go unfilled, close with a reduce-only market order, repeated until flat. Off: keeps repricing the limit until the position is flat; a close never gives up. |
| **Fill timeout per try** (`…FillTimeoutMs`, default 10 s) | How long each limit try waits for a fill before it's cancelled. | n/a |
| **Cooldown after failed open** (`…FillCooldownMs`, default 15 min) | How long a symbol is skipped after an entry that placed an order but never filled. A rejected order doesn't trigger it. | n/a |
| **Reprice interval** (`…CloseRetryMs`, default 10 s) | n/a | Time between close tries. After the fallback, market closes repeat at most every 4 s. |

With the defaults, an entry that doesn't fill on its first limit goes to market, and a close that hasn't filled after ten limit tries (about 100 s) goes to market.

## Main Config

Changes take effect immediately and are persisted to localStorage automatically.

| Setting | What it does |
|---|---|
| **Scan Interval** (`scanMins`) | How often (minutes) the bot runs a full market scan. Controls both entry frequency and the scan bar in the UI. |
| **Max Positions** (`maxPos`) | Maximum simultaneously open positions. No new entries open once this is reached. |
| **Leverage** (`leverage`) | Position leverage. Affects order size, TP/SL prices, and EDa thresholds. |
| **Min Notional** (`minNotional`) | Base margin per position in USDT. Actual order size = minNotional × leverage. |
| **Entry TP** (`entryTpRoi`, default 50%) | Take-profit ROI % target. When EDa is active this is the buffered target — the debt-free close happens at a lower percentage. In DCA Mode this is also the base the per-stage TP ladder scales down from (entry TP ÷ (stage+1), min 3%). |
| **Binary Mode** (`binaryModeEnabled`) | On: every position gets a take-profit and a stop-loss at entry and no DCA adds (`binaryTpPct`/`binarySlPct`, both default 50%). Off: multi-stage DCA. Add orders trigger below entry (PseudoChaser) or above it (PseudoWinter), each with a lower TP ROI target, and the stop-loss (`dcaSlPct`, default 16%) only arms once every first-wind DCA stage has filled. The DCA config controls need the `dca-long`/`dca-short` plugin (`plugins/modes/`); the binary and DCA logic itself is in the base bot either way. |
| **DCA Stages** (`dcaStages`, default 1) | Number of DCA add orders (1–6 in the plugin slider). Each stage has its own trigger slider (`dcaAddPct1`…`dcaAddPct6`, defaults 3 / 6 / 12 / 18 / 24 / 30), set as % below entry for PseudoChaser or above entry for PseudoWinter, and only the sliders for selected stages appear. Triggers always increase by stage: lowering one stops at the previous stage's trigger, and raising one pushes the later stages up. Configs saved before per-stage triggers (a fixed 1.5%, then +3% per stage for non-3 stage counts) are migrated on load/import so they keep the same trigger prices. |
| **DCA Add Notional** (`addNotional`) | Margin (USDT) added per DCA stage — separate from **Min Notional**, which only sizes the initial entry. |
| **Drawdown Throttle** (`drawdownThrottleEnabled`) | Halts new entries for `drawdownHaltHours` (default 12h, free-entry field with no upper bound) when the rolling 6h realized PnL falls below a loss threshold. The Halt tab shows the live 6h rolling PnL. Its **Clear 6hr Record** button (with confirmation) zeroes that window manually, whether or not a halt is active. |
| **Drawdown Factor** (`drawdownThrottleFactor`) | Loss threshold as a multiple of entry margin. At 0.5× with $1 margin, $0.50 of rolling losses triggers the halt. |
| **Bail on Trigger** (`drawdownBailEnabled`, default on) | When on, triggering the Drawdown Throttle halt also immediately closes every open position at market (`bailAll()`) — the same sweep the Danger Zone's manual **Bail All Positions** button runs, and what the **BAIL** trade-card badge marks. |
| **Gains Lock** (`gainsLockEnabled`) | Halts new entries for 12 hours once rolling 6h profit hits a target. Banks a winning streak before it reverses. Same 6h rolling PnL readout and **Clear 6hr Record** button as Drawdown Throttle, shown in its own section of the Halt tab. |
| **Gains Factor** (`gainsLockFactor`) | Profit target as a multiple of entry margin. Same scale as Drawdown Factor. |
| **Manual Halt** | Button (Halt tab) that blocks all new position entry indefinitely until manually lifted. Independent of Drawdown Throttle and Gains Lock — overrides both and doesn't stack with either. |
| **EDa / Laggard Check** (`laggardCheckEnabled`) | Enables the Effective Debt Adjusted system. Realized losses are passed forward to surviving positions, which take higher TP targets to recover the debt. **Requires the EDa-Winter / EDa-Chaser plugin** (`plugins/modes/`). |
| **TP Buffer** (`laggardProfitOffset`) | Extra TP headroom reserved above the functional target (%). The debt-free close happens at `tpPct ÷ (1 + buffer/100)` — at 50% buffer with an 18% TP slider, trades close at 12% without debt. Requires the EDa plugin. |
| **Ticker Cooldown** (`bulkTickerCooldownHours`) | How long the bot reuses a cached bulk ticker fetch before hitting the API again (default 12h). The bulk list only says which symbols exist — criteria data never reads it — and the same window sets how long MIW/MIC's re-entry block and the Ticker Graylist hold a closed symbol. |
| **Whiplash Audit** (`whiplashEnabled`) | When on, the position watcher fetches 1-minute klines near TP and near SL to confirm whether price spiked through either between watcher cycles. The SL audit (PseudoWinter 1.6.8 / PseudoChaser 1.6.9) uses the same proximity rule and 5-minute delay as the TP audit, with its own `_whiplashSlScheduled` flag, and closes at the SL price if a candle high (Winter) or low (Chaser) reached it. It aborts if the SL moved or cleared before the check ran. |
| **Whiplash Proximity** (`whiplashProximityPct`) | How close (%) to the TP or SL price triggers the kline audit. One setting drives both. |
| **Runtime Limit** (`runtimeHours`) | Maximum position age. Forces a close at the deadline if TP hasn't been hit. |
| **Symbol Banlist** (`banlistEnabled`) | When on, symbols on the ban list are excluded from all scans. Entries expire after 7 days. |
| **Position Price Feed** (`restPollEnabled`) | When on, replaces the WebSocket price stream for open positions with periodic REST calls; use it if the WS feed returns stale prices. Exactly one source runs at a time. Pseudo bots default to on and Psycho bots to off. ([more](#general-details)) |
| **Price Poll Interval** (`restPollBaseSec`) | Base polling interval in seconds for REST mode. The interval doubles automatically when price moves less than 0.1% between ticks and resets to base on any meaningful move. |
| **Dispatch Every** (`schedIntervalMs`) | Minimum gap (ms, default 150) between successive background fetches dispatched from the scheduling queue. Lower = faster background data turnover, at the cost of more simultaneous requests. |
| **Max Concurrent** (`schedMaxConcurrent`) | Hard cap (default 4) on background fetches in flight at once, regardless of how many subsystems have work queued. |
| **Slice Budget** (`schedSliceMs`) | How long (ms, default 8, 2–30) a scan stage runs before handing the browser back; a hidden tab uses 40 ms. Lower = smoother page, slightly slower scans. |
| **Follow Partner Bot** (`lfFollowPartner`) | When on, this bot stops fetching bulk tickers itself and uses the bulk list the partner hands over. The partner needs no toggle: it acts as leader while its heartbeat is fresh (newer than 2× **Scan Interval**), and this bot resumes scanning on its own if it goes stale. It also won't open a position on a ticker the leader already holds; Permafrost/Ashfall ignore this setting and always sample independently. ([more](#general-details)) |
| **Config Lock** (`cfgLocked`) | Locks all config controls to prevent accidental changes; it engages automatically while the bot is running. On EverWinter/SunChaser it also locks the Open and Close tab controls (the tabs themselves stay navigable). |

## Stats Menu

The stats panel shows session-level metrics since the page was last loaded or state was cleared.

| Stat | Meaning |
|---|---|
| **Session PnL** | Cumulative realized PnL from all closed trades this session. |
| **Win / Loss** | Count of profitable vs. losing closed trades. |
| **Win Skew** | Share of total PnL magnitude (all closed trades, cumulative) that came from wins — sum of winning PnL ÷ (sum of winning PnL + sum of losing PnL). Weighted by trade size, not just a count of wins vs. losses. |
| **Avg PnL** | Mean realized PnL per closed trade. |
| **Open uPnL** | Unrealized PnL across all currently open positions. |
| **Positions** | Count of open positions. |
| **Last Scan** | Timestamp of the most recent scan cycle. |
| **Laggard** | The oldest open position — the EDa debt holder. Shows its current debt load when EDa is active. |
| **Persistence** | "Active" (live in-memory position count) vs. "Stored" (confirmed saved to localStorage). These should always match. |

**Persistence mismatch**: shown in red with a warning banner. It means a save failed or was overwritten, and usually clears on its own within a few seconds as the bot retries automatically. If it doesn't:
- Check the activity log for `[PST]`/`[PERSIST]` entries.
- Close any duplicate tabs of the same bot — a second tab can overwrite the first tab's saves with its own stale position count.

**Storage usage** (dropdown below Persistence, PseudoWinter/PseudoChaser only): breaks this bot's localStorage footprint down to one row per data type, including genuinely shared cross-bot keys but never the partner's private state. Oversized rows show in red with a **✕** to clear that bucket (with confirmation), and **Export** downloads the breakdown as a text file. The cross-bot corridor shows as one row of in-flight packets (normally empty), and plugin sources show as an IndexedDB row that sits outside the localStorage quota and isn't part of the total.

**Power usage** (dropdown below Storage usage): a rolling average and peak of how many milliseconds the app spends reacting each second. A rising figure usually means a plugin panel left open somewhere is doing more work than it needs to — closing analytics panels you're not actively watching brings it back down.

**Ticker Graylist**: when MultiIndicator is enabled, the Stats menu shows a Ticker Graylist section listing symbols currently blocked from re-entry. It's empty when nothing is blocked. Each listed symbol clears itself automatically once the bulk ticker cooldown window elapses — no manual action needed.

### Actions Dropdown

- **Export** — Downloads current bot state (config, positions, closed trades, ban list, EDa state) as a `.json` file. Plugins with their own data (Permafrost/Ashfall scorer data) have their own Export in the Danger Zone of their accordions (see **Export & Import** under Permafrost / Ashfall Plugin) — the Stats menu Export covers the base bot state only.
- **Import** — Restores state from a previously exported `.json` file: config fields merge field by field and positions are replaced wholesale. A 5s debounce prevents accidental double-imports, and config keys that no longer belong to a loaded feature are dropped. ([more](#general-details))
- **Clear Closed Trades** — Wipes the closed trades list, resets session stats, and clears the 6hr drawdown/gains-lock rolling PnL windows. Open positions are unaffected.
- **Clear All** — Full reset. All positions, trades, stats, and config are wiped (config reverts to defaults).

### Activity Log

Timestamped entries for every significant bot event. Color coding:

- **White** — informational (scan results, entries, closes)
- **Yellow** — warnings (halts engaged, API retries)
- **Red** — errors (API failures, plugin conflicts)

Common prefixes: `[MHL]` manual halt · `[DWN]` drawdown throttle · `[GLK]` gains lock · `[PST]` (PseudoWinter) / `[PERSIST]` (PseudoChaser) save failures or recovered positions · `[PFR]`/`[ASH]` climate plugin events · `[MIW]`/`[MIC]` multi-indicator events · `[SHR]` cross-bot corridor handovers and failed shares.

Bulk operations (Cascade, Sacrifice, Bail, scan entry bursts) are rolled up: `_logBatchBegin()` / `_logBatchEnd(label)` buffer per-event messages into one entry. Errors always log immediately. `log(m, type, live)` takes an optional third argument; `live = true` bypasses the buffer, so live close/entry retry lines (repricing, market fallback, per-try failures, fill timeout) show as they happen instead of after the whole roll-up finishes.

The log keeps the latest 300 entries in memory and in localStorage, dropping the oldest first. Each entry has a local `HH:MM:SS` string (`t`), which is what the UI shows, and an epoch-millisecond timestamp (`ts`). `ts` lets you match a log export to position and config exports, which are timestamped in UTC epoch; `t` alone can't be tied to a date or time zone.

## Trades Menu

The trades panel shows a card for each closed trade, newest first, with a close-reason badge: **TP**, **SL**, **FORCE** (runtime limit), **BAIL** (drawdown throttle bail), **Sub** (Substitution) or **Eject** (Ejection). Reasons added by other plugins show their own label. The simulation bots also show estimated fees on each card, and Net PnL, win/loss and the drawdown and gains windows are net of them. ([more](#general-details))

**Roll-up card**: when the closed trades list exceeds 50 entries, the oldest are compacted into a single roll-up card showing their net PnL, trade count, and the date range they cover. The roll-up is not a trade — it is a historical summary. In the PnL chart, the roll-up's net value acts as a baseline offset applied to every plotted point.

**PnL chart**: click the **PNL CHART** bar below the header to expand a cumulative PnL line chart, green when the net result is positive and red when negative. It only appears once at least 2 individual trades are closed. ([more](#general-details))

**CLEAR button**: removes all closed trades, resets session stats, and clears the 6hr drawdown/gains-lock rolling PnL windows. It asks for an inline confirmation ("Sure? Yes / No") before anything is deleted. ([more](#general-details))

## MultiIndicator Plugin (MIW / MIC)

The Multi-Indicator plugin filters entries with combinations of criteria called **slots**: a slot is an AND-gate, and a ticker only needs to match one slot to be eligible. No criterion is mandatory, and a slot (Auto or manual) can use any combination of `fund`, `va`, `iol`, `ios`, `lta` and `lpa`. Entry is scan-driven only: one pass per fresh sample batch. ([more](#multiindicator-details))

### Criteria

See StrategyBook's **Market Reading** section for what each criterion means and when to use it. This section covers tiering, recording, and fetch mechanics only.

**Slot builder badge key**: the manual slot builder uses the same emoji set as position/trade badges.

| Badge | Criterion |
|---|---|
| 🤑/💸 | Funding tier (direction-aware, see [Trivia](#trivia)). |
| 🔊 | V/A, volume versus the population sample-window average. |
| 🐂 | IO/L, the long share of the ticker's open interest versus the population sample-window average of that share. |
| 🐻 | IO/S, the same for the short share. |
| 🕐 | LTA, last completed hour's turnover versus the ticker's own average hour. |
| 💹 | LPA, last completed hour's price change versus every other ticker in the sample window. |

**IO/L and IO/S**: a ticker's long share of open interest is its open interest × the long share of accounts from Bybit's long/short ratio, and its short share is the remainder. The tier is `floor(100 × ln(share ÷ window average) ÷ step)`, so `iol+12` is 12 tiers more long open interest than the sampled population averages. Each needs the ticker's long share and a window average, so it has no tier until the sample window holds readings. ([more](#multiindicator-details))

**Recording**: every criterion is recorded as a signed tier on the position at entry.

### Config

| Setting | What it does |
|---|---|
| **Enabled** (`miwEnabled`/`micEnabled`) | Master on/off. When off, the plugin opens no entries and runs no exits. |
| **Picks** (`miwPicks`/`micPicks`) | Max new entries per scan cycle (1–10). |
| **Share Cap** (`miwShareCapEnabled`/`micShareCapEnabled`) | Limits plugin entries to a percentage of `maxPos`. Prevents MIW/MIC from filling all position slots. |
| **Share Cap %** (`miwShareCapPct`/`micShareCapPct`) | The cap percentage. At 50% with maxPos=6, MIW/MIC can hold at most 3 positions. |
| **Tier Step Sizes** (`miwFundStep`/`miwVaStep`/`miwIolStep`/`miwIosStep`/`miwLtaStep`/`miwLpaStep` and `mic` equivalents) | Read-only chips on the **Fetch** tab showing the tier step for each criterion. Defaults: `va` 1% deviation from the population average; `iol` and `ios` 1% (log) deviation of the long / short open-interest share from its window average; `lta` 10% deviation from the ticker's own hourly average; `lpa` 0.25 absolute points of 1h price change (shown as `pp`); `fund` 0.0025% of funding rate per tier, so 0.25% is tier 100. They can't be edited from the UI; change them via config import. Older installs saved the fund step as 0.25; it's migrated once, and saved `fund>N`/`fund<N` slot gates are rescaled ×100 so each keeps its threshold. |
| **Cascade** (`miwCascadeEnabled`/`micCascadeEnabled`) | Closes every open position, whichever strategy opened it, when their collective unrealized profit reaches a threshold, banking a group move before it reverses. The position watcher checks this every 5s while the bot runs, not just once per scan, so a threshold crossed and reversed between scans is still caught. The closes are sent concurrently, not one after another. |
| **Cascade %** (`miwCascadePct`/`micCascadePct`) | Collective uPnL trigger as a % of base margin (minNotional ÷ leverage). While **Relative Target** is on the slider is hidden and unused: Cascade fires at the resolved entry TP. |
| **Sacrifice** (`miwSacrificeEnabled`/`micSacrificeEnabled`) | Closes every open position, whichever strategy opened it, when their collective unrealized loss reaches a threshold, capping group drawdown. It uses the same continuous position-watcher check as Cascade, and closes concurrently the same way. |
| **Sacrifice %** (`miwSacrificePct`/`micSacrificePct`) | Collective uLoss trigger as a % of base margin (minNotional ÷ leverage). While **Relative Target** is on the slider is hidden and unused: Sacrifice fires at the resolved SL. |
| **Relative Target** (`miwRelativeTargetEnabled`/`micRelativeTargetEnabled`, default on) | Sub-toggle on the **Exit** tab, shown only while Cascade or Sacrifice is on. It sets each new position's entry TP and SL from what the market is actually paying: the LPA sample window's average move in the bot's favor × leverage is the entry TP, and the average move against it × leverage is the SL. **Cascade** is the entry TP and **Sacrifice** is the SL, so all four agree, and the **Targets Gauge** shows the live averages and resolved targets. ([more](#multiindicator-details)) |
| **Window** (`miwRelBatches`/`micRelBatches`, default **6**, 1–25) | Shown only while Relative Target is on. How many of the latest sample batches the average moves are taken from; older batches are ignored so stale readings don't dilute them. Within those batches each ticker counts once, by its latest reading. A short window reacts faster, so targets and deferment swing more from batch to batch; 25 is the most batches the sample history keeps. |
| **Min Entry TP** (`miwMinEntryTp`/`micMinEntryTp`, default **6**) | Shown only while Relative Target is on: the ROI % below which a position can't cover its entry and exit fees. If the resolved entry TP falls under it, the market isn't paying enough and new entries are deferred (at 6× leverage the window's average favorable 1h move must be at least 1%). Cascade and Sacrifice never fire below it, and the SL is floored at 1%. ([more](#multiindicator-details)) |
| **Targets Gauge** (no toggle) | Two-sided readout below the Entry/Exit/Fetch tab zones, visible whenever the plugin is enabled: SL and Sacrifice on the left, TP and Cascade on the right, with bars for TP and SL and text for the other two. Every value is green at or above Min Entry TP and red below it. The caption shows the window averages, and the gauge greys out with a note while Relative Target waits for 3+ readings on each side of zero. ([more](#multiindicator-details)) |
| **Substitution** (`miwSubstitutionEnabled`/`micSubstitutionEnabled`) | When no entry slot is free (maxPos or Share Cap reached), closes the worst-scoring held position (any strategy's, not only MIW/MIC's) and opens the best fresh candidate in its place, but only if the candidate's collapsed score beats the held position's *current* score by the **Substitution Margin**. A held MIW/MIC position's current score (`_miwLiveCompositeScore`/`_micLiveCompositeScore`) is recomputed live from its rolling-average criteria (see **Position Rolling Average**), so it's judged on where it has drifted to, not where it stood at entry. Each candidate is pre-flighted through the Force-Evaluate top-up and entry vetoes before anything is closed, and a blocked one falls through to the next. It requires Co-Qualifying Penalty (Permafrost/Ashfall); without it every score is 0 and Substitution never fires. |
| **Substitution Margin** (`miwSubstitutionMarginPct`/`micSubstitutionMarginPct`) | How much better the new candidate must score than the worst held position, as a % of base margin (minNotional ÷ leverage), before a swap happens. Prevents swapping on marginal score differences. |
| **Substitution Min Age** (`miwSubstitutionMinAgeMins`/`micSubstitutionMinAgeMins`, default 35) | Minimum minutes a position must be held before it becomes eligible to be substituted out. |
| **Deferment** (`miwDefermentEnabled`/`micDefermentEnabled`, default on) | A regime-proxy entry stop, set on the **Exit** tab below Substitution. It blocks every new entry while the Sample Scorer headline is below zero (the favored side's mean raw 1h move in the bot's favor), or while a clause is in effect: **Both Poles Red** or the **Relative Target** floor. The headline test needs Sample Scoring; the floor needs only the LPA window. Two or more active paths trigger Ejection (see **Deferment & Ejection** below). |
| **Both Poles Red** (`miwDeferBothRedEnabled`/`micDeferBothRedEnabled`, default off) | Sub-toggle, only shown while Deferment is on. Defers while any criterion has both its `+` and `-` pole in the red on the scorecard side the chart shows — no good pole left to enter on. A pole under Min Samples doesn't count. Counts as one path toward Ejection. |
| **Re-entry Block Mode** (`miwReentryBlockMode`/`micReentryBlockMode`) | Defaults to **Losers Only**, which lets a symbol that just closed in profit re-trigger immediately and blocks only a symbol that closed at a loss. **Winners + Losers** blocks a symbol from re-triggering for one bulk-ticker cooldown window (12h by default) after any close, win or loss. |
| **Auto Slots** (`miwAutoSlots`/`micAutoSlots`) | Replaces the manual slot list with a minimum-gate qualifier: a ticker qualifies once it satisfies at least **Minimum Criteria per Slot** non-excluded criteria — not a fixed-size combination. Every criterion the ticker actually satisfies is captured and scored, not just enough to clear the floor. See `_miwAutoQualify`/`_micAutoQualify`. |
| **Minimum Criteria per Slot** (`miwAutoSlotSize`/`micAutoSlotSize`) | The floor (1–6). At 1, a single true criterion qualifies the ticker — any others it happens to satisfy are still captured and scored. |
| **Exclude from Auto** (`miwAutoSlotExclude`/`micAutoSlotExclude`) | Criteria omitted from Auto's qualifying set entirely — never checked, never counted toward the minimum, never scored. Excluding more than `6 − Minimum Criteria per Slot` leaves Auto unable to ever reach its floor, and the plugin reports no active entry gate (`_miwAutoActive`/`_micAutoActive`). |
| **Force-Evaluate General Criteria** (`miwForceGeneralCriteria`/`micForceGeneralCriteria`, on by default) | Auto mode only. When on, just before a ticker opens, the plugin re-checks `fund`, `iol`/`ios` and `lta`/`lpa` with a forced per-symbol fetch, since the cycle's capped sample may not have reached it yet, and adds any that are newly true. ### Slots UI

**Manual mode**: click a slot to select it, then toggle criteria on/off in the picker row below. ✕ deletes the slot; `+` adds a new empty one. All six criteria are tiered — clicking one opens its gate picker (direction plus tier) rather than toggling a bare tag. A slot with no criteria in it never matches.

**Auto mode**: replaces the manual builder with a minimum-slider and an exclusion chip row. A ticker qualifies on at least the chosen minimum of non-excluded criteria — every criterion actually true is scored, not just enough to clear the floor. The hint under the slider states the current floor as "qualifies on any N of M secondary criteria."

The six criteria are independent signed tiers, so any subset can be true for the same ticker at once and each contributes to the qualifying count on its own.

### Partner Feed

The Cross tab shows a scrollable **Partner Feed** listing the last 20 events the partner bot has broadcast: cascade/sacrifice triggers, DDH start/lift, gains-lock start/lift, and GC steps. Each row shows a kind-specific detail — position count and collective PnL for cascade/sacrifice, PnL and step number for GC, symbol for a rolling sacrifice — and a UTC timestamp, date-prefixed for anything not from today. Useful for diagnosing Mutual DDH Lift and GC: if the feed shows a partner `ddh-start` or `gc` step but no lift follows on this bot, the problem is on the receive side (freshness window, own-side toggle, read loop), not the trigger.

([more](#chart-and-scorer-display-details))
- **Liq**: each watched ticker's liquidation lean in pp (its side times its size against the event-size history) over the watch that started on that cycle, shown as a signed view from a zero line (up = liquidated shorts dominated, down = liquidated longs, zero = watched but quiet). **Window avg liquidation lean** and **Batch avg** count only tickers that had events, and the **Tickers** pills list only those tickers, styled by how one-sided the watch was and which side led. Hover shows the short/long split and the ticker's instability, and a `!` marks tickers currently skipped for entry. ([more](#chart-and-scorer-display-details))

### Extremity Scorer

Each criterion is a **dial family** (`fund`, `va`, `iol`, `ios`, `lta`, `lpa`) with a `+` and a `-` pole; each scan's readings build per-pole cutoffs that sort every reading as extreme or lukewarm. The side that has earned more dollars becomes the favored side (ties default to extreme), and the Lukewarm Veto rejects candidates whose criteria mostly sit on the other side. Scorecards are per bot; see **Extremity Scorer Internals** in Trivia. ([more](#chart-and-scorer-display-details))

**Scorecard chart**: only the favored side's chart is shown (Extreme or Lukewarm) and it flips automatically when the favored side changes. Each criterion is a duo of bars, the `+` pole on the left and the `-` pole on the right, with profit above a zero line and loss below it. Only shown when MIW/MIC (or Blind-Entry / Liquid-Diver) is loaded and enabled. ([more](#chart-and-scorer-display-details))

**CLEAR** wipes this bot's closed-record store, sample pool, Sample Scoring store and Forecast Grader store together (`__ew_pf_extremity_v1`/`__ew_pf_dialpool_v1`/`__ew_pf_sampleobs_v1`/`__ew_pf_fc_v1`, or the `af` set) — cutoffs included, never the partner's. It also empties the graded-forecast history in IndexedDB (`__ew_af_fcdb_v1`/`__ew_pf_fcdb_v1`). The Indicator Forecast's candle cache (`__ew_af_bg1h_v1`/`__ew_pf_bg1h_v1`) is market data and survives it.

Under **Sample Scoring** the same chart is titled **Sample Scorer** and its bars are mean edge in pp, with liquidation outcomes blended in when Liquidation Surveillance is on. A status line above it shows the scored-sample count, plus the liquidation-sample count, tickers on watch and quiet graylist when Liquidation Surveillance is on, and the illiquid count when the Illiquidity Filter is on. With Liquidation Surveillance on, a further line shows the Event Size History's median, peak, bottom and event count. The LPA dial isn't drawn unless Liquidation Surveillance is on, since LPA is the price outcome. ([more](#chart-and-scorer-display-details))

**Headline & gauge**: the header number is relative: the favored side's favorable share of raw 1h move, so 50% is even. A gauge under it is scaled to the best share recorded, with **bottom** and **peak** marking the lowest and highest share (they update once the favored side has at least 10 raw samples). With Liquidation Surveillance on, the share is the 50/50 mix of the price and liquidation values. ([more](#chart-and-scorer-display-details))

The dollar mean and the share are always blended from the same figures, so they can never disagree in sign: each source (price, liquidation) is reduced to its mean favorable pp (P) and mean unfavorable pp (Q) per observation, the sources are mixed on P and Q, and the mean is P − Q while the share is (P − Q) / (P + Q). A share above 50% therefore always goes with a positive mean, and the colour follows both.

## Randomized Outcomes

Scan timing drifts independently per tab, and the sample is a fresh random draw of **Batch Size** candidates each cycle, so two identically configured instances won't share entry triggers, exit timing, or readings. This is intentional: instances in lockstep are easier to front-run and cluster losses at the same market event.

## Multiplex Plugins

To save resources in single-file browser execution, the system supports **Multiplex Plugins**. A standard plugin keeps its own telemetry isolated, while a multiplex plugin hooks into the combined component built when all plugins are loaded and reads the core data directly, without wrapping parent methods. This treats the master engine as a shared database, cutting resource use and avoiding race conditions between plugins. ([more](#general-details))

### The Speeder Module (Tentative Multiplex)

Located in `/plugins/multiplex/`, **Speeder** reuses functions in `MultiIndicator` and the data produced by `Ashfall/Permafrost`. That lets it read the rolling sample-cycle histories and the entry criteria builder directly.

* **What it does**: instead of judging order flow by fixed millisecond limits, Speeder splits the whole deduplicated pool of recent per-ticker trade intervals at the median on each scan.

* **How it does it**: to filter noise, landing in the fast or slow half isn't enough. A ticker's trade interval must also pass that half's own *mean*, which confirms a clear gap from baseline market speed.

* **When it acts**: like `MultiIndicator`, Speeder chooses its entry criteria (fast or slow) automatically, using a `base` setting tied to the liquidation regime. It can enter fast or slow tickers in hot or cold regimes.

* **When it doesn't**: if the surveillance plugins it depends on aren't in the combined component, Speeder logs a warning and stays inactive.

> **Note**: The Speeder strategy is tentative and lacks long-term historical validation; it remains isolated within the multiplex directory for demonstration purposes and architectural testing.

The leader-held check runs at entry, before any instrument or price lookups.

A reason with no registered label shows its raw name. On EverWinter/SunChaser, a bail sweep is followed by a direct exchange re-check.

The fees are `FEE_MAKER_PCT` 0.02% on entry and DCA fills and `FEE_TAKER_PCT` 0.055% on the close (the Bybit base-tier rates); live positions are skipped.

Yes confirms; No cancels with no change.

An entry stays whole in the manifest until IndexedDB has returned its source identical on a later boot, so the manifest shrinks on the second load after a plugin file is loaded. A browser that doesn't persist IndexedDB for `file://` pages never loses a plugin; its entries just never shrink. If IndexedDB is unavailable, errors or doesn't answer within 4 s, the app starts anyway and plugin storage falls back to whole entries in localStorage. A manifest entry whose source is missing from IndexedDB is inactive, and the activity log says to re-load its plugin file. Removing a plugin deletes its source from IndexedDB.

Alpine loads only after the plugin sources have been read and applied (`window.__pluginReady`), which adds a few milliseconds to startup.

The core data it reads directly is the arrays, batched API payloads and state structures, with no reassigning of parent methods. The shared database in question is the master surveillance/execution engine.

### MultiIndicator Details

The details left out of the shortened MultiIndicator entries.

#### Slots

Every criterion in a slot must be true for a ticker to qualify.

#### IO/L and IO/S

`ios-3` is 3 tiers less short than the sampled population averages. They replaced IO/A (`ioa`, open interest alone) in 1.106.0. The long share is read by the sample batch, with one fresh read before entry when a candidate has none. Saved manual slots that still use `ioa` never match; they are flagged once in the log and have to be replaced by IO/L or IO/S by hand.

#### Relative Target

It replaced Target Halving, and a saved Target Halving on/off choice carries over once. On Chaser the favorable average is the up move (TP) and the adverse one the down move (SL); on Winter it is mirrored. Price move % × leverage is the ROI % the host's TP and SL use, so with a +2.5% average up move at 6× leverage Chaser's TP is 15%. While it's on, the Cascade/Sacrifice sliders are hidden and unused, and the gauge also shows the batch and ticker counts behind the averages. It also drives Deferment. It needs no Sample Scoring, only the LPA window: with fewer than 3 readings on either side of zero in the window, the configured values apply and Deferment's floor path is off.

#### Min Entry TP

Cascade is the same number as the resolved entry TP. Cascade and Sacrifice also never fire below 1%, and the SL has no deferral of its own.

#### Targets Gauge

It replaced the text line that sat in the Exit tab. TP and SL each get a bar from the centre axis, with a tick on the TP bar at Min Entry TP; Cascade and Sacrifice are text only, since they never fire below the floor. TP and SL are judged on the resolved value; Cascade and Sacrifice are judged on the resolved value *before* the floor lifts it, while their text shows the value that actually fires, so they read red while the floor is holding them up. A disabled Cascade or Sacrifice reads `off`.

The caption's window averages are up/down, leverage, batches and tickers, and it adds `TP under the N% floor: deferring` when the floor path is on. With Relative Target off the gauge shows the configured values (entry TP is the host's TP, SL the host's `binarySlPct`).

#### Force-Evaluate General Criteria

The function is `_miwTopUpGeneralCriteria`/`_micTopUpGeneralCriteria`, and it also recomputes the composite score. On a following bot this is the one exception to the no-own-fetch rule: it uses the leader's shared OC cache first and fetches the single symbol only if that has nothing.

#### Pole Blocking

The gap is `(partner − pole) / min(|pole|, partner)`, so LTA- at −0.20pp against LTA+ at +0.05pp is a 500% gap and never opens. There's no magnitude floor, both poles need Min Samples, a non-positive partner is left to Both Poles Red, and it reads the favored side.

#### Projected-PP Veto

The sign is in price direction: both mean the scorecard projects the ticker to trail the field for that side, i.e. a negative projection in the bot's favor. The score is the mean of the poles the ticker's fund, V/A, IO/L, IO/S and LTA readings land in (LPA never enters). It is not the Range Fit score because Range Fit lays each batch onto the market's expected range and would put roughly half of every batch on the wrong side.

The veto runs on the entry pool after historical logging (so skipped tickers keep feeding the scorecard) and again on the pre-entry refetch, which Substitution also goes through, so a position is never closed for a vetoed replacement. A ticker with no projection means Sample Scoring is off or no pole has Min Samples.

#### Sparsity

LPA is skipped when picking the thinnest pole because, with Liquidation Surveillance on, its poles fill only from liquidation events and are thin by nature (its score still shrinks by sample count). A family the scorecard doesn't score at all is likewise skipped rather than read as an empty pole.

### Permafrost and Ashfall Details

The details left out of the shortened Permafrost / Ashfall entries.

#### Permafrost / Ashfall overview

The bots' own halt timers govern halts; the plugins only lift them (Mutual DDH Lift) or trigger them (Gains Continuation).

#### Sample Scoring

Criteria are read at sample time and paired with the last completed hour's price move, less the rolling LPA average, which makes it a same-moment correlation. LPA is never scored as a criterion on price observations, and its dial stays hidden from the **Sample Scorer** unless Liquidation Surveillance is on. The hidden closed-trade settings are Position Rolling Average, Drift Credit, Sponge Quota and Stale Purge, while Extreme Split and Min Samples still apply; the panel title also carries a scored-sample count. It forces the hour-candle fetch on, since LPA is its outcome. Forward samples stored by the removed Delayed Pairing are dropped on load.

#### Score Horizon

It lives in the Score tab's settings dropdown. It's applied when the scorecard is built (scores move as batches age out) and when the store is saved. Before 2.27.0 the store was trimmed by size instead, which left price at about 3 h and liquidation at about 63 h. A short horizon leaves liquidation-fed poles thin (LPA especially, hence its exemption from **Sparsity**). The Forecast Grader's graded store has its own size setting.

#### Extremity Re-Evaluation

The criteria checked are the position's rolling average if **Position Rolling Average** is on, otherwise its frozen entry-time snapshot, which still drifts against the cutoffs as they rebuild. When Lukewarm is the target it closes positions drifting into extreme territory, and vice versa.

#### Sample Batch

The ticker request carries the 24h turnover, open interest and funding that `va`/`iol`/`ios`/`fund` compare against. The merged candle is what `lta`/`lpa` read, and the candles are kept for the batch so the Forecast Grader can read the last ~10 minutes. The long/short ratio is the long share that `iol`/`ios` split open interest by (one more request per ticker). Each fetch is an independent snapshot, and the only recent-trade fetch is the opt-in Illiquidity Filter's, one per ticker per refresh window (the order-count criteria `ocs`/`ocx` are retired). A follower also seeds its cycle history from that sample.

#### Liquidation Surveillance

It needs Sample Scoring to affect scores.

**What's watched**: the sample batch itself, less the slots the Forecast Grader's revisits take (**Batch Size**; there's no separate watch size). Revisit tickers are taken out of the pool before this runs, so the watch never sees them and Liquidation Surveillance only fills the remainder. The feed is open only while the toggle and Sample Scoring are on and the bot isn't following.

**Each scan**: the tickers that stay are ordered by most liquidated turnover first. A ticker with none is graylisted immediately and replaced by a fresh random one. The batch is always filled to Batch Size: graylisted tickers are only drawn back in, oldest first, when there aren't enough others, and they leave the graylist when they are. This quiet graylist is for sampling only, so a quiet ticker stays an entry candidate (the Instability Graylist is the one that blocks entries).

**Scoring**: at the end of each watch the batch is re-fetched as usual, and the observation's criteria come from that fresh reading. An event is the ticker's net liquidated turnover (liquidated shorts minus liquidated longs, as a dollar size). Its pp is its side times the window's typical move (the median distance of the latest 1h price changes from their average) times its size against the median event in the Event Size History, capped at the history's peak (so at most peak ÷ median). Liquidated shorts are good for Chaser and liquidated longs for Winter. Every liquidation observation counts 1:1 with a price observation, with no turnover weight since 2.48.0 (before it, the lean was the share of turnover, −1 to +1, so one-sided tickers all read the same ±typical move, which made the readings look alike, and observations were weighted by liquidated turnover against the median, capped at 3×).

**Event Size History** (2.48.0; `pfLiqHistHrs`/`afLiqHistHrs`, default 24 hours, 1–168, never shorter than the Score Horizon): one entry per liquidation event, its time and net liquidated dollars, kept in the Sample Scoring store (`lqh`, up to 5000 entries, aged out at the setting) and saved, exported, imported and cleared with it. The yardstick for a watch is the stored history plus that watch's own events, so it works from the first event: a lone event reads as exactly one typical move. A median-sized event reads one typical move, a smaller one less, a bigger one more, up to the biggest on record (peak ÷ median). Because liquidation sizes are heavy-tailed, that biggest event can read many times the typical move and carry its pole until it ages out. An event with exactly offsetting short and long liquidations reads 0 pp and stays out of the history. Events join the history even when their ticker could not be tagged. Observations stored before 2.48.0 keep their old values until the Score Horizon drops them.

**Reservation (Forecast Grader)**: a ticker that just had a liquidation event is reserved for a forecast of its own, so the event is still fresh when that forecast is graded. Each event in the chart history younger than the **Liquidation dropoff** reserves its ticker; a forecast started on it releases the reservation (a later event reserves it again) and is marked `bg._rv = 1`. A reserved ticker starts first among a batch's candidates, newest event first. One that already has a forecast in flight waits (a ticker is never queued twice) and, once free, is pulled into the next batch by the batch planner beside the revisits, at most half the revisit share, skipping illiquid and stablecoin tickers and any outside the pool. Reservations expire at the dropoff. It runs whenever the Forecast Grader and Liquidation Surveillance do and has no setting of its own. Reserved starts jump the random draw, so those forecasts are a liquidation-biased sample rather than a uniform one (the Export marks them).

**Blending**: a pole's score is the mean of its price edge and its liquidation edge once each has Min Samples (whichever has them stands alone; with neither, the pooled mean once the two together reach it). The favored-side comparison and the headline are mixed the same way, so the gauge and the negative-headline Deferment both read the mix. Liquidation samples count toward a pole's sample total and extreme cutoff, and LPA is scored on liquidation outcomes while the toggle is on, so its dial reappears.

**Display**: the Liq view's ticker pills list only tickers that had liquidation events.

**Good to know**: liquidation events are irregular, so these samples accrue slowly and a score built on them is slow to move, especially on a rare pole. The watch survives a reload: its tally is saved as events arrive and the next scan after a restart scores it (events missed while the page was closed are absent and counted as the watch's blind time, and a watch older than 12 h is dropped). Only the leader watches; a follower adopts the leader's liquidation observations with the rest of the scored store, and its Liq view fills in from the lean the leader publishes for each watch, and its event-size line shows the summary the leader publishes. Turning it off ignores the stored liquidation observations (they're kept) and closes the feed.

#### Instability Graylist

Each ticker's liquidated-short and liquidated-long turnover are kept per watch and summed over the retained sample window; in the score 0% is one-sided and 100% is evenly mixed, and a ticker that flips between short-heavy and long-heavy watches compounds into instability too. The threshold is relative to the average, so a market where everything is mixed doesn't graylist everything. The ticker stays in the watch so its record keeps updating, leaves the list once its mixed watches age out of the window, and the list works on a follower too, since the split rides on the adopted history.

#### Illiquidity Filter

Each sample batch measures only the tickers it carries, with one recent-trade fetch each; a ticker's speed is the average gap between the times of the 3 trades, and **Measure again after** is in days. An illiquid ticker is dropped from that batch before its hour candle is fetched, and while its reading is live it's also left out of the scan pool. When the reading expires the ticker is allowed back, and the next batch it appears in measures it again, so slow tickers are rechecked on the same cycle and can recover. Coverage builds gradually: a ticker with no reading passes until a batch measures it. The leader measures and publishes the readings, and a follower makes no fetch.

The sample scorer status line (with Sample Scoring on) and the setting's own hint show `N illiquid (>12s) · M measured · slowest Xs`.

#### Stablecoin Filter

The range is of the completed candle's open, high, low, close and the current price. Under the limit, the ticker is dropped from that batch (no result), counted in `excluded.gray`, and measured again the next batch it appears in after the verdict expires. The count graylisted shows under the setting. The limit is absolute; an earlier version compared each range with the universe's mean range and graylisted most tickers. The leader judges and publishes the verdicts.

#### Forecast Grader

It needs Sample Scoring, and it replaces the Period Scorer (removed in 2.31.0). The scorecard pairs a ticker's readings with the 1h move that had already happened when it was sampled, so nothing else tests it forward. The graded forecasts change no headline either (Future Awareness, which fed graded results back into pole scores, was removed in 2.38.0), and MIC/MIW's Projected-PP Veto computes the same raw first-appearance score for entry candidates directly.

**No extra fetches**: a forecast ticker simply appears in two ordinary sample batches, **Lead** batches apart.

**Forecast (first appearance)**: from the fresh fund, V/A, IO/L, IO/S and LTA readings of that fetch, the scorecard as it stands scores the ticker: the mean score of the poles it lands in (each read from the Extreme or Lukewarm bucket its own tier falls in; poles without Min Samples are skipped, a ticker with none scored isn't forecast). That number is pp against the field in the bot's favor. It is frozen with the typical price of the ticker's last ~10 minutes from the same fetch (no price enters the projection). With **Range Fit** on, the number is first laid onto the range the market is expected to pay, and the raw score is kept beside it. With the **Indicator Forecast** on, the order the batch is laid onto the range in comes from the indicator rank instead (see below), and the scorecard's own number is kept as `projections.sc`. New forecasts come only from the fresh half of a batch, never from a revisit, and at most the revisit share of the batch size, so starts and revisits balance.

**Revisit (second appearance)**: before each batch is built, MIC/MIW ask the grader for the forecasts falling due (oldest first) and give them up to **Revisits %** of the batch's slots (5–90). Liquidation Surveillance then fills only the remaining slots, from a pool without the revisit tickers. The revisit is an ordinary sample fetch, so it also feeds the scorecard as usual. A ticker that is illiquid now, or missing from the batch, is retried for two more batches and then voided.

**Start log**: every batch's start is logged (the last 120 batches, `startLog` in the Summary export): tickers in the batch, how many were excluded (taken by a revisit, already pending, no price, nothing scorable), the candidates left, the room (`min(share slots, share slots × (lead + 3) − pending)`), how many started and how many of those were reserved. A batch that starts fewer forecasts than its room ran out of candidates, and the exclusions say where they went; a graded cohort can still shrink later through voids (`gone`, `late`, `thin`).

**Actual**: the price move runs from the frozen price to the revisit's **typical price** over its last ~10 minutes ((highest high + lowest low + last close) / 3 of the two newest 5-minute candles; the hour candle's typical price, then the last price, when the ticker traded nothing that recently), read in the bot's favor. The raw move is kept and the Export grades it too (`windowRaw`). The highest and lowest point since the forecast, from the 5-minute candles, are kept as well. A start batch with fewer than 3 gradable forecasts is voided.

**Timing**: due is a batch **number** (a persisted counter), not a timer, so a plugin reload doesn't misalign it. Each forecast keeps its real elapsed time, and one that sat past 1.5× the expected lead (a gap or downtime) is voided, not graded. The expected step is the median gap of the latest retained batches (the configured scan interval until there are enough).

**Grade**: direction right = 50 + 50 × size match, wrong = 50 × (1 − size match), 50 when either side is flat (size match = the smaller over the larger of |projected| and |actual|). A batch or the window is the mean of its forecasts' accuracies (total points over tickers × 100), and **influence** is each criterion family's share (Fund, V/A, IO/L, IO/S, LTA) of the projections' total absolute contribution (still computed and exported, but no longer shown in the hint or the chart summary since 2.49.0; forecasts made before 2.32.0 carry none; IO/A, retired in 2.36.0, is dropped from saved forecasts on load). The Export also holds, over the window of graded forecasts, **rank corr** (Spearman between projection and actual: +1 the scores called the order, 0 no information, negative backwards), **hit** (share with the projected sign right) against **base** (what always calling one side would have scored on the same actuals), **top-bottom fifth** (mean actual of the top fifth by projection minus the bottom fifth, in pp, from 20 graded) and **slope** (actual per unit of projection: 1 is calibrated, 0 is no information). Fewer than 5 graded reads as too few. Per forecast the Export also logs the path since the forecast, a wide snapshot of the readings at forecast time, the market context of each start batch (averages plus the spread, skew and extremes of the hour changes) and the alternative projections, and `projectionTest` grades each projection form (fitted, raw, sum of the poles, strongest pole, the scorecard's own score) on the same actuals.

**Sign convention**: every pp number the Grader shows or exports (projected, raw projected, actual, contribution, alternative projections) is in the bot's favor, so one sign always means one price direction: on Ashfall + is price up and − is price down, on Permafrost + is price down and − is price up. The `%` fields (raw move, move relative to the start batch, batch mean move, highest and lowest point) are plain price moves, + is price up on both.

**Settings**: **Lead** ranges 2–24 batches and **Graded forecasts kept** 60–6000 (default 3000). Unique tickers per batch fall by the revisit share (the scorecard still receives every ticker in the batch).

**Readout**: the hint under the toggle shows pending and graded counts, the window accuracy and the Range Fit state (states stored, forecasts fitted). The Fcst chart view's summary lines the window and the selected batch, each with its net profit line.

**Net profit** (2.49.0; follows the host's maximum positions from 2.49.1): the Fcst view adds a **Batch net profit** and a **Window net profit** line, an estimate of what entering the forecasts' best picks would have returned. Per graded start batch the forecasts are ranked by projected pp in the bot's favor and the top N are taken, N being the host bot's Max Concurrent Positions (3 if it has none), and only forecasts projected in the bot's favor are entered. Each pick is one base-notional position (`minNotional`) held until grading (about an hour at the default lead of 6 batches) and earns notional × its recorded raw move in the bot's favor ÷ 100. A pick that moved against the bot is a loss at its full move (no stop-loss, no liquidation cap), so the figure includes the case where the best forecasts are wrong. The batch line shows the selected (else latest) batch's sum in dollars and its pick count; the window line sums every graded batch in the store and shows the total, the average per batch and how many batches were in profit. A batch with no forecast projected in the bot's favor reads that way and is left out of the window. Forecasts without a recorded raw move are skipped. It is a simple estimate from stored data (no fees, slippage or early exits) and changes no score or entry.

**Storage and sharing**: stored direction-neutral (price direction; the bot's favor is applied when read), so a following bot of the other direction adopts the leader's store as it is. **CLEAR** wipes it with the sample stores, its parts export on their own, and the Profile export carries its raw store, which Import restores. The graded forecasts live in IndexedDB (`__ew_af_fcdb_v1`/`__ew_pf_fcdb_v1`, object store `done`, one record per forecast keyed `startBatch|symbol`); localStorage keeps the pending queue, the Range Fit states, the counters and a short tail of graded rows: the newest 600 until IndexedDB has returned rows on a later boot (proof it persists in this browser), then the newest 120. Without IndexedDB, or if it hangs or fails, everything runs from localStorage as before. A following bot reads the leader's copy and leaves its own IndexedDB alone.

#### Range Fit

It replaced Future Awareness in 2.38.0 and targets **flattening**: scores average out toward zero, so projections come out far smaller than what the market actually pays and the accuracy's size match collapses.

**What's stored** (`ms` in the Forecast Grader store): every graded start batch files one minimal entry, the market's state when it began (the batch context: average 1h change, funding, long share, 10- and 60-minute returns and BTC's, plus the spread (p90 − p10), skew and extremes of the hour changes) and the range its tickers then paid, as batch-relative moves at min, p10, p25, p50, p75, p90 and max. An entry closer to an existing one than **Merge states closer than** (the RMS gap over the shared features, each in robust standard deviations of the stored states; 0 turns merging off) folds into it as a running average, so the store keeps its shape in less space, and the oldest entries drop past **Market states kept** (20–2000). Entries belong to one **Lead**: changing it sets the old ones aside.

**Fitting**: from 8 stored states on, a new forecast batch takes the nearest states (about the square root of the store, 5–15; closer and more-merged ones weigh more), pools their ranges into the range this market is expected to pay and lays the batch's forecasts onto it in the order of their scores: the best-scored takes the top of the range, the worst the bottom, and tied scores share one value. **Range fit (% of projection)** is the share of each projection taken from the fitted value (100 = fully; the rest stays the raw score). The raw projection's field is `rawProjectedPp`, and `projectionTest.raw` grades it on the same actuals, so the fit can be judged against it. The influence shares stay those of the raw score.

**Sizing (2.39.0)**: laying rank onto the pooled range turned weak rank noise into the largest projections: on the first wide export the largest projections hit less often than the small ones, and projected size had no relation to realized size, which does follow each ticker's own volatility (rank correlation about 0.37 with its 60-minute range, 0.36 with its hourly-return spread). Each fitted value is now a blend of the rank-laid value and a **volatility-sized** one: the expected range's median plus a rank tilt of up to **Rank tilt** % of the range's half-spread ((p90 − p10) / 2, by the forecast's plotting position), all times the ticker's own 60-minute range over its batch's median (clamped to 0.25–4×; 1 when it is missing). **Volatility sizing** is the share of the blend taken from that value (0 restores the pure rank-laid fit); **Rank tilt** 0 makes every projection the range's median scaled by volatility. The sign therefore follows the range's median, which is on the short side because batch-relative moves are right-skewed, shifted by the tilt, so read the hit rate against `base` and against the move relative to the batch median (`actualVsBatchMedianPp`). Direction from the scorecard alone had shown no skill, so the tilt carried ordering only (the Indicator Forecast, below, now supplies that ordering); size is what the projection gets right.

#### Indicator Forecast

Introduced in 2.43.0 and the only forecast since 2.43.1. It replaced the **Background Forecast** (2.40.0), a log-only pair of walk-forward ridge models that existed to find which readings carry signal without risking the live path. That test is why these readings were chosen; the models, their toggle and their Export section are gone, and the wide readings stay as the forecast's data feed.

**What it does**: each new batch's forecasts are ranked by an equal-weight rank average (no fitted weights, so nothing to overfit) of the readings picked from the graded window (see below; before 2.44.0 a fixed set of seven: `r10`, `r30`, `clv60`, `clv120`, `rsk`, `oi1h`, `oi4h`). Each picked reading is ranked within the batch, reversal readings counted upside down (centred, −0.5 to 0.5, ties sharing a rank), a ticker's score is the mean over the readings it has (at least 2, else it keeps the scorecard's number), and high = price up next. The score is blended into the forecast as `(1 − w) × scorecard + w × 2 × score × S` with `w` = **Indicator direction** and `S` the batch's mean absolute scorecard score (floor 0.05), then Range Fit lays the batch onto the expected range as before. Size comes from a **size index**: the geometric mean of the ticker's 60-minute range, Garman-Klass volatility (`gk60`) and 1-hour ATR (`atr14`), each against the batch median and clamped to 0.25–4×. The free readings exist when the forecast is filed and the 1-hour and open-interest ones a few seconds later, so the batch is scored once with the first and again when the rest has landed; it always starts again from the scorecard's own score.

**Which readings drive direction** (2.44.0): the set is re-picked whenever a batch has graded, from the graded forecasts of the last **Indicator test window** hours (default 4; at least 6 batches of 8 or more). Every logged reading is ranked within its batch against the move relative to the batch mean (so the market's drift is out of it) and gets its mean per-batch rank correlation over the window and over each half of it. A reading is used the way its own sign shows (a reversal reading counts upside down) and is **kept only if** (1) its sign is the same in both halves of the window, (2) its correlation is at least 0.02 in size, and (3) adding it does not pull the ensemble's rank correlation down (strongest first; a reading with the same values as one already considered is skipped, and so is one seen on under 15% of the window's forecasts). Nothing picked, or fewer than 6 graded batches, leaves the scorecard's own score standing. Size is not picked this way: it stays the volatility index. The Export's `directionTest` lists every reading's correlation (window, first half, second half), whether it is in and why not. Limits: about 4 hours with horizons overlapping 6 batches is only 4 or 5 independent windows, so some noise readings will be picked and drop out again as the window moves, and the picked ensemble's correlation on the window it was picked from is inflated. On the second wide export (600 graded forecasts) it read about 0.21 in-sample, but picked on earlier batches and scored on later ones, three splits read +0.04, −0.02 and +0.11. The fixed set that ran before read about zero on that export (`r10` was a steady reversal rather than momentum), which is why the choice moved from a one-off export to the data. Volatility, position and RSI readings were first kept out of direction because their link followed the batch's mean move; the test now removes the batch mean, and the volatility ones fade between halves while spread, LTA and the prior hour's change held.

**What it logs**: `bg._dc` (the direction score, price direction; the Export's `indDirScore` is it in the bot's favor), `bg._vi` (the size index; `sizeIndex`) and `ep.sc` (the scorecard's own score; `projections.sc`). `projectionTest.scorecard` grades that score on the same actuals as the forecast, and `rawProjectedPp` is now the score before the range fit with the indicator blend in it. Forecasts graded before 2.43.1 still carry the retired model fields (`_pd`/`_pm`/`_bd`/`_bm`); they are ignored.

**Liquidation readings** (2.44.0): `lqa` (the lean of the age-weighted liquidated turnover, −1 to +1 with liquidated shorts +, price direction) and `lqt` (log10 of that weighted turnover) are built when a forecast is filed from every liquidation sample in the chart history older than the forecast (nothing from its own future), each weighted 1 when fresh down to 0 at the **Liquidation dropoff** (linear), and blank when the ticker had none. The chart history holds 25 cycles (about 4 hours), so a dropoff beyond that changes nothing. They are ordinary candidates in the selection above and enter direction only if they hold up; the lean saturates on one-sided events, so `lqt` carries the size.

**Readings logged with each new forecast** (stored on it as `bg`): *free, from data already fetched*: top-of-book imbalance (`tob`), price against the 24h VWAP (`vwd`), the 24h range (`rng24`) and the squeeze (`sq`: the 60-minute range over it), the funding interval (`fih`), time of day (`todS`/`todC`); from the 5-minute candles, close-location-weighted volume over 1h and 2h (`clv60`/`clv120`), Garman-Klass volatility (`gk60`), upper and lower wick shares (`wku`/`wkd`), drawdown from the 1h high (`dd1h`) and the skew of the 5-minute returns (`rsk`). *1-hour candles* (one kline request per ticker, then only the completed hours not held yet): Wilder RSI 6/12/24 (`rsi6`/`rsi12`/`rsi24`), StochRSI K on RSI 12 (`stk12`: a 14-value stochastic smoothed over 3), ATR(14) in % (`atr14`), Bollinger (20, 2) %B and bandwidth (`bbp`/`bbw`), distance from the EMA(20) (`ema20`), 24h and 72h return (`rt24`/`rt72`), distance from the 72h high and low (`d72h`/`d72l`) and a volatility regime (`vreg`: the last 24 hours' spread of hourly returns over everything held). *Open interest* (15-minute history, 17 rows): its change over 15 minutes, 1 and 4 hours (`oi15`/`oi1h`/`oi4h`). *Funding* (last 6 settlements, refetched only after the next one is due): last rate, mean and slope in basis points per settlement, and the interval (`fhl`/`fhm`/`fhs`/`fhi`). Taker flow and the full order book are deliberately not fetched: recent-trade pages cost 20–100× the rest and cover seconds on a major but hours on a dead alt, and a book snapshot decays within seconds against a 1-hour horizon. The candle flow readings and the top-of-book imbalance stand in for them.

**Fetching**: the slow readings are fetched right after a batch's forecasts are filed, three tickers at a time through the shared queue (the scan never waits on it); when they have landed the batch is scored again with all of them.

**What the Export shows** (`featureIC`, and the readings on each forecast): per reading, its mean per-batch rank correlation with the move (in the bot's favor) and with its size, t over batches, and its family (mom: RSI and StochRSI; vol; pos; ret; oi; fund; flow; ctx). With about 45 readings a few will clear t > 2 by chance, and the t overstates the evidence: batches start one scan apart but grade **Lead** batches later, so neighbouring batches share most of their move (the t is inflated by roughly the square root of Lead, about 2.4× at the default 6). Judge a reading by its sign across the thirds of the window and by whether it follows the batch's mean move, and replicate on a later export before trusting it.

**Liquidation diagnostics**: the liquidation watch opens when a forecast starts, so what it sees is the 10 minutes **after** the start, which makes it a diagnostic and never a model input (the model's own liquidation readings, `lqa` / `lqt`, are built from earlier cycles). Each such forecast gets `x_lqw` (1 watched; 0 no reading, set when the forecast is graded), `x_lqu`/`x_lqd` (liquidated short/long turnover), `x_lql` (lean in pp), `x_lqs` (seconds the watch really listened) and `x_lqg` (seconds it was blind, because the page was closed or the feed dropped). A window made from two folded watches reports nothing. On the first export 22 of 600 forecasts saw any event, and the lean is saturated (a $19 event and a $3,000 one read alike), so use the turnover fields for size.

**Cost and storage**: about 3 extra requests per new forecast on first sight of a ticker (100 hourly candles ≈ 8 KB, open interest ≈ 1 KB, funding ≈ 0.6 KB), then mostly only the new hours; the free readings cost nothing. Since 2.46.0 the candle windows also hold each hour's volume (about 0.4 KB per ticker) for Candle Divination. The candle windows persist across reloads in their own key (`__ew_af_bg1h_v1`/`__ew_pf_bg1h_v1`, see Trivia); the open-interest and funding caches are memory-only. The readings are numbers on the forecast records, about half a kilobyte each, and live in IndexedDB with the graded forecasts (about 230 KB per 600 forecasts in the Export's compact Readings part). Without IndexedDB, if localStorage fills, the older half loses its readings and the save retries once. A readings run in flight is saved when the page is hidden or closed.

#### Candle Divination

Introduced in 2.46.0; the minimum, the shrinkage and the replacement rule changed in 2.47.0. A sub-toggle under Indicator Forecast that learns candle shapes from the 1-hour candles the forecast already keeps and reads each ticker's latest shape as a forecast reading. It makes no requests of its own.

**Shape**: six completed hours. Per hour, the body, upper wick and lower wick (the open is taken as the previous close), each divided by the ticker's own average hourly range over its last 24 hours (so a major and a small coin compare), clamped to ±4 and weighted from 0.6 (oldest hour) to 1 (newest): 18 numbers. The **volume** version adds six more: each hour's volume against the ticker's 24-hour median (log, clamped to ±3, same weights); it exists only when all 24 hours have volume. A slice needs 24 candles behind it for its scale, so a ticker holding 100 candles gives about 75 pairs (a slice and what followed it).

**Two libraries, learned prototypes**: price shape alone (reading `dvp`) and price + volume (reading `dvv`, behind its own switch). Each library is a set of **shapes** (prototypes): a centre, a match count, the mean move of the next hour (in units of the ticker's own average hourly range, + = price up), the share of next hours that rose, and the mean 6-hour path that followed with its count. A library starts empty and collects pairs; at 1,000 it is clustered (k-means with a k-means++ start, 12 rounds, at most one shape per 16 pairs, up to **Shapes in library**, default 64) and every pair gives its nearest shape its outcome. Afterwards every newly completed hour of a fetched ticker is one pair, learned once (the last hour learned is kept per ticker): it nudges its nearest shape's centre and averages (running means, rate 1 / min(count, 400)). At load the candle cache already in memory feeds a random sample of up to 4,000 pairs, so the price library is built at once with no fetch; the volume library fills as hours with volume accumulate (the cache holds volume only for hours fetched since 2.46.0). These learned shapes replace the preset PEC shapes and the separate VSG volume read of the older system. Changing **Shapes in library** applies on **Rebuild**, which re-clusters from the cached candles and drops the counts beyond them.

**Reading**: the ticker's newest slice (the last completed hour is its end) goes to its nearest shape (root-mean-square distance). No reading when that shape has fewer than **Minimum matches** (default 3) or lies farther than **No reading beyond** (default 2) × the library's typical distance (a slow average of the distances pairs matched at). Otherwise `dvp` / `dvv` = the shape's mean next-hour move, unshrunk (2.46.0 shrank thin shapes by n / (n + 30) and needed 20 matches). Diagnostics, never model inputs: `x_dvd` (the distance over the typical one, price library), `x_dvi` / `x_dvj` (which shape matched in the price / price + volume library). The forecast runs about 60 minutes from its start, and the reading is the next hour's close-to-close move after the last completed hour, so the two overlap rather than match exactly.

**In the forecast**: the readings are logged on each forecast like any other and are ordinary candidates in the direction test. Until the test has a verdict on one (too few graded batches or too few readings; the Export's `directionTest` shows `live until graded`) it counts at sign +1, since it is an expected price move; this also holds under 6 graded batches, when nothing else is picked. Once the test has a verdict, in or out (sign flip, too weak, pulls the ensemble down), the verdict rules. A ticker's direction score counts the columns present in the batch, so a ticker with no `dvv` is scored on the rest.

**Replacing the weakest** (2.47.0): a pair that matches no shape (beyond the abstain distance) takes over the shape with the fewest matches among those at least 300 pairs old, so a new pattern can earn a place instead of smearing into the nearest old one. At most one replacement per 100 pairs, so a market-wide shift cannot wipe the library; a new shape is protected for 300 pairs; a replacement keeps the shape's number, so an old reading's `x_dvi` / `x_dvj` can point at a shape that has since been swapped. The Export counts them (`replaced`).

**Storage and export**: the libraries are saved under `__ew_af_div_v1` / `__ew_pf_div_v1` (see Trivia) and the candle cache gained a volume field (see Cost and storage above). The Summary export carries `candleDivination`: settings, and per library every shape's matches, mean next-hour and next-6-hour move, share up and paths. The libraries are not in the Profile export or Import; they rebuild from the candle cache. A follower bot adopts the leader's forecasts with their readings but does not run the learning, so its panel stays empty.

**Limits**: a 6-hour hourly-candle shape on its own is a weak signal, and much of what it can see overlaps readings already in the ensemble (close location, RSI, returns); the direction test over about 4 hours is short, so the readings can flicker in and out. With a minimum of 3 and no shrinkage, a shape with 3 matches ranks as loudly as one with 300. The learning was tested on synthetic candles with a planted rule (it found it), not on live data.

### Chart and Scorer Display Details

The details left out of the shortened Sample Chart and Scorer entries.

#### Sample Chart

Each button is labelled with the view it goes to, the order wraps at either end, and the view resets to Vol on reload. The chart only shows when at least one sample exists. Each cycle group is stamped with its sample time, and clicking elsewhere returns to the latest.

#### L/S view

It is drawn from a zero line on a symmetric axis sized to 1.3× the 95th percentile of |value|. Only tickers whose batch carried the ratio appear (batches from before 2.36.0 carry none).

#### Fcst view

Bars are sorted best first on an axis of 0–100 (up at or above the 70% line, down below), and each column is stamped with the time it was graded. After the dashed line, each batch still to come shows a faint tick (`+1` = the next batch). The latest column is selected by default, and hover shows its count and grade. The summary also shows graded and pending counts, lead, revisit share and voids, in a **Window** line (accuracy) and a **Batch** line, each followed by its net profit line. The Tickers table lists that batch's tickers, best accuracy first: accuracy % (colored by the same cutoffs), projected pp, actual pp (green when the sign was called right) and the raw move, scrolling both ways. The Fcst view has no ticker chips.

#### Liq view

The window average uses each ticker's latest liquidation-event reading, and watched-but-quiet tickers aren't counted in either average, so they can't pull it toward 0. The pill styles are **favorable** (pure, the bot's side) fill and outline, **mixed favorable** fill only, **mixed unfavorable** outline only, **unfavorable** neither. Mixed means the minority side holds more than **Mixed %** of the turnover (default 30%; a dead-even split counts as mixed unfavorable), and favorable is liquidated shorts on Chaser and liquidated longs on Winter. The summary line adds how many tickers are unstable. Watches from before the split was recorded only know which side led, so their pills show as pure. Only tickers watched in a cycle appear, and only cycles watched while Liquidation Surveillance was on carry it; the newest cycle fills in once its watch is scored on the next scan. It rides in the same cycle history as the other views, so it holds as many cycles as that history does.

#### Dial families and the scorecard

Under Sample Scoring `lpa` is the outcome and has no dial. Closed trades are tallied per side and per pole, and each scorecard reflects only its own bot's trades.

#### Scorecard chart

It is a single non-wrapping row of criterion duos that scales to its container, with the criterion emoji underneath each. The header shows the side's name and total; hover a bar for its PnL and W/L.

#### Sample Scorer

Hover shows the average edge, ↑/↓ counts and n. When Liquidation Surveillance is on, LPA is scored on liquidation outcomes and drawn. The Illiquidity Filter's line shows how many tickers are illiquid, how many have been measured and the slowest.

#### Headline & gauge

The share is the move in the bot's favor as a share of all raw move on that side. Hovering the gauge shows the sample count, the mean in dollars on one base position and the relative edge, while the per-criterion bars stay relative (mean edge vs the sampled population). **Bottom** and **peak** also need at least Min Samples, and they're cleared with the samples. The headline reads `—` until enough samples carry a raw move. With Liquidation Surveillance on, the dollar mean is mixed too (hover shows how many liquidation samples went in), and **bottom** and **peak** record the mixed share.

### Criteria Sampling Internals

- **Ticker Ranking**: each scan draws **Batch Size** tickers (default 50) at random and fetches their data fresh; that batch is the sample that feeds scoring. Entry candidates are ranked on every ticker's latest stored reading, however old, and each is refetched right before it opens, so any ticker the sample has reached can be picked. Refetches stop at one batch size per scan, since fetching all six criteria across 600+ tickers every 10-minute scan would be too heavy on computation and bandwidth; a larger batch size is an option if you have the resources. The batch isn't always purely random: with Liquidation Surveillance on, tickers that just had liquidations stay and quiet ones are replaced (see **Liquidation Surveillance** below), and with the Forecast Grader on, up to its **Revisits %** of the slots go to forecasts falling due (see **Forecast Grader** below), with the Illiquidity Filter on, tickers measured as illiquid are left out (see **Illiquidity Filter** below).

- **Tier gate**: every criterion computes an integer tier as `floor(value / step)` and compares it against N. `fund` truncates toward zero instead, so a tiny negative rate lands on `fund-0` (mirroring `fund+0`) rather than flooring to `fund-1`. Current step sizes show as read-only chips under **Tier Step Sizes** on the Fetch tab. The same tier is recorded on the position and used as the scorecard key, so `fund>40` and `fund+70` are different tiers and are scored separately.

- **Bare-form exception — `fund`**: in Auto mode, a criterion named without a `>`/`<` comparison normally still requires a nonzero tier. `fund`'s bare form is the exception: it matches any finite funding rate, exactly 0% included, because real Bybit funding rates mostly sit well under a single **Fund Step**. A near-zero rate is a real lukewarm reading (`fund+0`/`fund-0`), so it attaches and feeds the lukewarm chart. The tiered forms are unaffected.

- **Funding emoji**: position and trade badges show 🤑 or 💸 for a `fund` tier, and the emoji says whether that funding sign favors the bot's own direction, so Winter and Chaser show opposite emoji for the same raw sign. The Extremity Scorer's own pills use one fixed set on both bots (💸 positive, 🤑 negative).
- **`va`**: `va+12` = 12 tiers hotter than the sampled population. `_pfVolIoWindowAvg`/`_afVolIoWindowAvg` delegates to `_pfWindowStats`/`_afWindowStats`, a deduplicated latest-reading-per-symbol read (`vol`, `oi`, `oil`, `ois`, `ls`, `lta` or `lpa`) memoized per history state; the Sample Chart's Total avg draws from the same read.
- **`iol` / `ios`**: a ticker's long share of open interest is `oi × long share` and its short share `oi × (1 − long share)`. The long share is Bybit's long/short account ratio (`_pfLsRatio`/`_afLsRatio`: `GET /v5/market/account-ratio`, 5-minute period, latest row, `buyRatio ÷ (buyRatio + sellRatio)`), fetched per sampled ticker with the batch and stored on its sample record as `bl` (null when the call fails; the record then carries no `bl`). The tier is `floor(100 × ln(share ÷ window average) ÷ step)` against the window average of that share (`oil`/`ois` in `_…WindowStats`, which only counts latest readings that carry both `oi` and `bl`), so there is no tier without both, or without a window average. The **L/S** chart view and the batch context read the same `bl` (skew = `(2 × bl − 1) × 100`).
- **`fund`**: tier is `trunc(rate% / Fund Step)` with an explicit sign, so tiny negatives tag `fund-0` and exact zero tags `fund+0`. Sample records carry the funding rate as `fr` (%) so the Fund chart and Sample Scoring can use it.
- **`lta`**: `_pfLtaDev`/`_afLtaDev`; `lta+12` = 12 × **LTA Step** (default 10%) above the ticker's own average hour (`turnover24h / 24`). No population baseline.
- **`lpa`**: `_pfLpaWindowAvg(sym)`/`_afLpaWindowAvg(sym)`, in tiers of **LPA Step** (default 0.25pp). Absolute points, since a relative deviation is unstable near a zero mean. No tier until at least one other ticker has an `hc` reading in the window.
- **Candle fetch**: `_pfHourCandle`/`_afHourCandle` calls `GET /v5/market/kline` at `interval=5&limit=26` (130 minutes of 5-minute candles) and merges the candles inside the last completed hour (`_pfHourStart`) into its hour reading, so `ht`, `hc` and `htp` keep their meaning (a minute with no trade can leave the merged hour a little short); the forming candle is never part of it. The candles also sit in memory for the batch (`CAND5`), where the Forecast Grader reads the typical price of the last ~10 minutes (`_pfTyp10`/`_afTyp10`: the two newest candles started within 15 minutes of now, (highest high + lowest low + last close) / 3) and the path since a forecast. The hour reading goes in a memory-only per-symbol cache (`HOUR_CACHE`, pruned past 500) and is attached, as `ht`, `hc` and `htp`, to the ticker's OC cycle entry, so a **Follow Partner Bot** instance gets it from the leader (`_pfHourReading`/`_afHourReading`). The fetch rides the same batch (`wantHr` on `_ocFetchBatch`) whenever `lta` or `lpa` is in use. The Indicator Forecast's 1-hour kline fetch (`interval=60`) is separate and feeds only it.
- **Fresh batch fetch**: `_pfFetchFreshTicker`/`_afFetchFreshTicker` calls `GET /v5/market/tickers?category=linear&symbol=` per batch symbol, keeps the raw payload for the scan (`_pfFreshTicker`/`_afFreshTicker`) and stores a compact `{ vol, oi, fr, px, ch }` reading. A failed fetch drops the ticker; there is no fallback to the bulk list. A **Follow Partner Bot** instance rebuilds tickers from the leader's readings (`_pfSynthTicker`/`_afSynthTicker`). Entry candidates are refetched the same way by `_pfFetchCandidate`/`_afFetchCandidate` (ticker, plus OC and the hour candle when used), which touches neither the OC results nor the cycle history.
- **Entry-pool freshness**: MIW/MIC act once per new batch (`_pfOcResultsAt`/`_afOcResultsAt`), not once per bulk fetch, and `_miwOpen`/`_micOpen` skip the pre-open price refetch for a ticker from the current batch (`_pfTickerIsCurrent`/`_afTickerIsCurrent`). Candidates are ranked on each ticker's latest stored reading (`_pfLatestReadings`/`_afLatestReadings`, rebuilt by `_pfSynthStored`/`_afSynthStored` with `_cycle` set to that reading's own cycle time, so only the latest batch counts as current). Before a non-batch candidate opens or displaces a position, `_miwVerify`/`_micVerify` refetches it, reruns the slot match and veto with the dial-pool sample off, and stops at **Batch Size** refetches per scan. The refetched ticker only has to still qualify; it doesn't need to keep its ranked tier or score.
- `_miwHourTier`/`_micHourTier` returns `null` for missing data: the criterion check reads it as false and the annotator as "no sample", never a fake `+0`.
- Emoji for retired criteria stay resolvable in `critEmoji`/`afCritEmoji` so old records and exports render; they are display-only.

### Deferment & Ejection Internals

- **Deferment signal**: `_miwWeatherNeg`/`_micWeatherNeg` reads `_pfSampleWeather`/`_afSampleWeather(side)` on the favored side and defers while its dollar `value` is below zero, with no deadband, trim, or cooldown. It needs Sample Scoring and returns nothing until the scorecard has a headline.
- **Deferment effect**: the scan returns before every open path, with guards inside `_miwTrySubstitute`/`_micTrySubstitute` and `_miwOpen`/`_micOpen`. Historical scoring still runs. One `⛔ Deferment` log line per streak.
- **Ejection**: runs every scan ahead of slot logic (so it acts with no active slots) when the deferment state's `eject` is set, which needs two or more paths in `why`. `_miwEject`/`_micEject` closes every non-pending position of any strategy concurrently (`Promise.all`), each close in its own try/catch, with one `⏏️ Ejection` log line naming the paths and close reason `ejection`. Each trade is scored against its opening criteria.

### Relative Target & Scorecard Deferment Internals

- **Targets**: `_miwRelMoves`/`_micRelMoves` reads `_pfOcCycleHistory`/`_afOcCycleHistory`, takes the latest `…RelBatches` cycles by time and each ticker's latest `hc` (1h price change %) within them, and averages the positive and the negative readings separately; it returns null unless each side has at least Min Samples (floor 3) readings. `_miwTargets`/`_micTargets` turns that into the targets: the favorable side's average × `leverage` is `entryTp` and `cascadePct`, the other side's average × `leverage` (floor 1%) is `slPct` and `sacrificePct`. Chaser's favorable side is the positive average, Winter's the negative. It returns the configured values untouched (`active:false`) when Relative Target is off, neither Cascade nor Sacrifice is on, or `_…RelMoves` has no data. `_miwEffCascadePct`/`_micEffCascadePct` and `_miwEffSacrificePct`/`_micEffSacrificePct` return the resolved % floored at Min Entry TP and 1%; `_miwTargetsText`/`_micTargetsText` feed the Exit-tab readout. A saved `…TargetHalvingEnabled` is migrated to `…RelativeTargetEnabled` once at load.
- **Per-position overrides**: `_miwOpen`/`_micOpen` pass `_tpPct` and `_slPct` on the candidate. PseudoWinter/PseudoChaser use `_tpPct` for the entry TP, and `_slPct` for the binary-mode SL at open. It is also stored as `pos._slPctOverride`, which the DCA-mode SL arm, the SL drift check and the position card honor. Both candidate fields are excluded from the copy of candidate fields onto the position.
- **Targets gauge**: `_miwTargetsView`/`_micTargetsView` turns `…Targets()` into `{left, right, note}` for the gauge (left SL and Sacrifice, right TP and Cascade). Each row carries its text, a bar width (none for Cascade/Sacrifice) and a class: `ok` when the resolved value is at or above `minTp`, `bad` below it, `off` when disabled or while Relative Target is still waiting. Cascade/Sacrifice classes read the raw `cascadePct`/`sacrificePct` (the configured value when `active` is false), while their text reads `…EffCascadePct`/`…EffSacrificePct`. The body binds it with `x-effect`. `…TargetsText` is no longer bound to anything.
- **Projected-PP veto**: `_miwProjectedPp`/`_micProjectedPp(t)` annotates the ticker with `…AnnotateCritRaw` for `fund`, `va`, `iol`, `ios` and `lta`, scores those tags with `_pfFcParts`/`_afFcParts` and multiplies the resulting `e` by `_pfSampleDir`/`_afSampleDir` (−1 Winter, +1 Chaser) to give price-direction pp; it returns null when there are no tags, no scored pole or no `…FcParts`. `_miwPpBad`/`_micPpBad` is true when direction × pp is below zero. It is called in the entry-pool filter after `…IsEntryBlocked` (counting `scanSkip.ppBad`) and in `…Verify` right after the same entry-block check, which covers the entry loop and Substitution.
- **Deferment layering**: `_miwDefermentState`/`_micDefermentState` wraps `…DefermentStateBase`. The wrapper evaluates the negative-headline test (on with Deferment), Both Poles Red and the base on their own and merges them, with `why` listing those that hold and `eject` set when there are two or more. The base holds only the Relative Target floor test: it defers while the resolved entry TP is under Min Entry TP. `_miwWeatherNeg`/`_micWeatherNeg` and `_miwBothPolesRed`/`_micBothPolesRed` are the two clause tests; the latter reads the favored side of `pfLukewarmScoreboard`/`afLukewarmScoreboard`.
- **Headline source**: `_pfSampleBuild`/`_afSampleBuild` accumulates the raw edge per bucket into `pfSampleBucketMeans`/`afSampleBucketMeans` (`aE`/`aL`, counts `nAE`/`nAL`) and the signed favorable share `(P−Q)/(P+Q)` of those raw moves (`sE`/`sL`). `_pfSampleWeather`/`_afSampleWeather` returns the dollar `value`, the share (`s`, and `share` as 0–1) and the peak/bottom of each (`hi`/`lo`, `sHi`/`sLo`). `_pfSampleTrackWx`/`_afSampleTrackWx` keeps those peaks in the sample store as `wx`, and the leader shares them with followers. `aE`/`aL`/`sE`/`sL` come from one blend: each source is reduced to per-observation pp mass `{P, Q}` (price `p/n`, `q/n`; liquidation `p/w`, `q/w` once its bucket holds Min Samples), the sources are mixed on `P` and `Q` (50/50 for liquidation, only when the base exists), and `a = P − Q`, `s = (P − Q) / (P + Q)`, so their signs can't differ. With Liquidation Surveillance on, the liquidation side is part of that mix; `nlE`/`nlL` report its count, `nE`/`nL` and `nAE`/`nAL` include it, and the weather's `nl` carries it for the tooltip. The bucket `extreme`/`lukewarm` means that pick the favored side are mixed the same way. `aE0`/`aL0`/`sE0`/`sL0` are still published (the removed Silence Penalty and Silence Amplifier used to scale the headline), so the negative-headline Deferment test reads the mixed share and value directly. The peak/bottom `sHi`/`sLo` are still tracked for the gauge; Relative Target no longer reads them.

### Extremity Scorer Internals

- **Cutoffs**: come from the sample pool (`pfDialSamplePool`/`afDialSamplePool`), fed by `_pfDialSample`/`_afDialSample` on every criterion annotation, not only trades, and persisted across reloads. A pole with at least **Min Samples** readings cuts off at its **Extreme Split** percentile; a reading at or above it is extreme, anything below it and everything on an unproven pole is lukewarm. Bare sign-only tags from Blind-Entry/Liquid-Diver (`+fund`/`-fund`/`+ocs`/`-ocs`) carry no magnitude and always classify extreme.
- **Two tallies**: the dial tally counts extreme occurrences only and is the flat `micCollapsedSlotRanks`/`micCollapsedCritStats` lookup that Co-Qualifying Penalty and entry ordering read. The Lukewarm Scoring tally counts every occurrence, bucketed by class then by pole (`fund+`/`fund-`, not merged by family, since a family's poles are opposite signals).
- **Favored side**: `_pfLukewarmFavoredSide`/`_afLukewarmFavoredSide`, re-decided each time the scorer rebuilds (once per scan cycle).
- **Veto**: `_pfExtremityVeto`/`_afExtremityVeto` counts the share of a candidate's dial-eligible criteria on the non-favored side and vetoes at **Lukewarm Veto**%. An unproven dial counts against the candidate. It checks every entry.
- **Pole Blocking**: `_miwPoleBlocked`/`_micPoleBlocked`, called from `_miwIsEntryBlocked`/`_micIsEntryBlocked` after the Lukewarm Veto, so it covers both the entry-pool filter and the post-top-up re-check. Reads the favored side of `pfLukewarmScoreboard`/`afLukewarmScoreboard`; inert without Sample Scoring.
- **Position Rolling Average**: when on, `_pfPositionCriteriaSample`/`_afPositionCriteriaSample` re-reads each open position's locked criteria families every scan and keeps a rolling 24h average per family, using a fresh single-ticker fetch and the cached 1h candle for `lta`/`lpa`. These fetches are exempt from Leader/Follower's no-own-fetch rule, like Force-Evaluate's. `_pfPositionAvgCriteria`/`_afPositionAvgCriteria` rebuilds the tag from the average, falling back to the frozen entry tag (`_miwCriteria`/`_micCriteria`, or the Blind-Entry/Liquid-Diver equivalents) for any family under **Min Samples** readings. Close-time scoring, Extremity Re-Evaluation and Substitution's live score all read that average. When off, nothing is fetched and only frozen tags are used; the cutoff sample pool is unaffected either way.
- **Sample Scoring**: when on, `_pfExtremityBuild`/`_afExtremityBuild` returns `_pfSampleBuild`/`_afSampleBuild` instead of walking closed records. It publishes the same outputs (cutoffs, `micCollapsedSlotRanks`/`miwCollapsedSlotRanks`, the two-bucket scoreboard) from `__ew_*_sampleobs_v1`, plus the per-bucket mean edge (`pfSampleBucketMeans`/`afSampleBucketMeans`) for the favored side. `_pfSampleIngest`/`_afSampleIngest` runs with each new sample cycle and stores one observation per ticker: its criteria tags at sample time, `y` (the last completed hour's price change minus the rolling LPA average from `_pfLpaWindowAvg`/`_afLpaWindowAvg`) and `r` (the raw change). The build keeps only each ticker's latest observation per clock hour and skips `lpa` tags on price observations. The leader hands over `sampleScore` through the corridor and a follower adopts the delivered copy each scan (`_pfSampleAdopt`/`_afSampleAdopt`).
- **Forecast Grader**: `_pfFcPlan`/`_afFcPlan(pool, cap)` is called by `_miwScanFetch`/`_micScanFetch` before the batch is built (leader only, null when off or following). It takes the pending forecasts with `d <= seq + 1`, oldest first, skips illiquid tickers (`_pfIlqIs`/`_afIlqIs`), caps them at `floor(cap × share)` and stores `{seq, cap, rev, rsv}` (`rev` = the revisits; `rsv` = the waiting liquidation reservations the planner added to the returned list, which the ingest does not treat as revisits) in `_pfFcPlanned`/`_afFcPlanned`; the builder removes those symbols from the pool, passes `cap − revisits` to `_pfLiqPick`/`_afLiqPick`, and fetches `[...revisits, ...pool]` deduplicated and cut to `cap`. `_pfFcIngest`/`_afFcIngest` runs after each batch's `_pfSampleIngest`/`_afSampleIngest` (and for a seeded follower batch, where it returns at once since a follower adopts the store with `_pfFcAdopt`/`_afFcAdopt`). It is idempotent on the batch timestamp, increments `seq`, and (1) grades every forecast with `d <= seq` whose ticker is in the batch with a price: elapsed over 1.5 × lead × `_pfFcStepMs`/`_afFcStepMs` counts as `late`, a missing ticker is retried until `seq − d >= 2` and then counts as `gone`, and a start batch with under 3 gradable forecasts counts as `thin`; the move is `m = (typical / price − 1) × 100`, where typical is `_pfTyp10`/`_afTyp10` of the ticker's 5-minute candles from this batch's fetch (`CAND5`; else the revisit result's `htp`, else its `px`) and price is the frozen typical price, `mu`/`md` are the highest and lowest point of those candles since the forecast, and the actual is `y = m − k`, `k` being the cohort's mean `m`; `y`, `m` and `k` are stored raw. Each graded start batch also files its Range Fit entry (`_pfFcRangeAdd`/`_afFcRangeAdd`: the state kept in `fc.ctx[a]` and the quantiles of the cohort's `m − k`). Then (2) it starts forecasts from batch results that are not revisits and not already pending: `_pfSampleTags`/`_afSampleTags` (without LPA) gives the tags, `_pfFcParts`/`_afFcParts` the mean `pnl` (and each family's share `w`, stored raw like `e`) of the scoreboard entry (`afLukewarmScoreboard.extreme`/`.lukewarm`, picked by `afDialCutoffs`, needing Min Samples) of each tag's pole, multiplied by `_pfSampleDir`/`_afSampleDir` to store it raw. Reserved candidates (`_pfFcReserve`/`_afFcReserve`) go first, newest event first, and the rest are shuffled; all are capped at `min(share slots, share slots × (lead + 3) − pending)`, so the revisit half and the fresh half balance. The picked forecasts go through `_pfFcRangeFit`/`_afFcRangeFit` before they are stored. The scoreboard used is the one built before this batch's observations, so a forecast never sees its own outcome. `_pfFcStats`/`_afFcStats` reads both values in the bot's favor (`dir × e`, `dir × y`) and returns n, Spearman rho (average ranks for ties), hit and base, the top/bottom fifth means and spread (n ≥ 20) the OLS slope, the mean accuracy (`_pfFcAcc`/`_afFcAcc` per forecast) and the influence shares (`_pfFcInfl`/`_afFcInfl`). `_pfFcChartSvg`/`_afFcChartSvg`, `_pfFcBreakdownHtml`/`_afFcBreakdownHtml`, `_pfFcSummaryText`/`_afFcSummaryText`, `_pfFcWindowText`/`_afFcWindowText` and `_pfFcBatchText`/`_afFcBatchText` draw the Fcst view; `_pfFcExport`/`_afFcExport` builds the Export file and Import restores `forecast.store` through `_pfFcSanitize`/`_afFcSanitize`. Nothing in `_pfSampleBuild`/`_afSampleBuild` reads the grader. **Range Fit**: `_pfFcRangeAdd(st, ys, k, ts, a)`/`_afFcRangeAdd` builds the entry (the state features in `FC_RANGE_FEATS`, the quantiles of `ys` at `FC_RANGE_P` = 0, .1, .25, .5, .75, .9, 1), merges it into the nearest same-lead entry within `…FcRangeSim` (`_…FcRangeDist`: the RMS of the gaps over at least 3 shared features, each scaled by `_…FcRangeScale`, the larger of 1.4826 × MAD and half the standard deviation across the store; merge weight 1 / (min(count, 6) + 1)) or appends it, and `_…FcRangeTrim` drops the oldest past `…FcRangeKeep`. `_…FcRangeExpect(state)` needs 8 same-lead entries with a distance, takes the nearest `round(√n)` of them (5–15) and averages their quantiles weighted `min(count, 6) / (distance + 0.15)`. `_…FcRangeFit(list, state)` sorts the new forecasts by raw `e`, gives tied values their middle rank, reads the expected range at plotting position `(rank + 0.5) / n` by linear interpolation between the stored quantiles (`M0`); with volatility sizing `vs` above 0 the fitted value becomes `(1 − vs) × M0 + vs × vr × (Q50 + tilt × (2 × pr − 1) × (Q90 − Q10) / 2)`, `vr` being the ticker's snapshot `rng60` over the batch's median clamped to 0.25–4 (1 when missing) and `pr` the plotting position, and `…FcVolSize`/`…FcTilt` read the two settings; it then sets `e0` to the raw `e` and `e` to `blend × fitted + (1 − blend) × raw`; `…FcRangeInfo` keeps the last fit for the hint and the Export. The state is `_…FcCtx(entry)`, the batch context. `_pfFcPass`/`_afFcPass` (70) is the chart's up/down split, `_pfFcMid`/`_afFcMid` (50) its second cutoff and `_pfFcClr`/`_afFcClr` the green / yellow / pink colour of an accuracy.
- **Indicator Forecast** (the Background Forecast before 2.43.1): `_pfBgFree`/`_afBgFree(r, t, cs, now, sn)` builds the readings that need nothing fetched (from the bulk ticker `t`, the 5-minute candles `cs` and the snapshot), and `_pfFcIngest`/`_afFcIngest` files them on each picked forecast as `bg`; `_pfBgRun`/`_afBgRun(pick)` (not awaited) then fills the slow ones with three workers: `_…BgH1` (kline `interval=60`; `BG1H[sym]` holds the last 100 completed closes, highs and lows, the Wilder state for RSI 6/12/24 (`_…BgFeed`: the first p changes seed a simple average, then `(avg × (p − 1) + x) / p`) and the last 20 RSI 12 values; first sight asks for 100 candles, later fetches for the completed hours missing plus one, and a gap over 90 hours re-warms; `_…BgH1Feat` computes the readings), `_…BgOi` (`/v5/market/open-interest`, `intervalTime=15min`; `BGOI` holds the last 17 rows merged by timestamp and counts as current when its newest row is the last completed quarter hour) and `_…BgFh` (`/v5/market/funding/history`, `limit=6`; `BGFH` is refetched when the next settlement, the last one plus the observed interval plus 2 minutes, is due, and at most every 10 minutes while the venue has not posted it). When the slow readings have landed, `_…FcLive(pick, ctx)` scores the batch again (it also runs at ingest with the free ones): it restarts every forecast from `ep.sc` (the scorecard's own score, stored at ingest), then, with `_…FcIndOn()` (= `_…BgOn()`: Forecast Grader on and `…FcInd` not off), `_…FcIndDir` writes `bg._dc` (`_…FcPct` ranks each reading `_…FcIndSelect` has picked within the batch, centred, ties sharing a rank, and flips it by its orientation; the mean over the readings a ticker has, at least 2 when that many are picked; none picked = no `_dc`) and `_…FcIndVol` writes `bg._vi` (`VOL_FEATS`: geometric mean of own / batch-median, clamped 0.25–4, a median needs 3 readings), blends `_dc` into `e` as `(1 − w) × e + w × 2 × dc × S` (`w` = `_…FcIndBlend()`, `S` the batch's mean |scorecard score|, floor 0.05) and lets `_…FcRangeFit` lay the batch onto the range, taking each ticker's size from `bg._vi` when present (else its 60-minute range over the batch median). `_…FcFeatureIC` reads both the snapshot and `bg`. `BG_SKIP` keeps predictions (`_…`), the post-start liquidation diagnostics (`x_…`) and `c60` out of `featureIC`. `_…BgLiq(cyc, syms, lean, split, cl)` is called by `_…LiqIngest` and copies the closed watch's result onto the pending forecasts of the cycle it started on, with `cl.at − cl.watch.t0 − cl.gap` as the listening time (`LIQ.gap`/`LIQ.downAt` count blind time: started when the feed closes, added when it opens, and on a restore `now − the saved time`; additive to the surveillance, scoring is unchanged), and saves the store at once; `_…BgSeal` writes `x_lqw = 0` when a forecast is graded without a reading. `_…BgPack`/`_…BgUnpack`/`_…BgPersist`/`_…BgLoad`/`_…BgFlush` persist `BG1H` (`BG_PERSIST_MAX` 600; returns ×1e5, wicks ×1e4, the Wilder state exact); `_…BgFlush` also runs on `pagehide` and when the page becomes hidden, and writes the unsaved readings of a run in flight.
- **Direction selection, liquidation readings and reservation (2.44.0–2.45.0)**: `_pfFcIndSelect`/`_afFcIndSelect()` is cached on the graded count, the last graded time and the window. Its candidates are every numeric `sn`/`bg` key outside `BG_SKIP` seen on at least 15% of the window's forecasts (identical-value readings skipped); `_…FcPct` ranks each within each batch, the per-batch rank correlation with `y` (`_…FcCorr` of `_…FcRank`s) gives the window and half-window means, the screens run (same sign in both halves, size at least `FC_IND_FLOOR` = 0.02, then greedy by strength keeping a reading only if the ensemble's mean per-batch correlation does not fall), and it returns `{feats: [{k, s, o}], batches, rows, ic, table}` (`s` = `sn` or `bg`, `o` = the orientation ±1); under `FC_IND_MINB` = 6 batches it returns no features. `_pfLiqDecayed`/`_afLiqDecayed(sym, now)` walks `_…OcCycleHistory` (25 cycles), takes the cycles older than `now` and younger than the dropoff whose result for the ticker has an event (`_…LiqHas`), and weights its `lu`/`ld` by `1 − age / dropoff`; `_…BgFree` writes the result as `lqa`/`lqt`. `_pfFcReserve`/`_afFcReserve(fc, now)` fills `fc.rsv` (ticker → the event's cycle time) from the same history, prunes at the dropoff and keeps `fc.rsvC` (what started forecasts consumed, stored as the batch time minus 1 ms so an event on that very cycle reserves again); `_…FcPlan` appends up to half the revisit share of waiting tickers (not pending, in the pool, not illiquid or stablecoin) to its returned list, and `_…FcIngest` starts reserved candidates first and appends each batch's row to `fc.sl` (kept 120). The settings are `…FcIndWin` (1–48 hours) and `…FcLiqDrop` (0.25–24 hours).
- **Candle Divination (2.46.0–2.47.0)**: module state `DIV` (`libs` {p, w}, `buf` for young libraries, `last` per ticker, `loaded`, `dirty`) and the constants `DIV_SL` 6, `DIV_BOOT` 1000, `DIV_SAMPLE` 4000, `DIV_CAP` 400, `DIV_MIN_I` 24, `DIV_GRACE` 300, `DIV_SPACE` 100. `BG1H[sym]` also holds `v` (hourly volume, null where not held), kept aligned with `c`/`h`/`l`; `_…BgPack` writes it as the 11th element and `_…BgUnpack` pads older entries with nulls. `_pfDivVec`/`_afDivVec(st, i)` builds a slice's shape for the slice ending at candle `i`; `_…DivPairs(st, from, keep)` yields every (shape, what followed) pair whose following hour is newer than `from`. `_…DivLearn(sym, st)` runs from `_…BgH1` after new hours are fed (in a try, so a failure never costs the forecast its readings) and `_…DivFeed` either nudges the nearest shape (`_…DivTake`, running means) or, for a pair beyond the abstain distance, replaces the fewest-matches shape old enough (`lib.g` counts pairs fed, `lib.lr` the last replacement, `q.b` a shape's birth); a young library only collects, and `_…DivMaybeBuild` (after each readings run) clusters it with `_…DivKmeans`/`_…DivBuild`. `_…DivEnsure` loads `__ew_…_div_v1` once and calls `_…DivBoot`, which samples the cached candles for any library still missing. `_…DivRead(st)` runs at the end of `_…BgH1Feat` and returns `dvp`/`dvv` and the diagnostics. In `_…FcIndSelect`, `_…DivLive(out)` adds `dvp`/`dvv` at sign +1 when no test verdict (a row with a correlation) exists, on both the under-`FC_IND_MINB` path and after the greedy pick; readings with the toggle off are skipped, and the cache key includes the toggle. `_…FcIndDir` requires at least 2 readings only as far as the batch has columns with any values. `_…DivPanel`/`_…DivSpark` draw the panel, `_…DivExport` builds `candleDivination`, `_…DivReset(rebuild)` backs the two buttons.
- **Liquidation event size (2.48.0)**: `_pfLiqIngest`/`_afLiqIngest(entry)` collects each watched ticker's event (`z` = |liquidated shorts − liquidated longs|), builds the yardstick from `_…LiqHistLive` (the stored `lqh` inside the sample store, aged by `_…LiqHistMs`: the setting, floored at the Score Horizon) plus the batch's own sizes through `_…LiqSizeStats` (`{n, med, peak, bottom}`), then writes `pp = sign(net) × _…LiqScale() × min(z, peak) ÷ med` as `r` (0 when `z` or `med` is 0) and appends the batch to `lqh` (capped at 5000). `_…LiqHistStats()` is the summary the status line shows; the leader publishes it as `lqs` in the shared `sampleScore` and a follower adopts it. The sample scorecard's liquidation weight is now 1; the profile import accepts `lqh`.
- **Forecast net profit (2.49.0–2.49.1)**: `_pfFcNet`/`_afFcNet(recs)` filters the batch's forecasts to those with a recorded `m`, converts `e` and `m` to the bot's favor with `_…SampleDir()`, keeps those with `e > 0`, takes the top `cfg.maxPos` (3 if unset) by `e` and sums `minNotional × m ÷ 100`. `_…FcNetBatchText`/`_…FcNetWindowText` feed two extra text lines in the Fcst view (null in other views); the window groups every graded forecast in the store by start batch. `_…FcFmt` no longer emits the influence text (`infl` is still computed and exported).
- **Forecast history and export parts**: `_pfFcIdbBoot`/`_afFcIdbBoot` (called once from init after `_…FcLoad`, never awaited, 4 s timeout, `_…FcIdbBroken` set on any failure) opens `FC_IDB`, reads every record and merges the ones the in-memory store lacks (records graded after the store's last batch are left over from a reset and are skipped; everything is skipped when following), sorts by grading time and cuts to the keep. `_…FcSave` hands the store to `_…FcIdbPush` (one transaction that puts the rows IndexedDB doesn't hold and deletes the ones the keep trimmed; `busy`/`dirty` serialise it) and writes localStorage with `FC_LS_TAIL` (120) graded rows only once IndexedDB has returned rows on a boot (`proven`), else `min(keep, 600)`; `_…FcClear` also clears the object store. `_…FcExport(part)` builds the Export parts (`summary` by default, `graded`, `readings` and `pending` with the readings as `columns` + `rows`, `ranges`, and `store`, which only the Profile export uses because Import reads `forecast.store`); `_…Download(name, data, compact)` writes the `forecast:` parts without indentation.
- **Graylist**: there are two lists. The quiet graylist `lgray` (symbol → time it was found quiet) sits in the sample store and is written and read only by `_pfLiqPick`/`_afLiqPick`; a quiet ticker is simply not picked for the batch until the pool runs short, and it stays a normal entry candidate. The Instability graylist blocks entries and isn't stored: `_pfInstabStats`/`_afInstabStats` (memoized per history state and a `_pfLiqVer`/`_afLiqVer` counter, since `lu`/`ld` are written onto cycles already in history) sums `lu`/`ld` per symbol over the retained cycles, needs `pfInstabMinWatches`/`afInstabMinWatches` (2, no UI) watches with liquidations, scores `1 − |U − D|/(U + D)`, and flags symbols at or above `avg × (1 + Instability %/100)`. `_pfGrayHas`/`_afGrayHas` (checked in `_miwScanFetch`/`_micScanFetch`, counted as `excluded.gray`) returns true for that set, for any ticker `_pfIlqIs`/`_afIlqIs` flags (Illiquidity Filter), plus the old time-based `st.gray` for a leader (`pfDistMins`/`afDistMins`; nothing writes it any more, and the status line that counted it is gone). The Instability check works while following, and neither of those two lists does anything when Sample Scoring or Liquidation Surveillance is off; the Illiquidity check depends only on its own toggle. `_pfLiqPillClass`/`_afLiqPillClass` classifies a watch for the pills from `lu`/`ld`, falling back to the sign of `lq` on older cycles.
- **Thin poles**: a pole under **Min Samples** scores 0 and counts as lukewarm; at Min Samples its score becomes the plain mean of those readings with no shrinkage, so a rare pole (e.g. `fund-`) jumps from neutral to full weight on a handful of readings. Entry ordering discounts thin poles separately (see **Sparsity**).
- **Score Horizon**: `_pfObsHorizonMs`/`_afObsHorizonMs` (the setting, minimum 0.5 h), `_pfObsLive`/`_afObsLive` (observations inside it) and `_pfObsTrim`/`_afObsTrim` (age trim, then a byte cap from `_pfObsCap`/`_afObsCap`) are the only retention rules for the sample store. `_pfSampleBuild`/`_afSampleBuild` and the status line read `_…ObsLive`, so scores follow the horizon between saves. The copy published for a following bot is the same age trim capped at 60 KB, so a follower can hold less than the leader.
- **Export / Import**: `_pfExportPart`/`_afExportPart` builds each export from the in-memory stores (cross events through `_…CrossRead`, so the full shared log, not the partner feed); `…ExportData` adds `exportType`, `exportedAt` and `version`. `_pfImportApply`/`_afImportApply` recognizes record types by their keys, not by `exportType`, which is why single-type files, Profile and Everything all import, and it replaces only the stores present in the file. Sample observations go through `_…SampleSave`, so anything older than the horizon is dropped on import; cross events are merged on `ts|kind|source|symbol` because that log is shared with the partner bot.
- **Liquidation Surveillance**: the feed is `allLiquidation.<symbol>` on the public linear WebSocket, held at module level in `LIQ`: the socket, its subscriptions, the per-symbol tally `{up, dn, n}` (up = liquidated-short turnover, down = liquidated-long turnover, `S:'Buy'` meaning a long was liquidated), the watched set and the closed watch awaiting scoring.
  - **Feed**: subscriptions are diffed and sent 10 per request, with a 20 s ping and 5 s reconnect (`_pfLiqWsSync`/`_afLiqWsSync`, `_pfLiqWsApply`/`_afLiqWsApply`), and only while `_pfLiqOn()`/`_afLiqOn()` holds (toggle on, Sample Scoring on, not following).
  - **Picking**: `_miwScanFetch`/`_micScanFetch` calls `_pfLiqPick(pool, cap)`/`_afLiqPick` with the shuffled pool. It closes the watch that just ran (snapshots and resets the tally; a watched ticker with events that is still in the pool is kept, most turnover first, and every watched ticker without events goes into `lgray`). It then fills the batch with the kept tickers, fresh non-graylisted ones and, only if still short, the oldest-graylisted (removed from `lgray` as they return), and subscribes the new set. It returns null when off or following, and the random batch stands.
  - **Ingest**: after that scan's batch lands, `_pfSampleIngest`/`_afSampleIngest` calls `_pfLiqIngest`/`_afLiqIngest`. It writes one `k:'l'` observation per ticker with events: criteria from the fresh reading (`_pfSampleTags` with LPA included), `y = (up − dn)/(up + dn)`, `r = y × S` and `w = up + dn`, where `S` (`_pfLiqScale`/`_afLiqScale`) is the median of |latest 1h change − window average| over each ticker's latest reading (floor 0.05pp). A ticker with events that wasn't re-fetched (more liquidated tickers than the batch holds) gets none.
  - **Cycle stamps and sharing**: it also stamps `lq` (the event's pp, size-scaled since 2.48.0, 0 for watched-but-quiet) and, for tickers with events, `lu`/`ld` (liquidated-short / liquidated-long turnover in $) on the cycle the watch began on. The Liq chart view reads `lq`, and the pills and Instability Graylist read `lu`/`ld`. The leader also hands the lean over through the corridor as `liqLean` (`{cts, lq, ls}`, `ls` being the `lu`/`ld` split per symbol), keyed by the ts the cycle was published under (stamped on the cycle as `pub` from `_sharedPubTs('ocResults')` once the `ocResults` handover is queued). A follower's `_pfLiqAdopt`/`_afLiqAdopt`, run at the end of `_ocSeedFromShared`, files it on the matching cycle of its own history, trying again next scan if that cycle isn't there yet.
  - **Build**: `_pfSampleBuild`/`_afSampleBuild` ignores `k:'l'` observations while the toggle is off. Otherwise each is parsed like a price observation (`edge = dir × r`, with `dir` −1 on Winter and +1 on Chaser), weighted `min(3, w / median w)`, added to the same pole pool and cutoffs and bucketed by them. The pole scores, favored-side means and headline figures are the 50/50 mixes described in **Headline source**.
  - **Caveat**: the LPA window average, V/A, IO/L and IO/S baselines read each ticker's latest reading, so a batch weighted toward tickers that keep liquidating tilts those baselines toward active names.
  - **Persistence**: the watch persists to `__af_liq_pending`/`__pf_liq_pending` (4 s throttle while events arrive, plus each pick, ingest and page hide), with its blind time (`gap`) and, for a closed watch, its start, end and gap. The first pick after a reload restores it (dropping anything older than 12 h), reconnects the feed, and the next ingest scores it like any other. Price and liquidation observations are trimmed to the byte cap separately (`_pfObsTrim`/`_afObsTrim`).
- **Illiquidity Filter**: readings live in the module-level `ILQ.rec` (`{ SYM: { t, g } }`), loaded by `_pfIlqLoad`/`_afIlqLoad` in `init()` and saved by `_pfIlqSave`/`_afIlqSave` to `__ew_pf_ilq_v1`/`__ew_af_ilq_v1`.
  - **Measure**: `_pfIlqMeasure`/`_afIlqMeasure(sym)` makes one `GET /v5/market/recent-trade?category=linear&symbol=…&limit=3` through `_qFetch`, sorts the trade times and returns `(newest − oldest) / 2` in ms. It returns null (nothing recorded, retried next batch) on a failed fetch or fewer than 3 trades. A reading is fresh while younger than `…IlqRefreshDays` (`_pfIlqFresh`/`_afIlqFresh`); `_pfIlqIs`/`_afIlqIs` is true when the toggle is on, the reading is fresh and its gap exceeds `…IlqSlowSecs` × 1000.
  - **In the batch**: in `_ocFetchBatch`, a ticker already flagged is skipped before any fetch. Otherwise, right after its ticker fetch and before the hour candle, a ticker with no fresh reading is measured; if that makes it illiquid it's removed from the batch (`FRESH_TICKERS` entry deleted, no candle fetched, no result). The batch log line adds `N t measured (M illiquid, left out)`. The save runs once per batch and drops readings unseen for 3× the refresh window.
  - **In the pool**: `_pfGrayHas`/`_afGrayHas` includes `_…IlqIs`, so MIW/MIC leave flagged tickers out of the scan pool before the batch is drawn, and they don't take a batch slot. Counted as `excluded.gray`.
  - **Following**: a follower makes no fetch. `_pfIlqAdopt`/`_afIlqAdopt`, run in `_ocSeedFromShared`, merges the leader's shared `ilq` (`{ SYM: [t, g] }`; the newer reading per ticker wins) into its own store and never publishes it back.
- **Stablecoin Filter**: verdicts live in the module-level `STB.rec` (`{ SYM: ms }`), loaded by `_pfStbLoad`/`_afStbLoad` and saved by `_pfStbSave`/`_afStbSave` to `__ew_pf_stb_v1`/`__ew_af_stb_v1`. It adds no request: `_pfHourCandle`/`_afHourCandle` calls `_pfStbJudge`/`_afStbJudge` with every freshly fetched hour candle, which takes the range of the candle's open, high, low and close and the current price (the forming candle's close) as `(max − min) ÷ open` and stamps the ticker when it is under `…StbMinPct`. `_pfStbIs`/`_afStbIs` is true while a stamp is younger than `…StbHours`. In `_ocFetchBatch` a ticker just judged a stablecoin is dropped from the batch after its candle fetch (no result), and `_pfGrayHas`/`_afGrayHas` includes `_…StbIs`, so MIW/MIC leave it out of the scan pool (counted as `excluded.gray`) until the verdict expires. A follower never judges: `_pfStbAdopt`/`_afStbAdopt` merges the leader's shared `stb`.
- **Sparsity**: `_pfPoleData`/`_afPoleData` returns the sample count behind the bucket a tier tag lands in (Extreme or Lukewarm, by the pole's cutoff) and the median count across that bucket type's poles, read from the scoreboard (so liquidation samples count). It returns `null` for a family with no scoreboard entry at all (LPA under Sample Scoring), so `_pfSparseOne`/`_afSparseOne` skips it instead of treating it as an empty pole. `_pfSparse`/`_afSparse` turns a candidate's tags into a factor (the thinnest pole's `n / (n + Min Samples)`) and a block flag (thinnest pole under the floor % of the median). LPA still feeds the factor but is skipped when choosing the thinnest pole for the block flag, since its poles fill from liquidation events only and sit far under the median by nature. MIW/MIC apply the per-pole factor in `_miwScaledRank`/`_micScaledRank`, multiply the Co-Qual-off richness sort by the candidate's factor, and check the block flag in `_miwIsEntryBlocked`/`_micIsEntryBlocked`, which covers the entry-pool filter and the post-top-up re-check. It's inert until a scoreboard exists.
- **Win/loss counts can appear high**: a criterion shared across many slots accumulates records from all of them, and the Sponge Quota caps per criterion, not per slot.

### Cross-Tab Data Pool

Both bots share data two ways: a small registry in `localStorage.__ew_shared_v1` (with `BroadcastChannel('ew_shared')` change notices) for caches, heartbeats and open-symbol lists, and the **corridor** for the large datasets. Registry writes are last-write-wins per data type. Either bot operates normally solo — nothing is handed over and all ladder checks fall through to normal fetches.

Each bot publishes its own open-symbol list to this registry on every position open/close, and once more per heartbeat as a safety net for close paths that bypass `pseudoClosePosition` (e.g. the gap-fill audit). A following bot (`lfFollowPartner` on, partner heartbeat fresh) checks the leader's list before opening and skips any ticker the leader already holds; the leader never checks its own publish. Since the check only runs while `_lfIsFollowing()` is true, it switches itself off the instant the leader's heartbeat goes stale, with no separate expiry logic on the position data.

Not every `BroadcastChannel('ew_shared')` message carries a `localStorage.__ew_shared_v1` write behind it, though most do (`_sharedWrite`/`_sharedMerge` post a change notification after writing). `registerSharedMessageHook` is the general subscription point either kind of push is dispatched through on the receiving end.

### The Corridor

The corridor is a handover lane, not storage. It carries `bulkTickers`, `ocResults`, `sampleScore`, `fcGrade`, `liqLean`, `ilq` and `stb`. The publisher cuts a dataset's JSON into packets of up to 40,000 characters and keeps only a short window of them in localStorage: at most 4 packets at once across all datasets, so a 650 KB bulk ticker list never holds more than about 160 KB of the lane. The partner copies each packet into memory and confirms it in `__ew_xa_<type>_<bot>` (a cumulative count). The publisher deletes every confirmed packet, releases the next ones, and deletes the manifest after the last, so the lane is empty between handovers.

The receiver reassembles in memory, checks the length and checksum, and exposes the result through `_sharedRead`, which returns only what the partner handed over; a bot never reads its own publication, and `_sharedPubTs(type)` gives the timestamp the partner will file it under. The consumers then overwrite their own stored data from it. The delivered copy is memory-only, so a bot that reloads has nothing until the partner's next publish.

- **Pacing**: packets are confirmed in order. Pumping is triggered by the browser's `storage` events, a 1 s timer and each heartbeat.
- **Resend**: a receiver that reloads mid-handover, or whose reassembly fails its checksum, asks for a restart and the publisher resends from packet 0 (at most 3 restarts).
- **Abandon**: no confirmation for 120 s, or no room in localStorage for a packet, abandons that handover and logs `[SHR] ⚠` once per 30 minutes per dataset. A newer publish of the same dataset supersedes an unfinished one.
- **Partner offline**: nothing is sent while the partner's heartbeat is stale, and the ledger records it as skipped.
- **Cleanup**: at init each bot removes its own leftover lane keys, the dedicated keys from an earlier build (`__ew_sh_*`) and any legacy copy of a corridor dataset still in the registry.

### Scan Scheduler Internals

- **Stages**: `runScan` calls `_scanPipeline(ctx)`, which runs the host's `tickers` stage, then each plugin stage in load order (`pf-post`/`af-post`, then `miw-`/`mic-` `prep`, `fetch`, `pool`, `entry`). Stages share `ctx`; a plugin appends `{ id, group, run }` to `_scanStageDefs` in `transform`, and a stage returning `false` skips the rest of its group. On a host without `_scanStageDefs` the plugin falls back to wrapping `runScan`.
- **Checkpoints**: loops call `if (this._scanDue()) await this._scanCp()`, which yields once `schedSliceMs` has elapsed (40 ms while the tab is hidden). The yield is a `MessageChannel` task rather than `setTimeout`, because a hidden tab clamps timers to 1 s or more.
- **Idle lane**: `_schIdle(key, fn)` queues one coalesced job per key (extremity rebuild, re-eval, sample-store saves), flushed when the pipeline ends; `_schIdleCancel(key)` drops it, which MIW/MIC's own rebuild uses to supersede Permafrost/Ashfall's.
- **Timing**: each scan logs one `[SCH]` line with total ms, yields, long-task count and per-stage ms. `ui.scanning` stays on through the plugin stages, so a batch that outlasts the scan interval makes the next scan skip. The extremity rebuild itself is still one synchronous call.
- Every background or bulk fetch (bulk tickers, market watch, and any loaded plugin's kline and sample batches) runs through a single per-bot scheduling queue (**Scan Scheduling** in Main Config) instead of firing all at once. This keeps the browser responsive with one bot open and workable with two. Execution-critical single-symbol calls (opening, closing and watching a position) bypass the queue so order execution is never delayed behind background scanning. The scan itself is a pipeline of named stages that hands control back to the browser after each time slice (**Slice Budget**), so position watching, clicks and timers run mid-scan instead of waiting for it to finish.
- **Running both bots**: When both are open simultaneously they automatically share bulk ticker fetches, kline caches, and sample batches to halve API load. Either bot works normally on its own when the other tab isn't open.

### Live-Mode Internals

- **The tab buttons always work**: every control from **Order type** down is locked while Config Lock is on (it locks automatically while the bot runs). Settings are saved in the bot's config, so they persist and travel with Export / Import. Keys use the `ew` prefix on EverWinter and `sc` on SunChaser.
- **Balance**: fetched automatically the moment a valid key/secret pair is saved in the credentials panel, not only at page load.
- **Symbol banning**: a symbol is banned for a week when Bybit reports it can't be traded, or when it's blocked until a trading agreement is signed (for example some leveraged or inverse instruments). Both cases need a manual fix on Bybit's side, so the ban is treated as long-term instead of retrying every cycle.
- **Post-bail re-check**: after a bail sweep (manual Danger Zone bail or an automatic Drawdown Throttle bail), the plugin queries the exchange directly for any position still open in its own direction (Sell for EverWinter, Buy for SunChaser) and force-flattens it with a reduce-only close that follows the **Close** tab settings (see below). This catches positions that failed to fully fill.
- **Exchange sync cadence** (v1.5.1): the full-book `GET /v5/position/list` sync runs once before and once after each scan loop, and nowhere else. It no longer fires after an SL/TP close, so exchange-native TP/SL fills and DCA fills are picked up at the next scan boundary, at most one Scan Interval later. Entries and closes still confirm their own fills with single-symbol `position/list` calls while they are in flight.
- **Concurrent group closes** (v1.5.2): a live close doesn't return until the position is flat, because `_scLimitClose`/`_ewLimitClose` reprice and retry against the exchange (poll 2 s, reprice every **Reprice interval**), so a sequential loop stacked those waits per position. Every multi-position close path now runs its closes under `Promise.all`: `bailAll` (host), Cascade, Sacrifice and Ejection (`_miwCheckCascade`/`_micCheckCascade`, `…CheckSacrifice`, `…Eject`) and Extremity Re-Evaluation (`_pfExtremityReEval`/`_afExtremityReEval`). Each close is isolated in its own try/catch, so one failed close no longer aborts the rest of the group. Signed requests from the in-flight closes still queue through `_scDelay`/`_ewDelay` (250 ms apart), so they interleave instead of bursting. Per-position state stays safe through the `_scClosing`/`_ewClosing` guard and the host's `_closingIds` set, which make a second close of the same position a no-op.
- **Close-record lookup** (Permafrost/Ashfall): the `pseudoClosePosition` wrapper finds the trade it just closed by position id (`closedTrades.find(x => x.id === pos.id)`, skipped if the record already existed before the call) rather than reading `closedTrades[0]`. With concurrent closes another position's record can be inserted while this one is still awaiting, so index 0 and list-length growth no longer identify the right trade. The record feeds Gains Continuation, the close-score settle and the MIW/MIC direction-awareness feedback.
- **Cycle re-entry guard** (v1.5.2): each close schedules a `runScheduledCycle` about 500 ms after it finishes. The host guards the scan itself with `_cycleRunning`, but not the plugin's pre- and post-scan `position/list` syncs, so N concurrent closes would have run N syncs. The plugin's `runScheduledCycle` wrapper now returns immediately while a cycle or an earlier wrapper call (`_cycleWrapBusy`) is in progress.
- **Pre-entry check**: before each entry the plugin asks the exchange for that one symbol and skips the entry if any position is already open on it, so a new order is never stacked on a position the bot isn't tracking.
- **DCA repair**: re-places missing DCA conditional orders, and runs only in the post-scan sync. It is skipped in binary mode, for positions with no DCA orders, and for positions opened in the last 2 minutes, because order status can lag a fresh placement and would trigger a duplicate.
- **Live retry log lines** (v1.5.3): the `[EW]`/`[SC]` close and entry retry messages are logged with `live = true` (see Activity Log). Cascade, Sacrifice and Bail wrap their concurrent closes in a log batch, which used to hold every non-error line until the last close succeeded, so a close stuck in its reprice loop looked frozen.
- **Mark price ownership** (v1.5.4): the pseudo watcher is the only writer of a live position's `markPrice` (last price). `_ewSyncPositions`/`_scSyncPositions` previously overwrote it on every sync with the exchange row's `markPrice`, falling back to `avgPrice`, so displayed prices jumped toward entry at each pre- and post-scan sync and snapped back on the next watcher tick. The sync now sets `markPrice` only when the position has none yet.
- **Live position prices**: the base bot's watcher skips live positions, so the plugin prices them itself. It reads the host's WebSocket ticker when the host has one for the symbol; otherwise it makes one REST ticker call per symbol on a throttle: the **Price Poll Interval** base (default 5 s), doubling while price moves less than 0.1% and capped at 60 s. This replaces a REST call per position on every 5 s tick.

### Plugin Transform Pipeline

```
pw()  →  plugin[0].transform(def)  →  plugin[1].transform(def)  →  ...  →  Alpine
```

Each plugin's `transform(def)` receives and returns the component definition, so load order matters for method wrapping. Strategy plugins must declare `after: ['everwinter']` / `after: ['sunchaser']` so the live-trading plugin's wraps are innermost, which means live-trading plugins (EverWinter, SunChaser) must load before strategy plugins (MultiIndicator, Permafrost/Ashfall). The Plugin Manager shows the current load order and warns about conflicts.

### Bybit API Endpoints Used

**Public**: `GET /v5/market/tickers` (bulk for the symbol universe, per symbol for criteria data), `GET /v5/market/recent-trade`, `GET /v5/market/kline` (hourly bars on the bots, 5-minute bars on Permafrost/Ashfall, plus 1-hour bars for their Indicator Forecast), `GET /v5/market/account-ratio` (long/short account ratio, Permafrost/Ashfall only), `GET /v5/market/open-interest` and `GET /v5/market/funding/history` (Permafrost/Ashfall Indicator Forecast only), `GET /v5/market/instruments-info`. **WebSocket**: `wss://stream.bybit.com/v5/public/linear` (position price stream). **Signed (live mode)**: `GET /v5/account/wallet-balance`, `GET /v5/position/list`, `GET /v5/position/closed-pnl`, `GET /v5/order/realtime`, `POST /v5/order/create`, `POST /v5/position/trading-stop`, `POST /v5/order/cancel`, plus `GET /v5/execution/list` on the Psycho bots (DCA/AMa ladder fill checks). Signing: HMAC-SHA-256 via `crypto.subtle.sign`; 250ms minimum gap between signed requests (plugins).

**Call cadence**: the full-book `position/list` runs only before and after each scan loop. Single-symbol `position/list` calls happen around an entry (once before it, then polling for the fill) and while a close is repricing. On the Psycho bots, `execution/list` is called for a pending DCA/AMa stage only once price has reached that stage's trigger, plus one sweep of every pending stage after each scan loop to catch a wick through a trigger.
